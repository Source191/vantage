# Design

## Context

See proposal.md - Why. The CLI's words and fields are read only in `Adapters\Claude` (`ClaudeAgentsListing`, `ClaudeStates`, `ClaudeCli`): unknown fields are ignored, an unknown status or state becomes `DisplayState.Unknown`, and a row without a session id or full working directory is skipped. `ClaudeAgentsListingShould` parses a listing captured from 2.1.309; `ProcessRunnerIntegrationShould` already runs read-only `claude` commands when the executable is installed (`Assert.SkipWhen`). The `handoff` job in `check.yml` installs the latest CLI with the native installer, seeds workspace trust for the checkout (the one scripted trust edit CLAUDE.md allows), and runs the headless attach check; it runs only on pull requests and pushes, with `continue-on-error`. The header's Claude value is `Wording.HeaderValues(..., string? claudeVersion, ...)`, read once at start-up in `Program.cs` from `IClaudeCli.VersionAsync`. `ReleaseVersion` (Domain) already parses and orders `2.1.302`. Tests run on Microsoft.Testing.Platform (`global.json`).

## Goals / Non-Goals

**Goals:**
- A CLI release that changes what Vantage reads fails a run within a day, through Vantage's own parsing code.
- New or removed commands and flags are visible without reading release notes.
- A user on a CLI older than the minimum sees why in the header.

**Non-Goals:**
- Provoking every state word: only what an idle, prompt-less session shows (see Risks).
- Testing `attach` in the contract tests: the hand-off check already covers it and runs in the same workflow.

## Decisions

**1. The minimum is a Domain rule over `ReleaseVersion`, and the header takes its answer.** A static `ClaudeCodeSupport` in Domain holds `Minimum` (2.1.309) and `Check(string? reported)`, which answers a closed `ClaudeCodeVersion` hierarchy: `Unknown` (nothing read), `Reported(string Text)` (at or above the minimum, or a version `ReleaseVersion.TryParse` cannot read, shown as it came without a warning) and `BelowMinimum(ReleaseVersion Installed, ReleaseVersion Minimum)`. `Wording.HeaderValues` takes `ClaudeCodeVersion` instead of `string?`, and its switch names the three cases with a throwing discard arm, as the project's closed hierarchies do. `Program.cs` calls `ClaudeCodeSupport.Check(await claudeVersion)`. Alternative: compare inside `Wording`; rejected because the rule would sit with the words and be untestable apart from them. An unparseable version gets no warning because a false alarm is worse than none for an advisory message.

**2. The documented minimum is checked by a C# test, not a script.** `DocumentedMinimumShould` in `Infrastructure.Tests` (which may touch the file system) finds the repository root by walking up from `AppContext.BaseDirectory` to the folder holding `global.json`, and asserts that `README.md` and `openspec\config.yaml` both contain `ClaudeCodeSupport.Minimum` formatted as `2.1.309 or later`. Alternative: a `.github\scripts\Assert-*.ps1` step like `Assert-VersionBumped.ps1`; rejected because it would have to read the constant out of C# source. CLAUDE.md's "verified" heading names the version the facts were checked against, which may run ahead of the minimum, so it is not checked.

**3. Contract tests are opt-in by environment variable as well as by the executable.** `ClaudeContractShould` and `ClaudeHelpSurfaceShould` (the snapshots) carry the trait `Category=ClaudeContract` and skip unless `VANTAGE_CLAUDE_CONTRACT` is `1` and `ClaudeExecutable` finds the CLI. The variable is needed, unlike for `ProcessRunnerIntegrationShould`, because these tests start a real background session: a developer's ordinary `dotnet test` must never add a session to their agent list, and the `check` job must not need trust or a token. The one existing test that started a real session whenever Claude was installed (`ProcessRunnerIntegrationShould`'s middle-dot check) moves behind the same gate. The nightly runs `dotnet test --project test\Source191.Vantage.Infrastructure.Tests -c Debug` with xunit.v3's `--filter-trait "Category=ClaudeContract"` (MTP options, not VSTest's `--filter`). A developer can run the same command locally from a trusted repository.

**4. The contract test drives the real adapters through one session's life.** With the real `ProcessRunner` (which already drops `CLAUDECODE`, `CLAUDE_PID` and `CLAUDE_CODE_*` from children), `ClaudeCli` and the repository root as the working folder, the test: reads `VersionAsync` and requires a version; starts `StartBackgroundAsync` with a unique name (`contract-<UTC timestamp>`) and no prompt, so no model call is made; polls `ListSessionsAsync` for up to 30 s until the row appears; asserts it is a `BackgroundSession` whose `DisplayState` is not `Unknown`; runs the raw `claude agents --json --all` and asserts the row carries `pid`, `id`, `cwd`, `kind`, `startedAt`, `sessionId`, `name` and `status` (the fields an idle background row has, and the ones the parser needs); then stops and removes it by job id (stop and rm take only ids) and asserts the row is gone. Removal runs in a `finally` so a failed assertion does not leave a session behind. Alternative: a pwsh script calling `claude` directly; rejected (user's choice) because it re-implements the parsing and can pass while Vantage fails.

**5. Snapshots hold commands and flags, extracted by a tested C# parser.** `HelpSurface.Extract(string help)` (test project, with `HelpSurfaceShould` unit tests over captured help text) returns the sorted, distinct command names from the Commands section and every long and short option token (`--resume`, `-n`), one per line. The snapshots are `test\Source191.Vantage.Infrastructure.Tests\Contract\Snapshots\claude-help.txt` and `claude-agents-help.txt`, copied to the output folder. On a difference the test writes `<name>.received.txt` beside the test output and fails with a unified-style list of added and removed lines; accepting a change means copying the received file over the snapshot in a change that re-checks CLAUDE.md's CLI facts. Only `claude --help` and `claude agents --help` are run: `claude --bg --resume --help` starts a session (CLAUDE.md). Alternative: full help text; rejected (user's choice) because wording changes would raise alarms that need no action.

**6. A separate scheduled workflow, `claude-contract.yml`.** Triggers: `schedule` (03:17 UTC daily, off the hour to avoid the queue peak) and `workflow_dispatch`. Top-level `permissions: contents: read, issues: write`. One job on `windows-latest`: gate on `CLAUDE_CODE_OAUTH_TOKEN` as `handoff` does; checkout without persisted credentials; setup-dotnet; install the latest CLI with the native installer and print its version; seed trust for the checkout exactly as `handoff` does (CLAUDE.md's exception widens to name this workflow); build Debug; run the contract tests with `VANTAGE_CLAUDE_CONTRACT=1`; run the hand-off check with `continue-on-error` (its timings are laptop-tuned, so it marks the run but does not raise the issue); upload the received snapshots and the hand-off capture. The token is set per step (the gate, the contract tests and the hand-off check), not on the job, so the downloaded installer, the build and the issue step never have it in their environment; `handoff` in `check.yml` is tightened the same way. `DISABLE_AUTOUPDATER: 1` stays as in `handoff`: a fresh install is already the latest, and the variable stops it changing mid-run. The shared install and trust steps are copied, not extracted into a composite action, until a third user appears.

**7. One rolling issue, assigned so the watcher is notified.** A final step that runs only when the install step or the contract tests failed (an install that breaks is as much a CLI change as a listing that does): `gh label create claude-cli --force` (idempotent), then `gh issue list --label claude-cli --state open` for an open issue; if found, `gh issue comment`, otherwise `gh issue create --label claude-cli` titled "Claude Code CLI check failed", with `--assignee` set from `vars.CLAUDE_CLI_WATCHER` when the variable is set. The body says whether the install or the contract failed and carries the CLI version, the run link and the failing tests' messages (the snapshot diff among them). An assignee is subscribed to the issue, so GitHub notifies them of every comment; a variable rather than `github.repository_owner`, because an organisation cannot be assigned and the login should not be written into the workflow. Closing the issue after a fix is done by hand.

## Risks / Trade-offs

- [Only an idle session's words are exercised: `busy`, `waiting`, `blocked`, `done`, `failed` and `waitingFor` are not provoked, because doing so needs a model call that costs usage and is slow and flaky] → the snapshot diff and the captured-listing tests remain the guard for those; a change in them shows as `DisplayState.Unknown` (amber "unknown" rows) rather than a crash.
- [Starting a session on the runner uses the OAuth token's account] → no prompt is sent, so no model call is made; the session is removed in `finally`.
- [A CLI release that needs trust or onboarding changes could fail the run for reasons outside Vantage] → the issue's body carries the step output, and the run is manual to re-run.
- [Help-surface parsing depends on the help layout] → `HelpSurfaceShould` pins the parser to captured text; a layout change fails loudly as a large diff, which is itself worth an issue.
- [`ProcessRunner` drops every `CLAUDE_CODE_*` variable from its children, so on the runner the contract tests' `claude` processes do not see `CLAUDE_CODE_OAUTH_TOKEN`; whether `--bg` and `agents` need it is unverified, because the secret is not set yet and `handoff` has never run live (the README records the same caveat for it)] → the first manual run shows it; if the start fails for want of the token, the tests fail with the CLI's message and the issue says so, and the fix is a decision of its own (the token is deliberately not passed to Vantage's children).
- [Without the secret the nightly does nothing] → the gate writes a warning annotation, not a notice, so a skipped night is visible on the run.
- [The header warning reads the version once per run] → acceptable: the CLI updates between runs, and a restart re-reads it.
- [The repository-root walk is a new pattern in the tests] → limited to `DocumentedMinimumShould`, and it fails with a clear message when `global.json` is not found.

## Migration Plan

Merge, then create the `CLAUDE_CLI_WATCHER` repository variable (Settings, Secrets and variables, Actions, Variables) with the watcher's GitHub login, and run the workflow once by hand to confirm it is green and that a deliberately edited snapshot raises the issue. Rollback is deleting the workflow file; the header warning ships with 0.13.0 and is reverted like any change.
