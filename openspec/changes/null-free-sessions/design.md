# Design

## Context

See proposal.md for why. As of main at `0d90932` (Enter opens a session's tab, F5 starts and opens):
- `BackgroundSession(..., int? ProcessId = null)` is built once in production, by `ClaudeAgentsListing.ToSession` from the row's `Pid`. It is read in `SessionsView.SessionAction` (`session.ProcessId is null && !row.HasTranscript` gives `NeverSentAMessage`), `MeasureMemory` (`BackgroundSession { ProcessId: int processId }`), `Rename` (`(false, { ProcessId: null })`), `WordingOfConsole.SessionsBar` (`{ ProcessId: not null }` adds `x` and `m`), `WorktreeInventory` (`BackgroundSession { ProcessId: not null }` counts as a live session) and `SessionRowEnricher.MemoryOf`.
- `LaunchPlan(Directory, Name, PlannedWorktree? Worktree, bool ReuseExistingWorktree, ...)` is built by `LaunchPlanBuilder` (and `HereCommand` through it) and read only by `LaunchService.LaunchAsync` (`Worktree is not null && !ReuseExistingWorktree` creates the worktree).
- `SessionRow(Session, string Repository, ...)` with `FolderPath? Checkout { get; init; }`: null outside a repository. Read by `SessionsScreenDefinition.Repository` (REPOSITORY falls back to the folder's label), `WordingOfDetail.PlaceOf`, `DetailLoader` (no worktree counts outside a repository) and the enricher itself (the pull-request lookup runs only with a checkout). When git names a root Vantage cannot read as a folder, the row keeps the root's text as its repository and has no checkout, which is the same shape as outside.
- `WizardState(AllChoices, RepositoryChoice? FixedChoice, ..., int? SelectedIndex, ...)`: `FixedChoice` is set only by `Open(..., FolderPath? fixedDirectory = null)`, which `LaunchWizardDialog.Show` and `DialogEffects.StartSession` thread from the worktrees view's `s` (`StartSessionIn`) and pass null for `n` (`OpenLaunchWizard`). `ShowsChooser`, `Chosen` (`FixedChoice ?? the selected choice`), `Preview`, `Wording.WizardTitle` and `Wording.WizardChosen` read it.

By the time this change is applied, null-free-rows has given `SessionRow` a `Head` (in place of `BranchName? Branch`) and changed the enricher's branch to one; null-free-outcomes has reshaped `LaunchOutcome` and the wizard dialog's answer; null-at-the-boundary has made `LaunchPlan`'s opening prompt a value. This design builds on those types and does not touch them.

## Goals / Non-Goals

**Goals:**
- No nullable reference member, parameter or default on `BackgroundSession`, `LaunchPlan`, `SessionRow` or `WizardState` (except `SelectedIndex`, see below).
- Each of the four concepts lands in its own task group, green, so the owner can stop after any group.

**Non-Goals:**
- Changing what any key, footer, label or preview says or does.
- `WizardState.SelectedIndex int?`: Terminal.Gui's `ListView.SelectedItem` is `int?` and `LaunchWizardDialog` binds it directly; it is a value type and the boundary's own shape. The null-guard-rule allow-list names it.
- Moving `AllChoices`, `Filter` and `SelectedIndex` inside a chooser case: it would rewrite most of `WizardViewShould` for no gain in meaning, since they are already empty for a fixed folder.

## Decisions

**`JobProcess` is a closed two-case Domain record, `Running(int Id)` and `None`, and a required positional member of `BackgroundSession`.** A member rather than splitting `BackgroundSession` into two records, because every effect carries a `BackgroundSession` (stop, delete, rename, open tab) and none cares which; splitting would also break the two-kind rule CLAUDE.md states for `Session`. Required rather than an init property defaulting to `None`, because a default hides a forgotten process in a test or a new adapter; `ClaudeAgentsListing` is the only production construction. The listing's `int? Pid` becomes a `JobProcess` on the line that builds the session (`row.Pid is int pid ? new JobProcess.Running(pid) : new JobProcess.None()`); `ClaudeStates.From` keeps reading the raw `Pid`, which null-at-the-boundary owns. Readers use one `is` pattern each (`{ Process: JobProcess.Running running }`, `{ Process: JobProcess.None }`); `MemoryOf`'s switch over the session kind gains a nested pattern rather than a switch over `JobProcess`, so no `UnreachableException` arm is needed there; any switch that does name both cases follows the two-case rule.
- Risk: key gating. `SessionsBar` and `SessionsView` decide which keys a stopped job shows and refuses; `WordingOfKeyBarShould`, `SessionsViewShould` and `WordingOfDetailShould` assert them, and each keeps its expected answer.

**`LaunchPlace` is a closed three-case record in `Application\Launch`: `CurrentBranch`, `NewWorktree(PlannedWorktree Worktree)`, `ExistingWorktree(PlannedWorktree Worktree)`.** It replaces the nullable worktree and the flag that is meaningless without it. `LaunchPlan.Directory` stays (the folder the session starts in, which the builder already derives). `LaunchService` creates a worktree only for `plan.Place is LaunchPlace.NewWorktree fresh`. Separate from the `LaunchMode` enum, which is what the person chose; the place is what the builder found (an existing folder turns a new worktree into a reused one). Alternative: an enum plus the worktree, which brings the null back.
- Risk: `WizardViewShould` asserts the plan the wizard launches (`plan.Worktree.ShouldNotBeNull()`, `ReuseExistingWorktree.ShouldBeTrue()`), and `LaunchServiceShould` asserts that a reused worktree is not created; each becomes a `ShouldBeOfType` on the case with the same meaning.

**`SessionLocation` is a closed two-case record in `Application\Views`: `Outside(string Folder)` and `InRepository(string Name, FolderPath Checkout)`, a positional member of `SessionRow` in place of `string Repository` and `FolderPath? Checkout`.** `SessionRow` keeps a `Repository` member answering `Folder` or `Name` (a switch naming both cases with an `UnreachableException` discard arm), so `SessionsView`'s filter and folder keys, `DetailLoader`, `WordingOfDetail` and `SessionsScreenDefinition` read the name as before. The enricher's cache holds the location and the head together in a private record. A root git names but Vantage cannot read becomes `Outside(root text)`, which is exactly today's row (that text as REPOSITORY, no checkout, the head kept), so no third case is needed. The head stays the row's own member: a folder outside a repository already has whatever head null-free-rows gave it, and moving it into `InRepository` would make this change rework null-free-rows'.
- Risk: REPOSITORY labelling (`SessionsScreenDefinition.Repository` chooses the folder label or a `WhereLabel` on the checkout), the detail pane's Worktree line (`PlaceOf`) and the pull-request lookup path (`Find` and `RefreshStaleAsync` only with a checkout and a branch). The facts in `SessionRowEnricherShould`, `WordingOfDetailShould`, `DetailLoaderShould` and `SessionsViewShould` keep their expected text; `SessionsScreenDefinition` has no test project, so the smoke check and a headless look at REPOSITORY for a session outside a repository cover it.

**`WizardOrigin` is a closed two-case record in `Application\Views`: `Anywhere` and `Fixed(RepositoryChoice Choice)`; `WizardState.Chosen` answers a `RepositoryPick`, `None` or `Picked(RepositoryChoice Choice)`.** `Open` takes a `WizardOrigin` in place of the defaulted folder, so `n` and `s` say which they are; `StartSessionIn` builds `Fixed` from the row's folder (the `RepositoryChoice` it builds today). `ShowsChooser` is `Origin is WizardOrigin.Anywhere`, and `WizardTitle` names the fixed choice by matching the case. `Chosen` matches the origin first, then the selected index. `WizardView`'s two readers (`Chosen is null` and `is not RepositoryChoice repository`) and `Wording.WizardChosen` and `Preview` match `RepositoryPick.Picked`.
- Risk: the highest of the four. `WizardViewShould` asserts state directly in about 23 lines, ten of them `Chosen!.Name`; each becomes `Chosen.ShouldBeOfType<RepositoryPick.Picked>().Choice.Name` with the same expected name, and `empty.Chosen.ShouldBeNull()` becomes `ShouldBeOfType<RepositoryPick.None>()`. The dialog's binding (`LaunchWizardDialog`) is checked headless.

## Risks / Trade-offs

- [A sibling has not landed, or landed differently] → the tasks name the types they build on; if `Head` or the outcome types differ, the affected task is adjusted before it starts, and the four groups do not depend on each other.
- [Test churn hides a changed answer] → every task changes only the shape of an assertion, never its expected value; a fact whose expected value has to change is a behaviour change and stops the task.
- [Four new small types] → each is a few lines and replaces a null and, for two of them, a flag or a second nullable that only made sense together.
