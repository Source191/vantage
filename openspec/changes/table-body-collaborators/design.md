# Design

## Context

See proposal.md for why. `TableBody<TState, TRow>` (`src\Source191.Vantage.Tui\TableBody.cs`, 586 lines at `main` 8dbf4150, 0.20.0-preview.13, untouched by the five changes that landed since the review) is built once per tab by `ConsoleScreen.Frame` (`ConsoleScreen.cs:141-143`, itself constructed in `src\Source191.Vantage\Composition\ConsoleComposition.cs` since PR #177) and never tested directly: the Tui is covered by the smoke check (`tools\HeadlessTerminal -- smoke`), the hand-off check and three small fact files in `test\Source191.Vantage.Core.Tests\Tui` (`ConfigScreenDefinitionShould`, `DialogEffectsShould`, `PaletteShould`), which can see Tui's internals. The concurrency review proved every mutable field of `TableBody` is touched only on the UI thread; the detail read (`ReadDetail`, `TableBody.cs:301-314`) and the load (`TriggerLoad`, `TableBody.cs:151-167`) run on pool threads and come back through `app.Invoke`. `DetailRequests` (`Application\Detail`) is UI-thread only. `IScreenDefinition` has three implementers. Since PR #179 `ConsoleScreen.Frame.Every(TimeSpan interval, Action tick)` (`ConsoleScreen.cs:417-428`) adds one `app.AddTimeout` per call and `StartRefreshing` (`ConsoleScreen.cs:402-415`) calls it three times: the Sessions and Worktrees tabs' `ITabBody.RefreshEvery`, and `Heartbeat.Interval` (250 ms, `Application\Diagnostics\Heartbeat.cs:13`) for the UI-thread heartbeat `ScreenContext.Heartbeat` that `performance-diagnostics` added; `terminal-gui.md` records that these timeouts keep running under a modal dialog. The Config tab's `RefreshEvery` is never read. The strip's span is read from each tab's `View.Title` (`HeaderSpan`, `ConsoleScreen.cs:395`), never `ITabBody.Title`, which nothing reads. `KeyMapping.TryFrom` (`KeyMapping.cs:23-38`) has had the house `[MaybeNullWhen(false)] out Key mapped` shape since PR #175, and its character branch is `key.AsRune.ToString()` with a one-character, non-control test. Terminal.Gui 2.5.0 (its XML docs, read 1 November 2026): `View.RemoveAll()` returns the removed views and transfers their disposal to the caller; `ApplicationToolTip.RemoveToolTip(View)` unsubscribes and drops the stored content; `Key.TryGetPrintableRune(out Rune)` answers true "when exactly one printable rune is available", and `Key.AsRune` (today's branch) answers default for a grapheme of several runes. Two ellipsis rules exist: `WhereLabel.Inside.ElideMiddle` (`Domain\WhereLabel.cs:62-73`) gives the head the odd character (`head = (kept + 1) / 2`, pinned by `WhereLabelShould` at widths 20, 57 and 64), `ConfigScreenDefinition.Middle` (`ConfigScreenDefinition.cs:73-84`) gives it to the tail and cuts without an ellipsis when `width <= 1`; no fact pins Config's split (`ConfigScreenDefinitionShould` passes width 200).

## Goals / Non-Goals

**Goals:**
- `TableBody` keeps `State`, the reducer loop (`Apply`, `Follow`, `OnKey`, `Press`), effect routing and `IEffectContext`; each collaborator owns one reason to change and the fields that go with it, so no field of `TableBody` is read by two of them.
- Rendering and behaviour unchanged: the same cells, colours, tooltips, detail requests, scroll and refresh timers, pinned by the smoke check and the definition facts.
- Every new fact is in the fast suite; the extracted collaborators change nothing the smoke check cannot see.

**Non-Goals:**
- Changing what `DetailRequests` accepts, when a load runs or how `running` is kept (`fix-refresh-ordering`).
- Making the collaborators Terminal.Gui-free so they can be unit tested; they exist to hold the `TableView` plumbing.

## Decisions

### After `columns-as-data`, and whichever lands second rebases

`ColumnSizing` is where `columns-as-data` puts each column's `Fit`, so writing it first would carry the `"NAME"` and `"AGE"` literals and be rewritten within the week. The alternative, writing it now and letting `columns-as-data` move into it, costs the same rebase twice. `wording-one-home` and `fix-refresh-ordering` touch members this change leaves in place (`WaitingText`, `LoadFailurePrefix`, `TriggerLoad`, `RunInBackground`), so for those the rule is only that whichever lands second rebases.

### `ColumnSizing<TRow>` holds the colour getters and the `selected` cache

The two colour getters are called per cell during a draw and read `selected`, a cache of `State.List.Selected` kept so they do not recompute `Visible`. Leaving the getters on `TableBody` would leave the cache there too, and `ColumnSizing` would then own the styles but not what fills them. So `ColumnSizing<TRow>(TableView table, IReadOnlyList<TableColumn<TRow>> columns, Func<TRow, Color> rowColour, IApplication app)` (the columns as `columns-as-data` shapes them, each with its `Cell`, `Fit` and `Paint`, so the cell paint is read off the column; one type parameter, as `TableToolTips` takes its columns and `rowTip`) sets `style.ColorGetter` and `table.Style.RowColorGetter` in its constructor, and `Redraw` calls `sizing.Selected(State.List.Selected)` before it replaces `table.Table`, then `sizing.ElasticWidth(rows, now)` and `sizing.RestoreOffset()` (the table loses its offset on every source swap, so the kept offset is reapplied after it, as `TableBody.cs:245` does today). The alternative name `ColumnStyling` describes the same class; the review's name is kept.

### `TableToolTips<TRow>` owns the anchor and `PointerOver`

The anchor is a zero-width view laid over the header or row under the pointer (`terminal-gui.md`); whoever moves it owns it. `TableToolTips(TableView table, IApplication app, IReadOnlyList<ColumnHelp> columns, Func<TRow, string> rowTip)` creates the anchor, exposes it as `Anchor` for `TableBody` to add to its view, wires `table.MouseEvent` and `MouseLeave`, and nests `PointerOver` (nested stays nested). `TableBody` only adds the anchor. The alternative, the tooltips class taking the parent view and adding the anchor itself, hides a child under a view it does not own.

### `DetailReader<TRow>` is a two-case null object that owns the lifetime token

Today `TableBody` guards `detailPart is not DetailPart.Pane` in `AskForDetail` (`TableBody.cs:277`), resets `detailKey` in `Shown` (`TableBody.cs:232`), compares it around `Apply` in `TriggerLoad` (`TableBody.cs:159-164`) and cancels `lifetime` in `Dispose` (`TableBody.cs:146`): four places that know whether the tab has a pane. `DetailReader<TRow>` is abstract with nested `None` (every member a no-op, `Current` a constant) and `Pane` (the `DetailPane`, `DetailRequests`, the source, the key and the `CancellationTokenSource`), built by `DetailReader<TRow>.For(TableDetail<TRow> detail, TableView table, IApplication app, DiagnosticLog log, ITabHost host)`, which for a pane also sets `table.Height` as `AddPane` does. Members: `Views` (the pane, or nothing, for `TableBody` to add to its view, as it adds `TableToolTips.Anchor`: a collaborator never adds to a view it does not own), `AskFor(TRow? selected, bool shown, bool refreshed)` (the body of `AskForDetail`, `Read` and `Show`), `AskAgain()` (for `Shown`), `object Current` (so `TriggerLoad` keeps its compare verbatim) and `Dispose`, which `TableBody.Dispose` calls before `View.Dispose()`, as `lifetime.Cancel()` runs first today. The threading stays as it is: `Read` on a pool thread, `Show` through `app.Invoke`. The alternative, a sealed class behind a `DetailPart.NoPane | Pane(reader)` switch in `TableBody`, keeps the four guards.

### `TextFit.ElideMiddle` keeps `WhereLabel`'s split and degrades to a cut below 3

One rule must win. `WhereLabel`'s is the Domain one and `WhereLabelShould` pins its output, so `TextFit.ElideMiddle(string text, int width)` keeps the odd character at the head, and below `width` 3 (one character, the ellipsis, one character, the least an elision can show) cuts to `width` with no ellipsis: at widths 0 and 1 as `Middle` does today, and at width 2, where `Middle` showed the ellipsis and the last character, which goes; so `ConfigScreenDefinition` needs no guard. `WhereLabel.Inside.Fit` keeps its `room >= 3` guard, so its output is identical; a Config value cell may move its ellipsis by one character where the two rules disagreed. `TextFit` also owns the `Ellipsis` constant both callers read. The alternative, Config's split, would change `WhereLabelShould`'s pinned text for no gain. Cell widths stay UTF-16 characters (`locale.md`).

### `KeyMapping` swaps to `TryGetPrintableRune` only if the spike agrees

`KeyMappingShould` is written first over `Key` values built in the test (`GuiKey.D`, `GuiKey.D.WithShift`, `WithCtrl`, `WithAlt`, space, `<`, the named keys, F1, a non-BMP rune) and is expected to pass against today's code: it characterises. The spike then presses the same keys at a real Windows Terminal and headless (Shift+letter, Ctrl+letter, Alt+letter, AltGr `€` on a UK layout, `<` and `>` as the scroll keys, `/`, `?`) and records which reach `TryFrom` and what `TryGetPrintableRune` answers for each in `terminal-gui.md`, dated and versioned. If every answer matches today's, the branch becomes `key.TryGetPrintableRune(out Rune rune) && rune.IsBmp ? Key.Of((char)rune.Value) : null` and the facts stay green; if any differs, `AsRune` stays and the rules file says why. The alternative, swapping first, trusts a two-line XML summary over a terminal.

### `IScreenDefinition`: `Tab`, `TabRefresh`, default members

`ConsoleTab Tab { get; }` replaces `TabTitle(TState)`; `TableBody` sets `View.Title = Wording.TabTitleFor(definition.Tab)` once in its constructor and `Redraw` stops re-setting it (`TableBody.cs:246`); `ITabBody.Title` goes because only `View.Title` is read. `TabRefresh` is a Tui closed type in its own file (`Never`, `Every(TimeSpan Interval)`); `ITabBody.Refresh` carries it in place of `RefreshEvery`. `ConsoleScreen.Frame.Every(TimeSpan, Action)` stays exactly as PR #179 left it, because the heartbeat's timer (`StartRefreshing`, `ConsoleScreen.cs:412`) is not a tab's and has no `TabRefresh` to switch over; a new private `Refresh(ITabBody body, Action tick)` on `Frame` switches `body.Refresh`, naming both cases with an `UnreachableException` discard: `Every` calls `Every(every.Interval, tick)`, `Never` adds nothing. `StartRefreshing` calls it for all three tabs (Config's tick `ReadConfig`, never run while it is `Never`), then `Every(Heartbeat.Interval, ...)` as today, so the heartbeat is untouched and the Config tab's "never used to refresh" comment (`ConfigScreenDefinition.cs:14`) goes. A `Never` tab changes nothing under a dialog either: `terminal-gui.md`'s fact that timeouts run under a modal dialog concerns the timers that exist, and `Never` adds none. The alternative, making `Every` take a `TabRefresh` and wrapping the heartbeat's interval in `TabRefresh.Every`, would dress a diagnostic timer as a tab's refresh. `OnInput`, `RowTip` and `Detail` get default bodies (`{ }`, `string.Empty`, `new TableDetail<TRow>.None()`) and the implementers that only restated them drop them (`CellPaint` is already each column's `Paint` after `columns-as-data`); `WithMessage` stays, since `with` cannot be written on an interface. The alternative, an abstract base definition, is inheritance where the house composes.

### C-07: dispose what `RemoveAll` returns

`Fill` (`ConsoleScreen.cs:380-389`) becomes `foreach (View removed in row.RemoveAll()) { removed.Dispose(); }` (its labels carry no tooltip); `ShowBar` (`ConsoleScreen.cs:555-566`) removes each label's tooltip with `app.ToolTips?.RemoveToolTip(removed)` before disposing it, the tooltips `AddBarRow` (`ConsoleScreen.cs:568-583`) registered. Ownership of a removed subview is Terminal.Gui's documented rule and goes into `terminal-gui.md`. No fact can see it; the smoke check rebuilds the bar on every tab and filter change.

### T-08 facts are built as `DetailSourcesShould` builds its sources

`SessionsScreenDefinition` needs a `StateTransitionNotifier` (over a `StringWriter`), `SessionActivity` (over a `FakeTimeProvider`), the claude path, `FolderLabels` and a `SessionDetails` over `DetailLoader`, as `ConsoleScreen.cs:141` hands them; `DetailSourcesShould.cs:84` already assembles the loader (`GitCli` over the fake process runner, `InMemoryState`, `SessionActivity`) and the new files build the notifier, path and `FolderLabels` beside it. `WorktreesScreenDefinition` needs `FolderLabels` and a `WorktreeDetails` over the same loader (`ConsoleScreen.cs:142`). `columns-as-data` creates both files with its column facts and the same fixtures, so this change adds to them: every column's `Cell`, every `Paint` arm, `RowColour` for every state kind and all six health kinds, `OnInput` observing a `RowsLoaded` into the notifier, and after this change `Tab` and `Refresh`. The alternative, a second file per definition, splits one definition's facts across two files.

## Risks / Trade-offs

- [A collaborator move changes a draw or a request order unseen, since no fact reads `TableBody`] → one collaborator per task, each verified by the build and the smoke check against a local pack; `TriggerLoad`'s compare and `Dispose`'s order are kept verbatim through `Current` and the disposal order above.
- [The Config ellipsis moves one character] → stated in the proposal; no spec or fact pins it, and `WhereLabel`'s text is unchanged.
- [`TryGetPrintableRune` differs from `AsRune` for a key the spike missed] → `KeyMappingShould` pins the keys the reducers use; the swap happens only after the spike, and the rules file records the semantics for the next reader.
- [Three parallel changes edit the same two files] → sequencing above; each is a refactor of the same shape, so a rebase is mechanical.
- [`None` as a `DetailReader` case adds a type to hold no-ops] → it removes four guards and matches `WizardEffect.None` and `StatusMessage.Blank`.
