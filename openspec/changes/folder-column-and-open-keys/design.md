# Design

## Context

See proposal.md. What the code offers today: every `SessionRow` carries `Session.WorkingDirectory` (a `FolderPath`) and every `WorktreeRow` its `Path`; `SessionRow.IsWorktree` exists only for the WT cell (`SessionsScreenDefinition.Cell`, column 4). `IProcessRunner` starts children with `UseShellExecute = false`, waits for them and drops `InheritedEnvironment` names, so it can neither open a file with its associated application nor leave an editor running. `IFolders.Files` walks a whole tree. Both reducers already have a "no row selected" footer (`NoSessionSelected`, `NoWorktreeSelected`) and the worktrees reducer refuses leftover rows without a folder through `InRealWorktree` and `Footer.LeftoverFolder`. The keys `c`, `e` and `v` are free in both views. The layering rules say nothing outside Adapters touches `Process` or `File`, and nothing outside Tui touches Terminal.Gui.

## Goals / Non-Goals

**Goals:** every decision (the folder label, which solution, which footer) lives in Core and is tested; the adapters only copy text, start a program or open a file; a folder path never reaches a command interpreter.

**Non-Goals:** a general "open with" menu, remembering the solution chosen last time, watching the editor process, opening a terminal in the folder (the worktrees view's `o` does that already).

## Decisions

- **The folder label is a Domain rule.** `FolderLabel.For(FolderPath folder, IReadOnlyList<FolderPath> roots, FolderPath home)` returns the text: the deepest root that strictly contains the folder (`IsUnder` and not equal) gives the relative path; otherwise home gives `~\...`; otherwise the full path. Pure, so every spec scenario is a fact. `Application\FolderLabels` wraps it with the roots taken from the current configuration (the repository roots plus the worktree root, read through whatever `settings-and-worktree-root` provides for reading config on use) and the home folder passed in from `Program.cs`. Both screen definitions take a `FolderLabels` and call it in `Cell`, so a settings change shows on the next redraw without touching the rows. Alternative: a label field on `SessionRow` set by the enricher; rejected because the worktrees rows would need the same field from the inventory, and the label is presentation, not a fact about the session.
- **Effects and routes.** `CopyFolderPath(FolderPath Folder)` and `OpenFolderInEditor(FolderPath Folder)` are background effects with handlers. `FindSolution(FolderPath Folder, string RepositoryName)` is an `IDialogEffect`, because the several-solutions case needs a chooser; its flow in `DialogEffects` runs `SolutionFinder` off the UI thread through `RunInBackground`, then either dispatches `OpenSolution(string File)` (a background effect), shows a chooser and dispatches the chosen one, or shows `Footer.NoSolution(folderName)`. Both reducers share one helper per key that picks the row's folder (`row.Session.WorkingDirectory` or `row.Path`) and the repository name (`row.Repository` or `row.RepositoryName`), so the session and worktree cases cannot drift.
- **Solution search** is `Application\SolutionFinder.Find(FolderPath folder, string repositoryName)` over `IFolders.FilesIn(path)`, a new non-recursive listing (the existing `Files` walks the whole tree, which in a repository means `node_modules` and `bin`). It looks in the folder, then in `src`; bin and obj are never searched because the search never descends. The result is `SolutionSearch.None`, `One(file)` or `Several(files)`; `Several` whose files include exactly one named after the repository (file name without extension, ignoring case) becomes `One`. Alternative: search during the refresh and show a SLN column; rejected because it costs a directory listing per row every five seconds for a key pressed rarely.
- **Ports.** `IClipboard.TrySetText(string text)` returns false when the clipboard stays busy. `IDesktop.OpenAsync(string file)` opens a file or URL with its associated application (ShellExecute), and `IDesktop.StartAsync(ProcessRequest request)` starts a program detached without waiting, with `InheritedEnvironment` applied; `pull-request-column` reuses `OpenAsync` for URLs. `IEditorLocator.Locate(EditorChoice editor)` returns the real executable for a preset, or null. Separate from `IProcessRunner` because its two methods both wait for the child and capture or hand over the console; folding detached starts into it would give every caller a third behaviour to think about.
- **Clipboard adapter** `WindowsClipboard` calls the Win32 clipboard (`OpenClipboard`, `EmptyClipboard`, `SetClipboardData` with `CF_UNICODETEXT`, `CloseClipboard`) through source-generated `LibraryImport`, retrying `OpenClipboard` a few times over about a quarter of a second before reporting busy. Alternatives: Terminal.Gui's `app.Clipboard` (only reachable from Tui, so the key would need a dialog route for no dialog and the handler could not be tested); `clip.exe` (a process per copy, and it appends a newline); OSC 52 (Terminal.Gui owns the output while the screen runs).
- **Editor launch without a shell.** `EditorChoice` comes from `settings-and-worktree-root` (a preset or a custom executable with arguments containing `{folder}`). `Application\EditorCommand.For(choice, executable, folder)` builds a `ProcessRequest` whose arguments are a list, the folder one element of it (for a custom editor each `{folder}` is replaced inside its own argument), so no quoting or interpolation happens anywhere. `EditorLocator` resolves presets to executables, never to `.cmd` shims: VS Code from `code.cmd` on the PATH to `Code.exe` in its parent's parent (`<install>\bin\code.cmd` beside `<install>\Code.exe`), then `%LOCALAPPDATA%\Programs\Microsoft VS Code\Code.exe` and `%ProgramFiles%\Microsoft VS Code\Code.exe`; Cursor from `%LOCALAPPDATA%\Programs\cursor\Cursor.exe`; Rider as the newest `rider64.exe` under `%ProgramFiles%\JetBrains` and the JetBrains Toolbox apps folder; Visual Studio through `vswhere.exe -latest -property productPath` (devenv opens a folder in Open Folder mode); Explorer as `explorer.exe`. A custom editor whose executable ends `.cmd` or `.bat` is refused with a footer, because Windows runs batch files through cmd.exe and its arguments would be parsed there. Alternative: the `vscode://file/` URL through ShellExecute; rejected because it covers only the VS Code family and its behaviour for folders is not documented.
- **Outcomes.** `FolderPathCopied(string path)`, `ClipboardBusy`, `OpenedInEditor(string folderName, string editorName)`, `EditorNotFound(string editorName)`, `EditorRefused(string executable)`, `FolderMissing(string folderName)` and `OpenedSolution(string fileName)`, each in its own file, with words in `WordingOfOutcomes`. The editor handler checks `IFolders.DirectoryExists` first, because a stopped session's folder may have been deleted and the editor would otherwise open an empty window.
- **Layout.** The session columns become NAME, STATE, REPOSITORY, FOLDER, BRANCH, AGE, TAB; `ExpandLastColumn` stays, so TAB takes the slack until `pull-request-column` adds PR. `IsWorktree` leaves `SessionRow` and the enricher's `Location`. The header gains a third key-hint column (`Keys3`/`KeyNames3` on `IScreenDefinition`, or the per-key labels if `header-and-help` has already replaced the multi-line labels) holding `<c> Copy path`, `<e> Editor`, `<v> Solution`.

## Risks / Trade-offs

- [An editor installed somewhere the locator does not look] → the footer names the editor and points at settings, and a custom editor with the full executable path always works.
- [The Win32 clipboard needs care: the memory handed to `SetClipboardData` belongs to the system afterwards] → the adapter allocates with `GlobalAlloc(GMEM_MOVEABLE)` and frees only on failure; `WindowsClipboardShould` writes and reads back real text, including a path with non-ASCII characters, in `Infrastructure.Tests`.
- [The clipboard test touches the real clipboard on a developer machine and the CI runner] → it saves and restores the previous text, and is the only test in a non-parallel collection.
- [`v` on a large repository where the solution sits deeper than `src`] → reported as "no solution found"; deeper search is a later change if it proves common.
- [`FolderLabel` and a root that is itself under another root, such as the worktree root inside the repository root] → the deepest containing root wins, which a scenario-level fact covers.

## Dependencies and rebasing

- Needs `remove-session-descriptions` merged first (the DESCRIPTION column and `SessionRow.Description` are gone; this change removes `IsWorktree` from the same record) and `settings-and-worktree-root` (the `EditorChoice` setting, the worktree root, and reading config on use). The names used here for those pieces follow that change's design and are renamed to match it if it settles differently.
- If `header-and-help` is archived first, the key-hint layout and the `?` help text it introduces are what this change extends; the session-listing requirement this change modifies is not touched by the other changes.
- `pull-request-column` depends on this change for `IDesktop.OpenAsync`.
