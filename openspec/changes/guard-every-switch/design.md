# Design

## Context

See proposal.md for the audit. Two facts shape the approach. First, the completeness guards already in place all take the same form: a reflection theory over the types in `Core` (`WordingShould.HaveWordsForEveryFooterCase`, `WordingOfOutcomesShould.HaveWordsForEveryOutcomeCase`, `ScreenLoopShould.SwitchQuitOrUseTheTerminalForEveryEffectThatLeavesTheScreen`) or a registry with a `Handles(Type)` query (`EffectDispatcherShould.HaveAHandlerForEveryEffectTheReducersCanProduce`). `DialogEffects` is a `switch` statement with a `default` and nothing asks it what it covers; `Show` and `IEffectContext` are internal to `Tui`, and `Tui` has no `InternalsVisibleTo`. Second, the compiler's exhaustiveness check for enum switch expressions is two diagnostics: CS8509 for a missing named member and CS8524 for an unnamed value. The repository's analysis level turns CS8524 on and warnings are errors, so every enum switch expression today carries a `_` arm, and that arm also silences CS8509. The probe (a console project built with this repository's `Directory.Build.props` and `.editorconfig`) showed: CS8524 in `NoWarn` lets a fully covered expression compile, a missing member still fails with CS8509, and a switch statement with a missing member is silent in every configuration.

## Goals / Non-Goals

**Goals:**
- A missing dialog flow fails the fast test suite, not the user's session.
- A new member on a closed enum fails `dotnet build` wherever a switch expression names the members.
- No change to what any key, footer, dialog or colour does.

**Non-Goals:**
- Making the compiler check the property-pattern decision tables or type switches over records; C# has no closed hierarchies, so those stay guarded by tests.
- Converting every `switch` statement to an expression. Only `RemoveWorktreeHandler.RemoveThroughGitAsync` converts, because it is a pure enum switch whose arms are single expressions. `Program.cs` (wiring, two cases then a fall-through) and `HereCommandRunner` (a `when` guard on `JobId`, so never exhaustive by enum alone) stay.
- Fixing the `DisplayState` pairing in this change. Unknown is a visible, spec-compliant landing ("its row shows the raw value rather than guessing"); changing it is a spec decision that needs the observed fact first.

## Decisions

- **Dialog registry over a reflection test that runs `Show`.** `DialogEffects` holds a `FrozenDictionary<Type, Action<DialogEffects, IEffectContext, ViewEffect>>` built once as a static field, each entry calling the existing private flow method, for example `(self, context, effect) => self.Rename(context, ((AskForNewName)effect).Row)`. `Show` looks the effect type up and falls back to the `NoDialogFor` footer as today; `public static bool Handles(Type effectType)` answers the test (one line, so expression-bodied as IDE0022 requires). Alternative rejected: a theory that calls `Show` for each `IDialogEffect` with a fake `IEffectContext` and asserts no `NoDialogFor` footer. Every real flow opens a Terminal.Gui dialog on `context.App`, so the test would need a running application or a null `App` that throws before the footer is reached; brittle and slow. The registry is the shape `EffectDispatcher` already has, so the two completeness facts read the same.
- **Static registry, instance flows.** The handled set does not depend on the constructor arguments (`LaunchWorkflow`, `WorktreeBase`, the two handlers), so a static dictionary lets the test ask `Handles` without constructing `DialogEffects`, whose dependencies `wizard-as-reducer` and `consolidate-helpers` are both about to change. The lambdas take `DialogEffects self` so the flows stay instance methods with their current bodies.
- **`DialogEffectsShould` lives in `Core.Tests` under `Tui\`.** The test project already references the Tui project (for `LayeringShould`), and `Handles` is public, so no `InternalsVisibleTo` is added. The theory's member data is `typeof(ViewEffect).Assembly.GetTypes()` filtered to non-abstract `IDialogEffect` implementers, the same shape as `EffectDispatcherShould`. A second fact asserts `Handles(typeof(StopSession))` is false, so the registry does not quietly claim background effects.
- **Suppress CS8524 solution-wide rather than per file.** A `#pragma warning disable CS8524` around six expressions would say the same thing six times and would be forgotten on the seventh. `Directory.Build.props` is where the repository already states its analysis stance ("every warning fails the build"), so the one-line addition and its comment belong beside that. Alternative rejected: keep the `_` arm but make it `_ => throw new UnreachableException()`; that still hides CS8509 and turns a compile-time check into a runtime one.
- **Name every member; no `_` arm on a closed enum.** After the suppression, the six expressions list each member explicitly: `Sessions.AttentionRank` adds `Unknown => 6`; `Palette.ForState` adds `Stopped => Grey` and `Unknown => Grey`; `WorktreesScreenDefinition.RowColour` adds `Orphan => Red` and `Broken => Red`; `RemoveWorktreeHandler.RemoveAsync` names `RemovalOutcome.RemoveWorktree`; `Wording.Here` names `LaunchOutcomeKind.Failed`; `ListSelection.EditFilter` adds `Up => this` and `Down => this`. The values are the ones the discard arm produces today, so no test changes. `RemoveThroughGitAsync` becomes a switch expression over the tuple of `decision.Branch` and the typed `BranchName?` that `value-objects-ids` introduced: `(Delete, BranchName)` awaits a private method that deletes the branch and returns `RemovedAndDeletedBranch`, `(Ask, BranchName)` keeps it, and `(None, _) or (_, null)` is a plain removal, which is what the former `default` did for a folder name that is not a valid branch name; a new `BranchAction` member paired with a branch is then uncovered and fails with CS8509. This is legal because the method is already async and `RemoveAsync` in the same file already awaits inside a switch expression.
- **The DisplayState check is a recorded observation.** The task is to attach to a background session that has completed a task, send it a new prompt, run `claude agents --json` while it works and after it finishes, and write the observed status and state pairings into CLAUDE.md's "Claude Code CLI facts" with the CLI version. That is where verified CLI behaviour lives. If `busy` ever pairs with `done`, `blocked` or `failed`, the follow-up is an OpenSpec change against `session-listing` adding a scenario and a `Status: "busy"` arm that maps to working (in `DisplayState.From`, or `ClaudeStates` once `consolidate-helpers` lands).

## Risks / Trade-offs

- [Suppressing CS8524 means an out-of-range enum value cast from an integer would hit no arm and throw `SwitchExpressionException` at runtime] → no enum in this solution is parsed from an integer; `DisplayStateKind` and `WorktreeHealthKind` are produced by domain code from strings and booleans, the rest by the code itself. The comment in `Directory.Build.props` states the assumption so it is revisited if an enum ever comes off the wire.
- [`FrozenDictionary` lambdas cast the effect, where the `switch` pattern-matched it] → each cast is one line beside the type key that guarantees it, and `DialogEffectsShould` runs each key through `Handles`; a wrong cast would surface on the first use of that key in the hand-off check or the manual pass in task 3.3.
- [`wizard-as-reducer` and `consolidate-helpers` both edit `DialogEffects.cs`] → this change touches only `Show` and adds the registry; the flow methods' bodies are untouched, so the merge is an ordering of hunks rather than a conflict of intent. Land this change first if possible; it is the smallest.
- [Removing a `default` from a switch statement that is not a pure enum switch would fail the build with CS8509 for a reason unrelated to enums] → the task list names the six expressions and one statement exactly; nothing else changes.

## Open Questions

- Whether `claude agents --json` ever reports `busy` with a state other than `working` or null. Deferrable: the answer changes a later spec, not this change's approach or tasks.
