# Design

## Context

See proposal.md for why. The design reads against `main` at 8dbf4150 (0.20.0-preview.13). `Wording` is one static partial class in `Application` (`Wording.cs` and eight `WordingOf*.cs` files, `WordingOfReleaseNotes.cs` the newest, from PR #180), each with a `Wording*Should` test pinning its sentences verbatim; the smoke script (`tools\HeadlessTerminal\SmokeScript.cs`) reads its keys by hint (`KeyFor`, `:113-119`) and its markers from `Wording`, and uses none of the waiting words. Nine dialog titles already come from `Wording` (`WizardTitle`, `SettingsDialogTitle`, `ChooseSolutionTitle`, `MemoryDialogTitle`, `ProblemReportDialogTitle`, `WhatsNewBeforeUpdateTitle`, `WhatsNewAfterUpdateTitle`, `FolderPickerTitle`, `FilePickerTitle`) and so do some buttons (`BrowseButton`, `ProblemReportButtons`, `UpdateNowButton`, `ReleasePageButton`, `LaterButton`, `CloseButton`) and captions (`PlaceCaption`, `WizardChosenCaption`, `ProblemReportTitleCaption`, `ProblemReportPreviewCaption`), so the Tui is inconsistent with itself rather than following a different rule. The hotkey mark has three shapes today: `Confirm.Ask` (`Confirm.cs:30`) prefixes `_` to each button it is given; `WhatsNewDialog` (`:35, 43, 54`) prefixes it to a bare `Wording` word (`$"_{Wording.LaterButton}"`); every other dialog writes the `_` into its literal, as `Wording.BrowseButton` does. `KeyHelp(string Key, string Hint, string Line, string Tip)` names its key by text (`"enter"`, `"esc"`, `"←"`, `"n"`), which `WordingOfKeysAndColumnsShould:13-29` pins and `SmokeScript.Sequence` (`:130-135`) turns into keystrokes; `Application.Views.Key(KeyName, char)` is what the reducers see. `DisplayState(Kind, Label)` is a sealed record with six singletons, `Starting` (Kind `Working`, label "starting") and `Unknown(label)`, built only in `Infrastructure\Claude\ClaudeStates.cs` (`:16, 22`); `SessionActivity`, `StateTransitionNotifier`, `Palette.ForState` and the counts read `Kind` only, and `WordingOfScreensShould:199-201` pins that a starting row counts as working. `Microsoft.CodeAnalysis.CSharp` is referenced by `Infrastructure.Tests` alone, where `OneTypePerFileShould` parses every source file and `RepositoryFolder.Root()` finds the repository. `Core.Tests` references Tui and already tests `ConfigScreenDefinition`, `DialogEffects` and `Palette` in its `Tui` folder.

## Goals / Non-Goals

**Goals:**
- Every word a person reads is declared in `Wording`, pinned verbatim by a fact, and read by the Tui or the Application at the last moment; nothing visible changes.
- A fact the Tui needs (which key, which enum member, which glyph) is carried as a value from the Application, never recovered from text.
- A mechanical check catches the next sentence declared in `Application` outside `Wording`.

**Non-Goals:**
- Reshaping `IScreenDefinition`, the `Cell` switches or the key dispatch (the open changes `table-body-collaborators` and `columns-as-data`).
- Tying `KeyHelp` entries to reducer arms (V-06 c).
- Unifying the hotkey-mark shapes.
- Testing Terminal.Gui layout.

## Decisions

### Tab-scoped words are closed-enum switches; dialog words are one member each

`Wording.WaitingText(ConsoleTab)` and `Wording.LoadFailurePrefix(ConsoleTab)` switch over the three tabs with no discard arm, so a fourth tab fails the build at each, as `TabTitleFor` does. The dialog titles and buttons become members named for their dialog (`KeysTitle`, `DeleteBranchTitle`, `DeleteBranchButtons`, `RenameTitle`, `CloseEmptyTitle`, `CloseEmptyButtons`, `ForceRemoveTitle`, `DeleteSessionTitle`, `DeleteButtons`, `CancelButton`, `CancelWithEscButton`, `CopyNameButton`, `StartButton`, `SaveButton`, and `UpdateTabTitle` for the update tab), following the nine titles already there rather than a `DialogTitle(DialogName)` switch, which could not serve the state-taking titles. The alternative, one switch for all, was rejected for that reason. The tab-title word (`DialogWord`, `WordingOfScreens.cs:22-38`: "Delete session" for the tab, "Delete session" for the dialog) stays a separate fact: the tab word is short by design (`TabTitleDuring`), the title is the dialog's, and two members that happen to agree today are allowed to diverge. Each new `Wording` member holds exactly the text the dialog passes today, `_` included where the dialog wrote it (`"_Cancel (Esc)"`, `"Cop_y name (F2)"`, whose mark sits mid-word and so cannot be prefixed) and excluded for `Confirm.Ask`'s buttons, which add their own; so `BrowseButton`'s precedent is followed and nothing visible changes. The one exception is Close: `Wording.CloseButton` ("Close", bare) exists since PR #180 and a second `CloseButton` could not be declared beside it, so `HelpDialog.cs:31` and `MemoryDialog.cs:35` write `$"_{Wording.CloseButton}"` exactly as `WhatsNewDialog.cs:54` does. That leaves `Wording` holding both shapes (`BrowseButton` with its mark, `CloseButton` without); unifying them is a visible-text risk for no reader's gain, so it is recorded here and left.

The original design served one `UpdateVantageTitle` to the update question's dialog and the update tab. PR #180 replaced that question with the What's new dialog, titled by `Wording.WhatsNewBeforeUpdateTitle(current, newest)` ("Update Vantage 0.20.0 to 0.21.0"), so the member and the `UpdateButtons` list are gone from this design; "Update Vantage" now names only the tab (`TabScripts.cs:50`) and is `UpdateTabTitle`.

### Captions and hints are layout text, and the rule says so

The static captions in `WizardControls` (`:77, 95, 98, 100, 102, 117`), `SettingsControls` (`:30, 35, 39, 43, 47`), `NameDialog.cs:23` and `TypedConfirmationDialog.cs:35`, and the two under-field hints (`NameDialog.cs:27`, `TypedConfirmationDialog.cs:42`), stay in their binders: they name the control beneath them, never vary with state and are read in place. A caption that varies with state (`WizardChosenCaption`) is `Wording`'s, as now. `CLAUDE.md`'s Wording section (`:74-78`) gains the sentence "static captions and hints beside a control may stay in the Tui binder that lays them out; the waiting words, failure prefixes, titles, buttons and anything that varies with state are `Wording`'s". The alternative, moving some thirty captions, buys a fact per caption and no one home, since each is read by one control.

A sweep of every string literal in the Tui (1 November 2026, `rg -o '"[^"]*"' src\Source191.Vantage.Tui`) found two fragments a person reads that the categories above miss, and both become `Wording`'s because each varies with state or is read by a `Wording` sentence. `DialogEffects.cs:98` passes `"folder name"` as the `expectedKind` that `Wording.NothingTypedYet(expectedKind, expected)` (`Wording.cs:40`) puts in its sentence; the force-remove dialog is `TypedConfirmationDialog`'s only caller, so `NothingTypedYet(expected)` says "folder name" itself, `TypedConfirmationDialog.Show` loses the parameter and `WordingShould:628` is rewritten from its made-up "worktree folder" to the one real text ("Nothing typed yet; the folder name is Northwind.Orders-fix-123."). `TableBody.cs:129` composes `$"filter: {text}_  {Wording.Describe(title)}"` while a filter is typed; `Wording.FilterBeingTyped(string text, TableTitle title)` holds it, pinned by a `WordingOfScreensShould` fact against the quotation in `openspec\specs\console-layout\spec.md:86` (`filter: tem_`). Everything else the sweep found stays: the glyphs `"-"` (`WorktreesScreenDefinition.cs:36`, no last commit) and `"…"` (`ConfigScreenDefinition.cs:10`, `ConsoleScreen.cs:360`, `TableBody.cs:483`), the `" "` a Label needs before it is given text (`ProblemReportDialog.cs:31, 55`, `SettingsControls.cs:145`, `TypedConfirmationDialog.cs:40`; `.claude\rules\terminal-gui.md`), compositions of `Wording` values with punctuation only (`TableBody.cs:125, 437`, `DetailPane.cs:38`, `ToolTips.cs:11`), the `.exe` extension (`SettingsDialog.cs:97`), the `"NAME"`/`"AGE"` coupling (`TableBody.cs:480, 486`, `columns-as-data`'s), the throw messages (`ConsoleScreen.cs:209`, `SettingsControls.cs:53`, `VantageIcon.cs:57`) and the `"Enter"`/`"Esc"` at `ConsoleScreen.cs:595-596`, which the `KeyHelp` decision below removes.

### `LaunchPreview` and `TabScripts` keep their decisions and borrow their words

`LaunchPreview.Describe` still chooses among its four cases (current branch, not a repository, no slug yet, planned worktree) and returns `Wording.PreviewCurrentBranch(repositoryName)`, `Wording.PreviewNeedsRepository`, `Wording.PreviewBeforeAName(repositoryName, worktreeRoot)` or `Wording.PreviewWorktree(folderName, worktreeRoot, branch)`; `LaunchPreviewShould` asserts which member is chosen and `WordingShould` pins the words, so the four sentences are pinned once. `TabScripts.Trust` reads `Wording.TrustTabTitle(folderName)` and `Wording.TrustTabMessage(folderName)`, and `Update` reads `Wording.UpdateTabTitle`; the message still reaches the script only through `PowerShellScript.Quote`, which `TabScriptsShould.QuoteUserTextSafely` keeps checking. The alternative, declaring `LaunchPreview` and `TabScripts` as exceptions in `CLAUDE.md`, was rejected because it leaves nothing mechanical to hold the rule and the same `TabScripts` already reads `UpdateFailedHint` from `Wording` (`:56`).

### The sentence fact parses source and skips `throw`

`SentenceLiteralsShould.KeepSentencesInWording` in `test\Source191.Vantage.Infrastructure.Tests`, beside `OneTypePerFileShould`, parses every file under `src\Source191.Vantage.Core\Application` with Roslyn and fails for a `LiteralExpressionSyntax` string or an `InterpolatedStringExpressionSyntax` whose last text part ends in `.`, `?` or `!`, except in `Wording*.cs`, `CommandLine.cs` and `Diagnostics\` (the three exceptions `CLAUDE.md` names) and except under a `ThrowStatementSyntax` or `ThrowExpressionSyntax` ancestor, because an exception's message is never user text by the house rule and today's five such messages (`Effects\EffectDispatcher.cs:30`, `ScreenLoop.cs:37`, `Views\ConsoleView.cs:23`, `Views\SettingsScope.cs:27`, `Diagnostics\DiagnosticLine.cs:59`) would otherwise fail it. The classes `main` added to `Application` since the review (`HeaderSettingsRow`, `RequiredPrograms`, `ConsoleLoads`, `UpdateCheckSwitch`, `WhatsNewOnStart`, `ReleasePage`, the heartbeat and counts) hold no sentence literal, so the fact's first run still names the five sites in `LaunchPreview` and `TabScripts` alone. It lives in `Infrastructure.Tests` rather than `Core.Tests\Architecture` because that project alone references `Microsoft.CodeAnalysis.CSharp` and adding it to `Core.Tests` would slow the two-second suite's build; the alternative, a text rule over `Views` and `Actions` only, misses `Launch` and `TabScripts`, which is where the strays were.

### `KeyHelp` is built from a `Key`; its text is derived

`KeyHelp(Key Press, string Hint, string Line, string Tip)` and `KeyHelp.HelpOnly(Key, line, tip)`; the string `Key` becomes a computed property from `Press` by one switch over `KeyName` naming every member (Enter "enter", Escape "esc", Left "←", Right "→", Up "↑", Down "↓", Backspace "backspace", Character the character itself), and `HelpKey` capitalises the named ones as today (`KeyHelp.cs:17`). The `Wording` lists change from `new("enter", ...)` to `new(Key.Enter, ...)` and `new("n", ...)` to `new(Key.Of('n'), ...)`; `WordingOfKeysAndColumnsShould` and `SmokeScript.Sequence` keep reading the same strings. `KeyBarItem` gains `Key Press`, filled by `Placed` and `OwnItem` in `WordingOfConsole.cs:154-172`, and `ConsoleScreen.Click` (`:585-599`) presses `item.Press`. The alternative, a computed `Press` decoded from the string, keeps text as the home, which is the finding.

### One `OptionSelectors` helper, by position in `Enum.GetValues`

`Tui\OptionSelectors` (static): `Labels<TEnum>(Func<TEnum, string> describe)` and `For<TEnum>(int x, Func<TEnum, string> describe)` build a selector whose labels are `Enum.GetValues<TEnum>()` described in order; `Index<TEnum>(TEnum)` and `At<TEnum>(int?)` convert by `Array.IndexOf` over the same array, never by cast, so a reordered or renumbered enum cannot pick the wrong label. It covers `WizardControls.Mode` and `BaseRef` (`:28-33, 56, 58`), `SettingsControls.Editor`, `BaseRef` and `Place` (`:25, 28-29, 65, 71, 73`), and the `ValueChanged` handlers at `LaunchWizardDialog.cs:91-92` and `SettingsDialog.cs:155, 158-159`, which today convert by `== 1` or an `(EditorPreset)`/`(LaunchMode)` cast. It does not cover `SettingsControls.ShowPresets` (`:109-119`, PR #178), which retitles the Editor selector's existing `CheckBox`es in place from `Wording.Describe(EditorPreset, PresetSearch)` once the dialog's look has answered, because setting `Labels` would rebuild the options and lose focus (`.claude\rules\terminal-gui.md`); it zips the options with `Enum.GetValues<EditorPreset>()`, the same order `OptionSelectors` uses, so one ordering holds throughout. The original design left the whole Editor selector to `editor-not-found` to avoid overlapping an open change; that change landed in PR #178, so the selector's construction and index conversions join the helper and only the relabelling stays as PR #178 wrote it. `Labels`, `Index` and `At` are pure and tested in `Core.Tests\Tui\OptionSelectorsShould`; `For` is the one line that constructs a Terminal.Gui view.

### `DisplayState` is a closed hierarchy whose only words are the CLI's

`public abstract record DisplayState(DisplayStateKind Kind)` with three nested cases: `Known`, a non-positional record with an explicit private constructor and six `public static readonly Known` fields of its own (`Known.Working` to `Known.Stopped`), so no `Known` with the `Unknown` kind can exist; `Starting` (Kind `Working`, no members: being its own case is what distinguishes it); and `Unknown(string RawWords)` (Kind `Unknown`). `DisplayState` exposes `public static DisplayState Working => Known.Working;` and the other five, so those call sites are unchanged; a nested type and a static member cannot share a name (CS0102), so the static `Starting` field and `Unknown(string)` method go, and their five call sites (`ClaudeStates.cs:16, 22`, `ClaudeAgentsListingShould:143`, `WordingOfScreensShould:201`, `DisplayStateShould:22`) write `new DisplayState.Starting()` and `new DisplayState.Unknown(text)`, the house's `new X.None()` shape. Record equality still separates `Starting` from `Working`; every `Kind` reader is untouched. `Wording.StateWord(DisplayState)` is written first against today's shape (`Starting` told apart by equality with `DisplayState.Starting`, `Unknown` read through `Label`) and the `Label` readers moved onto it, so every commit builds; the reshaping then only changes its body to a switch naming the three cases and, under `Known`, every `DisplayStateKind` (the `Unknown` kind under `Known` throws `UnreachableException`). `SessionsScreenDefinition.cs:43` and `WordingOfConsole.CountedState` (`:121-130`) read it, the latter keeping "need input" for several and "working" for a group that holds a starting row. `ClaudeStates.cs:22` keeps building the unknown case from `$"{status}/{state}"`. The alternative, a `bool Starting` flag on one record, admits `Starting` with any kind.

### `terminal_bell` is a constant in Ports, not on the interface

`public const string TerminalBell = "terminal_bell";` on `NotificationChannelState`, usable as a constant pattern in `Configured { Value: NotificationChannelState.TerminalBell }` at `SetupFactsReader.cs:51` and `TerminalSetupRunner.cs:152`, assigned by `ClaudeSettings.cs:58` and `FakeClaudeSettings.cs:43`, and interpolated into `Wording.ClaudeBellPlan` and `ClaudeBellEnabled` (`Wording.cs:354-355, 362`). A constant on `IClaudeSettings` was considered and rejected because SonarAnalyzer's S1214 (constants in interfaces) is not silenced in `.editorconfig` and warnings are errors.

### Repetition inside `Wording`

`EditorName` (`WordingOfOutcomes.cs:322-332`) becomes `editor.Preset == EditorPreset.Custom ? Path.GetFileNameWithoutExtension(editor.Executable) : Describe(editor.Preset)` (a ternary, not a switch with a discard arm), reusing the one-argument `Describe` (`Wording.cs:174-184`) that PR #178's two-argument `Describe(EditorPreset, PresetSearch)` (`:187-197`) already reuses. `Counted` (`WordingOfScreens.cs:83`) is deleted for `Count` (`WordingOfOutcomes.cs:320`), which produces identical text. A private `IsToday(DateTimeOffset at, DateTimeOffset now, TimeZoneInfo zone)` in `Wording.cs` serves `WordingOfConfig.When` (`:169-176`) and `WordingOfDetail.DayAndTime` (`:187-192`), each keeping its own format.

## Risks / Trade-offs

- [A moved word changes by a character and the screen differs] → every member is pinned verbatim by a fact written from the current literal before the Tui reads it; the two spec quotations keep holding; the smoke check's markers come from `Wording` and never from the waiting words.
- [`KeyHelp`'s new shape ripples through 50 list entries (18 Sessions, 16 Worktrees, 9 Config, 7 tab keys) and `KeyBarItem`] → the string `Key` and `HelpKey` are kept as computed properties, so `WordingOfKeysAndColumnsShould`, `WordingOfKeyBarShould` and `SmokeScript` compile and pass unchanged.
- [`DisplayState` reshaping breaks a `Label` reader not found by the build] → the build finds them all (`SessionsScreenDefinition`, `WordingOfConsole`, `DisplayStateShould`, `ClaudeStatesShould`, `Contract\ClaudeContractShould:54`, which compiles even when skipped); `NullFreeModelsShould` and `SealedTypesShould` check the new cases.
- [The sentence fact fails on a message that is not user text] → the `throw` exclusion and the three folder exclusions are the whole allow list; a new exception message outside a `throw` is a finding, not noise.
- [Three open changes touch the same files] → proposal.md names the overlap (`IScreenDefinition`'s members, the `Cell` switches, the discard arms in `SetupFactsReader` and `TerminalSetupRunner`), and this change alters none of them.

## Migration Plan

Nothing to migrate: no state file, key, setting or command line changes. Rollback is reverting the pull request.
