# Design

## Context

`UpdateCheck` (Application) reads `update-check.json` through `IUpdateCheckRecords`, asks `IPackageVersions` (adapter `NuGetPackageVersions`: one anonymous GET of `https://api.nuget.org/v3-flatcontainer/source191.vantage/index.json`, 3 s timeout, `Vantage/<version>` user agent) at most once a day, and holds the newest release in a `SharedSnapshot<NewestRelease>`; `Status` gives `UpdateStatus` (`Off`, `UpToDate`, `Available(Current, Newest)`). The header's notice is built in `WordingOfScreens` (line 60) as part of one plain string. `U` raises `UpdateVantage` (an `IDialogEffect`); `Tui\DialogEffects.ConfirmUpdate` calls `UpdateVantage.Decide` and, on `Ask`, `Confirm.Ask(...)` with `Wording.UpdateQuestion`, then dispatches `StartUpdate`, handled by `StartUpdateHandler`. `IDesktop.OpenAsync` already opens a URL through ShellExecute. `TextTone.Amber` exists for frame text. The package sets `PackageReleaseNotes` to a link to the GitHub Release; `release.yml` creates releases with `--generate-notes` and checks nothing out in its release job. nuget.org limits `releaseNotes` to 35,000 characters ([nuspec reference](https://learn.microsoft.com/nuget/reference/nuspec#releasenotes)).

See proposal.md for the why and specs/ for the behaviour.

## Goals / Non-Goals

**Goals:**
- One hand-written source of notes, read the same way from nuget.org and from inside the installed tool.
- No new host, no new wait: `U` and the start-up dialogue read what is already on disc.
- Parsing and choosing sections are pure Domain rules with in-memory tests; the adapters only fetch text.

**Non-Goals:**
- Rendering Markdown beyond headings and bullets (no bold, links or tables in the dialogue).
- Notes for prereleases, or for versions published before the changelog exists (they show as "no notes").

## Decisions

- **The changelog format is a narrow Keep a Changelog.** `## Unreleased`, `## 0.21.0` (optionally followed by ` - 2026-11-20`), `### Added|Changed|Fixed|Removed|Security|Internal`, and `- ` bullets of one line each, ending `(#171)`. `Domain\ReleaseNotes.TryParse(string?, out ReleaseNotes)` reads it, skipping lines it does not understand and answering false only when no version section is found; `ReleaseNotes.Between(ReleaseVersion after, ReleaseVersion upTo)` answers the stable sections in that range, newest first, without Unreleased and Internal. Control characters (Unicode category Cc, which includes ESC) are dropped from each line as it is parsed, so nothing downstream sees them. Alternative: GitHub's generated notes; rejected because they are PR titles written for contributors and need the GitHub API. Alternative: the OpenSpec proposals' What Changes; rejected because they are written for the specs and include internal changes.
- **The notes travel inside the package, as the changelog is.** The csproj sets `PackageReleaseNotes` with `$([System.IO.File]::ReadAllText('$(MSBuildThisFileDirectory)..\..\CHANGELOG.md'))` and packs `CHANGELOG.md` into the tool's folder beside `vantage.dll` (as `vantage.ico` is shipped). Filtering happens in Vantage, not at pack time, so packing needs no script. Alternative: a pack-time script that writes filtered notes; rejected as a build dependency for no user-visible gain.
- **The check fetches the nuspec only when it finds a newer release.** `IPackageVersions` gains `NotesAsync(packageId, version, cancellationToken)` answering `PackageNotes.Read(text)` or `PackageNotes.NothingLearned`, implemented in `NuGetPackageVersions` as a GET of `.../source191.vantage/<version>/source191.vantage.nuspec` with the same client, timeout and user agent, reading `metadata/releaseNotes` with `XmlReader` (DTD processing prohibited). Same host, same anonymity, so the README's "What the check sends" gains one sentence, not a new endpoint. Alternative: fetch on `U`; rejected because the dialogue would wait up to 3 s and need a loading state.
- **The record carries the notes.** `UpdateCheckRecord.Checked` gains `NewestNotes` (`ReleaseNotes` or a `ReleaseNotes.None` case, never null); `update-check.json` gains an optional `notes` string holding the nuspec text as read, so a record written by an earlier version still reads (no notes). A due check that finds the same newest version with no recorded notes asks for them again; one that already has them does not.
- **Announcing once needs no new state.** `UpdateCheck.RunAsync` compares the newest it found with the newest it read from the record; when the found one is higher than both the record's and the running version, it holds a pending announcement in a `SharedSnapshot`. The screen takes it (once: taking clears it) when it next reads the header's update status and shows `StatusMessage.NewerReleaseFound(version)` (Info tone); exactly where the screen reads it is settled by the first failing test in that task. Alternative: an `announced` field in the record; rejected because the recorded newest version already says what was seen.
- **The What's new dialogue is one Tui view for both moments.** `UpdateVantage.Decide` returns `UpdateDecision.Ask(Newest, Notes)` (the sections from `Between(current, newest)`); `Tui\WhatsNewDialog` shows a title from `Wording`, a read-only scrolling list of version headings and entries, and buttons. Before an update: Update now, Release page, Later (default focus Later). After an update: Close only. Release page raises `OpenReleasePage(ReleaseVersion)` (a background effect, handler `OpenReleasePageHandler` over `IDesktop.OpenAsync`, URL `https://github.com/Source191/vantage/releases/tag/v{version}` built only in `Application\ReleasePage`, the one home of the URL), so the dialogue stays open. The yes or no `Confirm.Ask` for updates and `Wording.UpdateQuestion` go.
- **"Last run" is its own small state file.** `%LOCALAPPDATA%\Vantage\last-run.json` (`{"version": "0.21.0"}`) through a new port `ILastRunVersion` on `JsonFileStore`. It is independent of `update-check.json` because the after-update dialogue must work with the check turned off or `VANTAGE_NO_UPDATE_CHECK` set, and when the user updated by hand. A prerelease running version neither reads nor writes it. The packaged notes are read through a port `IPackagedReleaseNotes` (adapter reads `CHANGELOG.md` from `AppContext.BaseDirectory`), and `Application\WhatsNewOnStart` decides `Show(sections)` or `Nothing` before `ScreenLoop` opens the console; `ScreenLoop` shows the dialogue before the first key is read, so no keystroke can race it.
- **Enforcement sits beside the version check.** `.github\scripts\Assert-ChangelogUpdated.ps1` reuses `Assert-VersionBumped.ps1`'s tool-path list (moved into a shared `ToolPaths.ps1` dot-sourced by both): when a tool path changed, `CHANGELOG.md` must differ between Base and Head; when Head's `Version` is stable, Head's changelog must have its `## <version>` section and an Unreleased section with no entries; and the file must stay under 35,000 characters. `check.yml` runs it where it runs `Assert-VersionBumped.ps1`.
- **Stable GitHub Releases use the changelog section.** The build job extracts the version's section into `release-notes.md` and uploads it with the package artefact; the release job, for a stable version, adds `--notes-file release-notes.md --notes-start-tag v<previous stable>` beside `--generate-notes`, where the previous stable tag comes from `gh release list --exclude-pre-releases`. Prereleases keep `--generate-notes` alone.

## Risks / Trade-offs

- [The changelog outgrows nuget.org's 35,000 characters] → The changelog check fails above that size; the oldest sections then move to `docs\CHANGELOG-earlier.md`, which is not packed, and a user that far behind sees the sections kept plus the Release page button.
- [Entries written for contributors creep in] → `CONTRIBUTING.md` gives the rule (one line a user would understand, Internal for the rest), and review keeps it; the check can only see that an entry exists.
- [A version published before this change has no notes] → `ReleaseNotes.TryParse` on its link-only release notes answers false, and the dialogue says the notes could not be read; from the first stable release with a changelog on, every newer package carries every earlier section.
- [A modal dialogue on the first start after an update surprises the user] → It is shown only once per version, only after an update the user chose (or ran by hand), before any key is read, and closes with Enter or Esc.
- [Notes text from nuget.org reaching the terminal] → Control characters are dropped at parse time, the text is never used as a URL, a path or a command, and `NothingLearned` covers XML that cannot be read; `DiagnosticsPrivacyShould` gains a Northwind changelog fixture so no note text reaches the log.
- [`gh release create` combining `--notes-file` with `--generate-notes`] → To be confirmed against `gh release create --help` when implementing; if the two do not combine, the release job generates the notes with `gh api repos/{owner}/{repo}/releases/generate-notes` and appends them to the file.

## Migration Plan

- `CHANGELOG.md` starts with an Unreleased section holding this change's own entry, and a section for 0.16.1 (the latest stable on nuget.org) saying release notes start with the next release; earlier releases keep their GitHub notes.
- Old `update-check.json` files read as having no notes; the next due check that finds a newer release fetches them. No migration of `config.json`.
- The first start of the version that ships this change finds no `last-run.json`, records its version, and shows nothing; the dialogue appears from the next update on.
- Rollback: an older Vantage ignores the `notes` field and `last-run.json`.

## Open Questions

- Whether to add a dialogue on start when a release is first found (once per version, Later focused), on top of the amber notice and the status line. It would reuse `WhatsNewDialog` and the announcement; deferred until the quieter notice has been tried.
- Whether to change the Windows Terminal tab title to `Vantage (update available)` while an update is offered, so it shows when another tab is in front. It would go through `Wording.TabTitle` and `TabEscapes`; deferred for the same reason.
- Whether Enter on an entry in the dialogue opens its pull request in the browser, the URL built from the parsed number alone (`https://github.com/Source191/vantage/pull/171`), as Release page builds its URL from the version. It would make the pull request numbers links without relying on the terminal to draw hyperlinks; it adds a selectable list and one effect, so it can follow once the dialogue exists.
