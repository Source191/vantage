## Goals / Non-Goals

**Goals:**
- Every ordering and counting rule is a pure `Application` type with its own facts; `TableBody` and `ConsoleScreen` only call them.
- A child that never answers costs one banner and one minute, never a second child or a spinner for ever.
- No reducer, `ViewInput` or fake changes shape: `RowsLoaded` carries no number and `FakeProcessRunner` needs no edit (PR #179's `OnRun` hook is enough for a test that wants a run to take time).

**Non-Goals:**
- Making `TableBody` testable: PR #177 left it as the Tui's untested binder, and this change keeps it so.
- A limit chosen per caller, a retry, or any change to how often the tabs refresh.
- Changing the refresh timing or the heartbeat PR #179 added; the reservation sits beside them.

## Decisions

### Reselect keeps the list's Loaded flag
`Reselect` becomes `Selected is not null ? this : Load(Rows) with { Loaded = Loaded }`, so a filter edit before the first load reselects over the empty rows and leaves `Loaded` false; `Load` itself still sets it. Alternative: guard every caller of `Reselect` in the three reducers, which repeats the rule three times and misses the next caller.

### A bare Escape on Sessions is a no-op, and Escape clears the message
`SessionsView.cs:32` takes `when state.Filter.Text.Length > 0`, so Escape with no filter falls to `_ => Unchanged(state)` (`TabKeys.TryFor` does not claim Escape, checked). All three Escape arms gain `with { Message = StatusMessage.None }`, which the rule in `.claude\rules\console-screen.md` ("the reducers clear a message when the selection moves or the filter changes") already asks for. Alternative: make Escape on Sessions clear the message too when no filter is set, as a "dismiss" key; rejected, the close mark and the ten-second timer already dismiss, and the other two tabs use that Escape to leave.

### Each load carries a ticket from an Application LoadSequence
New `Application\LoadSequence`: `int Begin()` hands out the next number, `bool Accept(int ticket)` answers true and remembers the ticket when it is above the last accepted, false otherwise. `TableBody` holds one per tab, calls `Begin()` inside `TriggerLoad` on the UI thread before `Task.Run`, and in the `app.Invoke` continuation returns before `Apply(input)` when `Accept` is false, so a stale result reaches neither `definition.OnInput` (where `StateTransitionNotifier` and `SessionActivity` observe) nor `Reduce`, success and `LoadFailed` alike. Alternative: a sequence number on `RowsLoaded` and `WorktreeRowsLoaded` checked in the reducers; rejected because it spreads one rule over three reducers and their states and still needs the Tui to stamp it. Alternative: single-flight for every load; rejected because the reload after an action must never be skipped, so overlap stays possible by design.

### The sessions listing is reserved like the worktrees scan
`ConsoleScreen` takes a second `RunningLoads listings`; a `ListSessions()` beside `ScanWorktrees()` reserves it and the timer and start-up call that, while `TableBody.RunInBackground`'s `TriggerLoad()` keeps calling the tab directly, counted by `Track` but never refused. `ConsoleComposition.Screen` builds `RunningLoads listings` beside `scans` and hands the screen `listings.Track<ViewInput>(loads.LoadSessionsAsync)` and `listings`, as it already does for the scan. How this nests with PR #179's timing: `Track` is the outer layer and counts the whole load, listing and enrichment together, which is what must not overlap; `RefreshCounts.TimeAsync` stays inside `LoadSessionsAsync` and times each part on its own, so a timed-out listing passes through it uncounted and the refresh counts keep describing the runs that finished. Why both this and the ticket: the ticket keeps the rows right whatever overlaps; the reservation bounds the children, because a listing slower than five seconds would otherwise be joined by another every tick (at the 60-second limit, twelve 189 MB children before the first is ended), and the timers tick under a dialog too (`.claude\rules\terminal-gui.md`, observed 1 November 2026), so a long dialog over a slow listing would stack them the same way. Alternative: rely on the ticket alone; rejected for that memory reason, which the review's C-01 is really about.

### The runner limits every captured run and kills on any cancellation
`ProcessRunner` takes `TimeSpan limit` in its constructor (`SharedParts.ForCurrentUser` passes `ProcessRunner.DefaultLimit`, 60 seconds, at `SharedParts.cs:45`; a `claude agents` listing takes about two, the slowest `gh` or `az` call a few). `RunAsync` links the caller's token with a `CancellationTokenSource(limit)` and waits on the linked token; in `catch (OperationCanceledException)` it calls `process.Kill(entireProcessTree: true)` inside a `try` that swallows `InvalidOperationException` (already exited), then rethrows when the caller's token is cancelled and otherwise throws `Ports\ProcessTimedOutException(fileName, limit)`. The two `ReadToEndAsync` calls take no token (today they take the caller's): the kill closes the pipes, so they complete, and they are awaited after the kill so nothing is left pending and their own cancellation can never pre-empt the exception below. The three callers whose tokens fire all gain from the kill: the version check's `claude --version` is ended at five seconds instead of running on behind the console, a tab disposed at quit ends the git its detail pane was still reading, and Ctrl+C during a `vantage here` start ends the git or `claude --bg` it was waiting on; the attach that follows is interactive and keeps no limit. `RunInteractiveAsync` is unchanged: a hand-off lasts as long as the user wants. Alternative: an `init` property on `ProcessRequest` with a default, so a caller could choose; rejected as YAGNI, no caller has a reason to differ today, and a Ports default would be one more thing every fake must honour.

### The timeout is its own exception, recorded as its own event
`ProcessTimedOutException` is sealed, in its own file beside `IProcessRunner` as `GitException` sits beside `IGit` and as PR #178's `ProgramNotStartedException` does, derives from `Exception` (not `OperationCanceledException`: a limit is Vantage giving up, not the caller), and carries the limit and the program's bare file name, which the adapter takes with `Path.GetFileName` before constructing it, so no folder reaches a message and Ports touches no `System.IO`. Its message, "claude.exe did not finish within 60 seconds and was ended", is what `Attempt.RunAsync` (`TableBody.cs:155`) puts after "listing failed:" on the Sessions tab, which the wording rule allows (an exception's message only to report what failed, in a load failure). `RecordedProcessRunner.Started` (`RecordedProcessRunner.cs:39-50`) catches it before its `Exception` filter (`:45`) and records a new `ProcessTimedOut(ChildCommand Command, TimeSpan Limit)` event (both member types are on `DiagnosticEventsShould.AllowedTypes`, `DiagnosticEventsShould.cs:16`) instead of `ProcessFailedToStart`, and no count is added, since there is no exit code; `DiagnosticLine.Body` gains the arm `timed out claude agents after 60000 ms` beside `ProcessSlow` (`DiagnosticLine.cs:53`), above the discard arm that throws for an event without a line (`:59`); `ClaudeCli.VersionAsync` adds the type to its `when` filter (`ClaudeCli.cs:30`). A timed-out listing therefore leaves two lines, `timed out claude agents` from the runner and `failed Load SessionsViewState: ProcessTimedOutException` from `Attempt`, and no refresh count; that is one event per layer that saw it, as a failed start leaves today. Alternative: a typed `LoadFailed` reason worded by `Wording`; bigger, and the owner may prefer it later, so this is the decision most open to overturning.

### Two TableBody edits with no test seam
C-03: `running = false` (now the count), then `StatusMessage settled = settle();`, then `State = definition.WithMessage(State, settled)`, so a `Dispatch` inside the continuation re-increments the count and the rows a dialog's nested `app.Run` let in are kept. `m`, `s`, `!` and the branch question all open their dialog from `RunInBackground`'s `app.Invoke` continuation (`Tui\DialogEffects`), and `.claude\rules\terminal-gui.md` (added by PR #179, 1 November 2026) reads from the decompiled assembly, without observing it, that a dialog opened inside an `Invoke` callback holds every other thread's `app.Invoke` until it closes while the timers keep ticking. If that reading holds, the listings the timer starts under such a dialog land after it and after the assignment, their continuations queued and accepted in order by the ticket, and the reorder costs nothing; if it does not, the reorder is the fix. Either way it is right, so the decision stands, and the hand check in tasks 4.2 is where it is observed. C-06: `bool running` becomes `int inFlight`, `Running => inFlight > 0`, incremented before `Task.Run` and decremented first in the continuation. Both are rendering, verified by the headless smoke check and by hand (an `m` dialog left open over a listing; two `d` presses in a row).

## Risks / Trade-offs

- [A legitimate child takes over 60 seconds, such as `gh` on a slow network] → it is reported as a failure and the next refresh retries; the pull-request catalogue already keeps its last answer, and the limit is one constant to raise.
- [`Process.Kill(entireProcessTree: true)` throws `AggregateException` for a descendant it cannot end (review C-08)] → caught alongside `InvalidOperationException` in the kill; the exception that follows still reports the timeout.
- [The ticket drops a failure that followed a success, so the banner never shows] → intended: the newer rows are the truth, and the next load reports its own result.
- [Reserving the listing delays a timed refresh behind a slow one] → the reload after an action is never refused, and a listing over 60 seconds is ended.
- [`LatestSessions.firstListing` is released by a timed-out first listing] → already so: `TrySetResult` is in the `finally` (`LatestSessions.cs:30-34`), covered by `LatestSessionsShould.AnswerNoSessionsWhenTheFirstListingFails`; no new test.
- [A timed-out listing is not a refresh count, so a listing that always times out leaves the sessions listing count still] → intended: the counts describe runs that finished, and the `timed out` lines say what happened instead.
