# Design

## Context

See proposal.md for why. At `main` 8dbf4150 (0.20.0-preview.13; the line numbers below were re-read there) the three reducers are static classes in `src\Source191.Vantage.Core\Application\Views`: `SessionsView.Reduce` returns `ViewUpdate` (`SessionsViewState`, effects), `WorktreesView.Reduce` a `WorktreesViewUpdate` and `ConfigView.Reduce` a `ConfigViewUpdate`, each view declaring its own `Unchanged` and `Effect`. `WorktreesView.RowAction` (`WorktreesView.cs:56-70`) and `ConfigView.RowAction` (`ConfigView.cs:64-77`) read `state.Selected`, answer the view's "no row selected" message for null, and turn a `RowDecision.Act` into an effect with the message cleared or a `RowDecision.Explain` into its message; `RowDecision` (`RowDecision.cs`) is exactly those two cases. `SessionsView` has `Opening(SessionRow)`, already a `RowDecision` and shared with `ConsoleView.OpenSession` (`ConsoleView.cs:39`), and six per-key methods that each read `state.Selected` themselves. `TabKeys.TryFor(Key key, [MaybeNullWhen(false)] out ViewEffect effect)` (`TabKeys.cs:9`, the shape PR #175 gave every Try method) is the one shared key helper, called from a `_ when TabKeys.TryFor(key, out ViewEffect? tab)` arm in each view (`SessionsView.cs:53`, `WorktreesView.cs:50`, `ConfigView.cs:58`) and pinned by `TabKeysShould`. `U` raises `UpdateVantage` from the same four-arm block (`SessionsView.cs:49-52`); PR #180 changed its dialog flow (`UpdateVantage.Decide(UpdateStatus, ReleaseNotes)` and `UpdateDecision.Ask` with sections, run by `Tui\DialogEffects`) and added no reducer or view state under `Application\Views`, so the arm this change moves is as it was. The Tui's `IScreenDefinition<TState, TRow>.Reduce` (`IScreenDefinition.cs:50`) returns a `(TState State, IReadOnlyList<ViewEffect> Effects)` tuple that each definition builds from its view's record and `TableBody.Apply` (`TableBody.cs:344`) deconstructs. `IListViewState<TRow>.Shown` is read only by `TableBody.Status` (`TableBody.cs:139`) and three test facts, and equals `Message` in all three states. One top-level type per file is enforced by `OneTypePerFileShould`, which names a generic type's file without its arity.

## Goals / Non-Goals

**Goals:**
- Every reducer returns the same record and reaches a row through the same `RowAction`, so the three views read as one shape with their own keys.
- Behaviour identical to today for every input: the same effect, the same state and the same message instance for every key on every row, pinned by the reducer facts already in `SessionsViewShould`, `WorktreesViewShould` and `ConfigViewShould`.
- The Tui changes only in how it reads a reducer's answer.

**Non-Goals:**
- Holding `ListSelection<TRow>` in the states (`list-selection-in-state`), new keys, new messages, new `Wording`, or any change to `ConsoleView`, the effects or their handlers.
- A fact tying `KeyHelp` to the arms (V-06), or changing the key switches' shape (V-11).

## Decisions

**One generic record, its helpers reached through `using static`.** `public sealed record ViewUpdate<TState>(TState State, IReadOnlyList<ViewEffect> Effects)` stays in `ViewUpdate.cs` and gains `public static ViewUpdate<TState> Unchanged(TState state) => new(state, [])` and `Effect(TState state, ViewEffect effect) => new(state, [effect])`. A static member of a generic type cannot infer its type argument, so each reducer imports its closed type once, `using static Source191.Vantage.Application.Views.ViewUpdate<Source191.Vantage.Application.Views.SessionsViewState>;` (C# accepts a constructed generic in `using static`; only an unbound one is CS7002), and its arms keep reading `Unchanged(...)` and `Effect(...)`. Alternatives: spelling `ViewUpdate<SessionsViewState>.Unchanged(...)` at every arm, which lengthens arms already near the line limit; a non-generic static class with generic methods, which would be a second type whose natural name the record already has; keeping a one-line `Unchanged`/`Effect` pair per view, which keeps the six helpers the review counted.

**`IScreenDefinition.Reduce` returns the record.** The tuple existed only because the three records differed; the definitions become `public ViewUpdate<SessionsViewState> Reduce(SessionsViewState state, ViewInput input) => SessionsView.Reduce(state, input);` and `TableBody.Apply` reads `update.State` and `update.Effects`. Alternative: keep the tuple and the adaptors; rejected as the adaptor is now a repetition with no reason.

**`RowAction` on Sessions, the same four lines as the other two.** `private static ViewUpdate<SessionsViewState> RowAction(SessionsViewState state, Func<SessionRow, RowDecision> decide)` answers `StatusMessage.NoSessionSelected` for no row and maps `Act` and `Explain` as `WorktreesView.RowAction` does, with the discard arm throwing `UnreachableException`. The arms: Enter `RowAction(state, Opening)`; `x` `RowAction(state, row => OnJob(row, job => new StopSession(job)))`, where `OnJob(SessionRow, Func<BackgroundSession, ViewEffect>)` answers `Explain(RunsInOwnTerminal(row.Session.Name, row.HasTranscript))` for an interactive row, which is what `SessionAction` gives today; `d` `RowAction(state, Delete)`, where `Delete(row)` answers `Act(CloseEmptyTerminals([terminal]))` for an interactive row with no transcript and otherwise `OnJob(row, job => new DeleteSession(job))`, so the two `d` arms (`SessionsView.cs:37-40`) become one and `C` no longer sits between them; `c`, `f`, `s` build `RowDecision.Act` directly from `row.Session.WorkingDirectory` and `row.Repository`, so `FolderAction` goes; `p`, `m`, `b`, `r` become `PullRequestOf(row)`, `Memory(row)`, `Adopt(row)`, `Rename(row)` returning `RowDecision`, keeping today's arm order and messages. `Rename`'s first arm answers `RunsInOwnTerminal` itself, so the lambda at `SessionsView.cs:170` that could never run goes. `C`, `R`, `n`, `/`, Escape, Up and Down are not row keys and keep their arms. Alternative: a `RowAction` that takes `Func<SessionRow, BackgroundSession, RowDecision>` for job keys; rejected because three of the ten row keys act on any session.

**Rewritten arms follow the two-case rule.** `PullRequestOf` names `PullRequestLookup.Found` and `Missing`, `Adopt` names `BackgroundSession` and `InteractiveSession`, and each discard arm throws `UnreachableException`, where today's `_ => Unchanged(state)` (`SessionsView.cs:139, 208`) guesses. Both hierarchies are closed with exactly two cases, so no input reaches the throw and no fact changes; `convention-nets` (V-03) then has only `WorktreesView.PullRequestOf:104` and the non-view sites left. Alternative: carry the guesses over and leave all of V-03 to `convention-nets`; rejected because the methods are rewritten here anyway and a second edit would follow.

**`SharedKeys` beside `TabKeys`, the tab keys staying where they are.** `Application\Views\SharedKeys.cs`, `public static bool TryFor(Key key, [MaybeNullWhen(false)] out ViewEffect effect)` answering `Quit`, `ShowHelp`, `UpdateVantage` and `ShowProblemReport` for `q`, `?`, `U`, `!`, the same shape as `TabKeys.TryFor` (`TabKeys.cs:9`): `[MaybeNullWhen(false)]` on a non-nullable `out`, which PR #175 (standardise-maybe-null-when) made the one shape for every Try method. Each view replaces its four arms with `_ when SharedKeys.TryFor(key, out ViewEffect? shared) => Effect(state, shared)` before the `TabKeys` arm, the call written as the `TabKeys` arm already is; no row key shares a character with them, so the move changes no match. Alternative: fold the tab keys into `SharedKeys` for one arm; rejected because `.claude\rules\console-screen.md` names `TabKeys.TryFor`, the tab keys are `ISwitchesTab` effects routed differently by `TableBody`, and `TabKeysShould` would move for nothing.

**No `Reduce` guards its state.** `ConfigView.Reduce`'s `ArgumentNullException.ThrowIfNull(state)` (`ConfigView.cs:12`) goes, matching the other two: a reducer is a static pure function whose first use of a null `state` throws at once anyway, and CA1062 is not enabled. The `convention-nets` change decides the guard rule for the codebase (A-08); if it lands first and says guard everywhere, the task flips to adding the guard to `SessionsView` and `WorktreesView`. The guards in `ConsoleView.Apply`, `ConsoleView.OpenSession` and `SessionsView.Opening` are outside this decision and stay. Alternative: guard all three now; rejected as pre-empting that decision.

**`Shown` goes; `Message` is the interface member.** `IListViewState<TRow>` gains `StatusMessage Message { get; }`, which the three records' positional `Message` already implements, and loses `Shown`; `TableBody.Status => State.Message`. The three facts that assert `.Shown` assert `.Message`, and `ConfigViewShould.cs:196` (`advised.Shown.ShouldBe(advised.Message)`) goes as a tautology. `TableTitle.Shown` (a count) and `ITabBody.Shown(bool)` are different things and stay.

**Pin before moving.** `SessionsViewShould` states no fact for `x` or `r` on an interactive row, nor for Enter, `x`, `d`, `r` and `b` on an empty table; those pass today and are added green, in their own commit, before `SessionAction` is taken apart.

## Risks / Trade-offs

- [A `using static` of a constructed generic is unusual in this codebase] → one line per reducer, checked by the build; if the owner dislikes it, the fallback is the spelled-out `ViewUpdate<SessionsViewState>.Unchanged(...)`, a mechanical edit.
- [Merging the two `d` arms could change what `d` does on a row that matches neither guard] → `Delete(row)` is the same two tests in the same order (`InteractiveSession` with `HasTranscript: false` first, then the job rule); `OfferToCloseATerminalSessionThatHasNoMessagesAndCloseItOnX`, `KeepRefusingToDeleteATerminalSessionThatHasAConversation` and `EmitTheEffectForTheKey('d')` pin the three outcomes.
- [`Explain(StatusMessage.None)` through `RowAction` sets the message to `None`, where a `_ => Unchanged(state)` kept it] → the only such arms are the two unreachable discards, which now throw rather than answer.
- [Two open changes edit these files (`list-selection-in-state`, `convention-nets`)] → whichever lands second rebases; the guard task says which way it flips. (`standardise-maybe-null-when` landed in PR #175, so `SharedKeys`' attribute shape is settled above.)
- [The Tui adaptors have no unit test] → the build checks the signature, the solution's tests run `TableBody` through `ConsoleViewShould`'s collaborators where they do, and CI's smoke check presses every key.

## Migration Plan

Nothing to migrate: no state file, key, setting or command line changes. Rollback is reverting the pull request.
