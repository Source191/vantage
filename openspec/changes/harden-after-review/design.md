# Design

## Context

See proposal.md for the findings. The facts the design rests on, each read in the code at main bc0e8125 or reproduced in scratch repositories during the review of 1 November 2026:

- `WorktreeInventory.RegisteredRowsAsync` sets `folderExists = !entry.IsPrunable && DirectoryExists(path)`, so a prunable entry is a row with `FolderExists: false`, health broken with `HealthReason.FolderGone`, and `LeftoverFileCount: 0`. `RemovalDecision.For` then answers `DeleteFolder(prune: true)`, and `WorktreeRemover.DeleteFolderAsync` calls `DeleteTree(row.Path)`. `RemoveWorktreeHandler` reads only the created-worktree record and the merge state; it never looks at the disc. `FolderDeletion.DeleteTree` refuses only relative paths, drive roots and share roots.
- Git lists a worktree as `prunable gitdir file points to non-existent location` when the `<worktree>\.git` file its registration's `gitdir` names is missing, whether or not the folder exists. A `.git\worktrees\<name>\gitdir` from a copied `.git` folder can name any path.
- `WorktreeInspector.HealthAsync`, used by `DeleteSessionHandler.RowAsync`, answers broken and folder gone both for a prunable entry and for no matching entry; git lists the real path behind a junction, so a worktree root spelled through a junction matches no entry.
- `WorktreeInventory.BrokenWorktree` reads the owner from the `.git\worktrees\` segment of the `gitdir`, resolves a relative `gitdir` with `Path.GetFullPath(gitdir)` (against Vantage's current folder), and answers elsewhere only when it named an owner and that owner has a `.git` folder; a bare repository's `X.git\worktrees\` matches the segment inside `X.git` and names a missing `X`.
- `TerminalTab.Walk` follows `IProcessRegistry.ParentOf` for up to eight steps until a parent is named WindowsTerminal; it never compares start times. `ProcessTree` already keeps a child only when it started after its nearest measured ancestor.
- `PathFolders.ForCurrentUser` and `AzureCliExecutable.Locate` split the PATH and keep every non-empty entry; `Path.Combine(".", "git.exe")` is `.\git.exe`, which `File.Exists` checks against the current folder. `EditorLocator.CodeBesideTheShim` searches the same folders and calls `Path.GetFullPath` on what it finds.
- `WindowsTerminalArguments.ForTab` puts the bare name `pwsh.exe` after the tab options; Windows Terminal starts it with `CreateProcessW` and no application name. `Program.cs` already locates `pwsh` for `Desktop`.
- `claude --help` (CLI 2.1.316) lists `-r, --resume [value]`: the value is optional, and the CLI's parser does not take a value that starts with `-` for an optional option. `SessionId` accepts any text that is not blank; `ClaudeTranscripts` joins it into a file name. No test fixture uses a session id outside letters, digits and hyphens.
- `ProgramLabel.PackageAfterRunner` takes the first token after `npx` or `uvx` that does not start with `-`, so an option's value becomes the label.
- `FolderPath.TryParse` answers `From(text)` whenever `Path.IsPathFullyQualified` holds, which it does for text holding a NUL, and `Path.GetFullPath` then throws `ArgumentException`; `SettingsFile.From` and `BrokenWorktree` reach it with text from outside.
- `publish.yml` downloads the release's nupkg and pushes it; `release.yml`'s comment and `CONTRIBUTING.md` say the attestation is checked before a publish, but nothing checks it. Immutable releases are off for the repository (checked with `gh api`, 1 November 2026). `release.yml` is one job with `contents: write`, `id-token: write` and `attestations: write` that also builds and tests. `claude-contract.yml` grants `issues: write` to the job that installs Claude Code and runs the tests.

## Goals / Non-Goals

**Goals:**
- No folder that holds files is ever deleted without the typed force confirmation, and none outside the roots is deleted at all.
- A `.git` file that points at an existing folder always means a live checkout.
- Nothing Vantage starts, directly or through a tab, is resolved through a relative folder.
- What `publish.yml` pushes is provably what `release.yml` built.

**Non-Goals:**
- Changing how a registered, healthy worktree is removed: that stays `git worktree remove`, whose own check of the `.git` back-pointer refuses a planted path.
- Resolving junctions or 8.3 names in configured roots.
- Passing `--resume=<id>` to the CLI as well: the shape rule makes it unnecessary and the `=` form is not checked against the CLI.

## Decisions

- **The disc decides, at the key.** `WorktreeInventory` sets `FolderExists` from the disc alone, and a registered entry whose folder exists but is prunable gets a new `HealthReason.GitFileGone` (health broken) and its `CountLeftoverFiles`, like any other leftover; `RemovalDecision`'s existing broken-with-files refusal then applies unchanged. `RemoveWorktreeHandler` re-reads `FolderExists` and the leftover count through `IFolders` before it asks `RemovalDecision`, and passes a row carrying those facts, so a stale scan cannot delete. `WorktreeInspector.HealthAsync` answers the same three cases (listed and fine, listed and prunable, not listed) from the folder on disc: a folder that exists is never `FolderGone`, and `DeleteSessionHandler.RowAsync` counts its leftover files for any health other than ok. Alternative: refuse every prunable row outright. Rejected: the empty folder a half-finished remove leaves (measured on 30 October) would then need a force for nothing.
- **The roots are the last guard.** `WorktreeRemover.DeleteFolderAsync` refuses a path that is not `IsUnder` a repository root or the worktree root, answering `RemoveWorktreeOutcome.Refused(new RemovalReason.OutsideTheRoots())`; the roots come from `CurrentSettings` through the handler, so a save applies at once. The check sits in the remover rather than in `RemovalDecision` because it must hold for every caller, the session delete included, and in front of the `IFolders.DeleteTree` call rather than inside `FolderDeletion`, which knows nothing of settings. `OutsideTheRoots` has `CanBeForced: false`. Alternative: put the root check in `FolderDeletion`. Rejected: an adapter would need the settings, and the refusal would come back as an exception instead of an outcome with words.
- **A live target is elsewhere.** `BrokenWorktree` resolves a relative `gitdir` with `Path.GetFullPath(gitdir, folderOfTheDotGitFile)` and answers `GitPointer.RegisteredElsewhere` whenever the target exists. The owner is read structurally: a registration sits at `<git directory>\worktrees\<name>`, so the git directory is two levels up; when that folder is named `.git` the repository is its parent, otherwise it is the git directory itself (a bare repository); a target with no `worktrees` parent is a git directory of its own (`--separate-git-dir`) and is the owner. The `.git\worktrees\` string search goes. Alternative: a new health kind for owner-less checkouts. Rejected: elsewhere already has the refusal, the colour, the keys and the words, and "its repository is not under the roots" is true of all three layouts.
- **The tab walk checks ages.** `TerminalTab.Walk` reads `StartTimeOf` for the child and each parent and stops, answering no tab, at a parent that started after its child or whose start cannot be read. `TabRegistration.OwningTerminal`, which uses the same walk, gets the same protection. Alternative: walk with Toolhelp snapshots as `ProcessTree` does. Rejected: the registry port already answers both facts.
- **PATH entries must be full paths.** `PathFolders.ForCurrentUser` keeps only entries for which `Path.IsPathFullyQualified` holds, and `AzureCliExecutable.Locate` takes those folders instead of the raw variable, so all three searches (programs, az, the VS Code shim) share one filter. Alternative: set `NoDefaultCurrentDirectoryInExePath`. Rejected on 29 October for the reason recorded then: tabs inherit it.
- **The tab's PowerShell is a located path.** `WindowsTerminal` takes the `ProgramLocation` of pwsh beside that of wt, `WindowsTerminalArguments.ForTab` takes its path in place of the literal `pwsh.exe`, and a missing pwsh fails the key with the existing pwsh.exe sentence, as wt.exe does. This revisits a non-goal of 29 October: the claim then was that Windows Terminal resolves the name from its own folder, which holds only while a Windows Terminal is already running; a cold start can resolve it from the caller's.
- **One shape for a session id.** `SessionId`'s private constructor and `TryParse` both require ASCII letters, digits and hyphens with a letter or digit first, so `From` throws and `TryParse` answers false for anything else, keeping the three doors to one spelling as `TextValuesShould` expects. The CLI's ids are lowercase UUIDs; the rule is wider than a UUID so a future format with the same characters still works, and narrow enough that no id can start an option or hold a separator. A `ClaudeContract` fact asserts that a real listing's ids match it.
- **Option values are not labels.** `ProgramLabel` skips the value after the options of npx and uvx that take one (`--from`, `--with`, `--registry`, `--package`, `-p`, `--python`, `--index-url` and their `=` forms), and no candidate holding `:` is a label, so a URL falls back to the runner's name.
- **NUL is not a path.** `FolderPath.TryParse` answers false for text holding `\0`, and `BrokenWorktree` reads a `gitdir` line through `TryParse`, so a bad `.git` file reads as no target.
- **CI.** `publish.yml` runs `gh attestation verify <nupkg> --repo Source191/vantage --signer-workflow Source191/vantage/.github/workflows/release.yml --source-ref refs/heads/main` after the download and fails on anything but success; immutable releases are turned on with `gh api -X PUT repos/Source191/vantage/immutable-releases` after the merge. `release.yml` becomes a `build` job (`contents: read`: the version check, the build-test-pack action, an artefact upload) and a `release` job (`needs: build`, the three write permissions: download, attest, `gh release create`) that checks nothing out. `claude-contract.yml`'s contract job drops to `contents: read` and a `report` job (`needs: contract`, `if: failure()`, `issues: write`) raises or comments on the issue from the results artefact.

## Risks / Trade-offs

- [A user whose worktree root is a junction finds a prunable leftover listed by git under the real path refused as outside the roots] → the status line names the folder; deleting it by hand or setting the root to the real path both work, and a healthy worktree still goes through git.
- [The "folder in use" scenario now relies on git leaving the folder empty] → that is what was measured on 30 October; if files remain, remove explains and force-remove finishes the job.
- [A future CLI session id with other characters would hide its rows] → the contract fact fails first, nightly, against the latest CLI.
- [Splitting `release.yml` adds an artefact hop] → the package's path is the artefact's only file, and the attestation is made on the downloaded bytes, which are the ones published.
- [Immutable releases stop a release from being fixed in place] → a fix is a new version, which the tool cache already requires.

## Migration Plan

- Version: a minor step in the implementing pull request (`0.20.0-preview.1` unless main has moved); no state file changes.
- After the merge: `gh api -X PUT repos/Source191/vantage/immutable-releases`, then confirm with `gh api repos/Source191/vantage/immutable-releases` that it answers enabled, and that the next release's `immutable` is true.
- Rollback is the previous release; nothing persists.
