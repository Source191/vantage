# Design

## Context

See proposal.md, Why. Today `Program.cs` builds a `FileLogger` (`Adapters\Diagnostics`) only when `VANTAGE_LOG` is set, hands the same `ILogger` to `Terminal.Gui.App.Logging.Logger` and to `ScreenLoop`, and `Application\HandoffLog` holds Vantage's four `LoggerMessage` lines; `HandingOver` is given `effect.ToString()`, so the record's members (job ids, names, folders) reach the file. Failures become footer text in two `catch (Exception)` blocks in `Tui\TableScreen` (`TriggerLoad` turns one into `LoadFailed(message)`, `RunInBackground` into `Footer.Failed(message)`), and `ScreenLoop.CheckForUpdatesAsync` logs the update check's. Every captured or interactive child goes through `IProcessRunner` (`GitCli`, `ClaudeCli`, the pull-request adapters, `WindowsTerminal`, `Desktop.OpenAsync`, `EditorLocator`); only `Desktop.StartAsync` (editors) starts a process directly. `EffectDispatcher` is the one route from a background effect to its handler. `CommandLine.InvokeAsync` runs System.CommandLine, whose default exception handler prints an exception escaping an action and returns 1. Terminal.Gui 2.5.0's messages are interpolated strings, some quoting raw input it failed to parse ("InputProcessorImpl ignored unrecognized response '…'"). The sessions view refreshes every 5 seconds, each refresh running `claude agents --json` and, every 30 seconds per row, a few git commands.

## Goals / Non-Goals

**Goals:**
- Make it impossible, not merely unlikely, for a diagnostic record to carry user data: the types themselves can only hold values Vantage defines, and a test fails when one could hold more.
- Keep enough to diagnose: what the user did (as kinds), what failed and where in Vantage's code, which child programs misbehaved, and the environment.
- Leave the screens' behaviour unchanged: footers show what they show today.

**Non-Goals:**
- Any route off the machine (that is `report-a-problem`).
- A general logging framework, levels or categories; the event set is closed and small.
- Recording keys, mouse events or Terminal.Gui's text.

## Decisions

**A closed set of event records with typed fields, never a message string.** `Application\Diagnostics\DiagnosticEvent` is an abstract record with one sealed case per thing Vantage records: `Started`, `ViewShown`, `DialogShown`, `EffectRan`, `HandingOver`, `ChildReturned`, `ProcessSlow`, `ProcessFailedToStart`, `Failed`, `TerminalGuiReported`. Their members may only be `int`, `long`, `bool`, `TimeSpan`, `System.Version`, `ToolVersion`, an enum, `CodeName` or `ExceptionSummary`. `CodeName` is a value whose only factories take a `Type` (`CodeName.For(effect.GetType())` gives `AttachToSession`; a nested outcome gives `StartSessionOutcome.Started`) or a `MethodBase`, so it can only ever hold an identifier compiled into an assembly. `ExceptionSummary.From(Exception)` keeps each exception's type (`CodeName`) and its frames (declaring type, method, the source file's name without its folder, the line), at most 20 frames per exception and three inner exceptions deep, and never reads `Message`, `Data` or `Source`. `Architecture\DiagnosticEventsShould` reflects over every concrete `DiagnosticEvent`: a member of any other type, a public `string` anywhere in the namespace's public surface, or a `CodeName` or `ExceptionSummary` factory taking a `string` fails it. Alternatives: an `ILogger` with message templates and a redaction pass (rejected: redaction is a blacklist, and one new template with a `{Name}` defeats it); an allow-list of safe Terminal.Gui messages (rejected: their wording changes with the package).

**Rendering is one pure function and the only text.** `DiagnosticLine.Render(TimedEvent)` turns an event into one line: `2026-10-29T14:03:12.345Z effect DeleteWorktree -> RemoveWorktreeOutcome.Removed 412 ms`. These lines are a maintainer's format, not interface text, so they live in `Application\Diagnostics` beside the events rather than in `Wording`; CLAUDE.md's rule on user-facing text gains this one exception. The file sink, the crash file and `report-a-problem` all use the same rendering, which is what the spec's "exactly the text the in-memory log holds" means.

**`DiagnosticLog` is the in-memory log and the only recorder.** `Application\Diagnostics\DiagnosticLog(TimeProvider clock, IReadOnlyList<IDiagnosticSink> sinks)` implements a small `IDiagnostics` (`Record(DiagnosticEvent)`, `Snapshot()`), keeps the latest 500 `TimedEvent`s in a ring guarded by a `Lock` (events arrive from pool threads), and writes each rendered line to every sink. `Ports\IDiagnosticSink` (`Write(string line)`) is implemented by `Adapters\Diagnostics\DiagnosticFile` for `VANTAGE_LOG`, which appends and swallows `IOException` (a log must never take Vantage down). `RecordingDiagnostics` in TestDoubles replaces `RecordingLogger`. `Microsoft.Extensions.Logging.Abstractions` leaves Core (nothing there uses `ILogger` any more) and stays in Infrastructure for the Terminal.Gui bridge.

**Child programs are counted, not logged.** `Application\Diagnostics\RecordedProcessRunner` decorates `IProcessRunner`. It maps `Path.GetFileNameWithoutExtension(request.FileName)` to the closed enum `ChildProgram` (Git, Claude, Gh, Az, Pwsh, Wt, Vswhere, Dotnet, Other) and takes up to two leading arguments while each is a word on that program's fixed list (`ChildCommandWords`: git's `worktree`, `list`, `add`, `remove`, `prune`, `status`, `rev-list`, `log`, `branch`, `symbolic-ref`, `merge-base`, `rev-parse`, `remote`, `get-url`, `ls-files`; claude's `agents`, `attach`, `stop`, `rm`, `--version`, `--bg`, `--resume`; and so on), stopping at the first that is not. A user value that happens to equal a listed word (a branch called `list`) reveals only that listed word. Each run adds to `ProcessCounts` (program, subcommand, exit code → runs, longest duration); a run over 2 seconds records `ProcessSlow`, one that throws records `ProcessFailedToStart` with a summary and rethrows. `ProcessCounts` (thread-safe, like the log) renders through `DiagnosticLine` too; it is part of the crash file, written to the sinks on a normal exit, and read by `report-a-problem`. Its keys are `ChildProgram`, a subcommand made only of listed words, and an `int`, so `DiagnosticEventsShould` covers it as well. Program.cs wraps the real `ProcessRunner` once, so every adapter is covered. Alternative: a line per run (rejected: the 5-second refresh would fill 500 events in minutes); folding consecutive repeats (rejected: refreshes interleave claude and git, so nothing is consecutive).

**Failures are recorded where they are caught, once.** The outermost catch records, nothing below it does, so a failing effect gives one line. `Application\Diagnostics\Attempt.RunAsync<T>(IDiagnostics, FailureSite, CodeName, Func<CancellationToken, Task<T>>)` returns the result or the exception's message for the footer, recording `Failed(site, what, summary)` on the way; `TableScreen.TriggerLoad` and `RunInBackground` call it instead of their own `try`, with `FailureSite.Load` and the view, or `FailureSite.Effect` and the working effect's `CodeName`. `ScreenLoop.CheckForUpdatesAsync` records `FailureSite.UpdateCheck`. `EffectDispatcher` records `EffectRan` (kind, outcome kind, duration) on success only, so a failure is never counted twice.

**Terminal.Gui is bridged without its words.** `Adapters\Diagnostics\TerminalGuiBridge : ILogger` is assigned to `Terminal.Gui.App.Logging.Logger`, always, not only under `VANTAGE_LOG`. `IsEnabled` answers true for Warning and above; `Log` ignores `state` and the formatter and records `TerminalGuiReported(level, ExceptionSummary?)`. Trace and Debug are dropped: without their text they say nothing. The hand-off detail Terminal.Gui used to give is still covered by the HeadlessTerminal `check`.

**Views, dialogs and hand-offs.** `ScreenLoop` records `ViewShown(ViewKind)` (a new two-member enum, Sessions and Worktrees) for the first screen and on each switch, not on the re-runs after a hand-off, and `HandingOver(CodeName)` and `ChildReturned` around `effects.RunAsync`, replacing `HandoffLog`. `Tui\DialogTabTitle.Apply` already receives every dialog's `DialogName`, so it records `DialogShown(DialogName)` when the dialog becomes modal.

**Start facts.** `Program.cs` gathers the Vantage `ToolVersion`, the Claude Code version (parsed to `System.Version` by `ClaudeVersion.TryParse`, null when unreadable), `Environment.OSVersion.Version`, `Environment.Version` and the console's columns and rows, and records `Started` once the console action begins. `here`, `setup-terminal` and `claim-tab` record nothing beyond `Started` and failures.

**Crash file.** `Application\Diagnostics\CrashRecorder(IDiagnostics, ProcessCounts, ICrashFile)` has `Guard(Func<…, Task<int>>)`, which wraps the console and `here` actions in `CommandActions`: an exception records `Failed(FailureSite.Crash, …)`, writes the rendered snapshot, the counts and the crash summary through `Ports\ICrashFile`, and rethrows so System.CommandLine reports it as today; a normal return writes the rendered counts to the sinks (the spec's "when Vantage exits") and leaves the crash file alone. `Program.cs` also subscribes `AppDomain.CurrentDomain.UnhandledException` (a thread the guard cannot see) to the same recorder and `TaskScheduler.UnobservedTaskException` to `Failed(FailureSite.BackgroundTask, …)` without crashing. `Adapters\Diagnostics\CrashFile` writes `%LOCALAPPDATA%\Vantage\last-crash.log` (UTF-8, no BOM, replaced whole), and a failure to write is swallowed so the original exception surfaces. Alternative: `EnableDefaultExceptionHandler = false` and a `try` in Program.cs (rejected: Program.cs is untested wiring, and the parse-error behaviour depends on the default handler).

**The privacy fact.** `Application\DiagnosticsPrivacyShould` composes the real reducers, dispatcher, handlers and `DiagnosticLog` over the TestDoubles fakes seeded with Northwind fixtures and drives the flows the spec names: a sessions load, an attach hand-off, a wizard start with a name and prompt, a worktree remove whose fake git fails with a message naming folders, a failing load and a crash through `CrashRecorder`. It then asserts that no fixture value (every repository, branch, worktree and session name, job and session id, prompt, folder, PR number and title, and `C:\Users\me`) appears in any rendered line, the counts or the crash text. The fixture list is built from the seeds themselves, so a new seed is checked without editing the assertion.

## Risks / Trade-offs

- [Losing Terminal.Gui's text makes a terminal-mode bug harder to read from a user's log] → the HeadlessTerminal `check` and `drive` reproduce hand-off problems locally, where a developer can read Terminal.Gui's output in the capture; the user's rule outranks the convenience.
- [Frames without line numbers when the PDBs are not shipped] → method names still locate the failure; whether the packed tool carries portable PDBs is checked in task 6 and recorded.
- [A new event case with a `string` member slips in] → `DiagnosticEventsShould` fails the build's tests; the reflection is over the namespace, not a hand-kept list.
- [A future adapter starts a process without `IProcessRunner`] → it is simply not counted, never leaked; `LayeringShould` already confines `System.Diagnostics.Process` to Adapters.
- [The crash writer itself throws while the process is dying] → every write is wrapped and swallowed; the original exception is rethrown.
- [500 events is too few or too many] → it is one constant; the report trims to its own budget anyway.

## Migration Plan

Nothing to migrate: `VANTAGE_LOG` keeps its name and meaning, and its lines change format. Rolling back is reverting the change; `last-crash.log` is then simply ignored.
