# Design

## Context

See proposal.md. Today `Program.cs` reads `config.json` once (`JsonFileStore.ReadConfigAsync`, which answers `VantageConfig.Default` for a missing or corrupt file) and copies the values out: the roots into `RepositoryCatalogue`, `WorktreeInventory` and the header string, the default base into `DialogEffects`. `VantageConfig` is a positional record, so a property missing from the JSON deserialises as null (a list) or the first enum member, never as the record's own default. New worktrees are placed by `SiblingWorktree.For(repository, slug)` (parent folder, `<name>-<slug>`), called from `LaunchPlanBuilder.Build` and `LaunchPreview.Describe`. `RepositoryCatalogue.IsGitCheckout` accepts a `.git` folder or file, so linked worktrees under a root are offered as repositories. `WorktreeInventory.ScanAsync` walks the roots once, sorting children into repositories (`.git` folder), candidates for broken siblings (`.git` file) and empty `.worktrees` leftovers. `KeyMapping` already passes `,` through as a character key.

## Goals / Non-Goals

**Goals:** one place that holds the current settings and every consumer reading it on use; the settings dialog follows the reducer-plus-binder pattern so its rules are tested; a `config.json` from 0.4.x keeps working, and a file written by this version still reads in 0.4.x.

**Non-Goals:** watching `config.json` for hand edits while Vantage runs (a hand edit applies on the next start, as today); launching the editor (`folder-column-and-open-keys`); moving existing worktrees.

## Decisions

- **File shape.** `VantageConfig(IReadOnlyList<string>? RepositoryRoots, WorktreeBase DefaultBase, string? WorktreeRoot, EditorSetting? Editor)` stays the file record in `Ports`, with nullable members so a missing property is visible. `Settings.From(VantageConfig?, FolderPath home)` in `Domain` resolves it to a complete, immutable `Settings(IReadOnlyList<FolderPath> RepositoryRoots, FolderPath WorktreeRoot, EditorChoice Editor, WorktreeBase DefaultBase)`: no or empty roots means `<home>\source\repos`; no worktree root means `worktrees` beside the first root (the root itself when it has no parent, such as `D:\`); no or invalid editor means VS Code. `Settings.ToConfig()` writes every property, so a saved file is complete. Alternative considered: give the positional record's parameters default values. Rejected because System.Text.Json passes null for missing constructor parameters rather than using C# defaults, which is the bug the brief warns about; resolving in one tested place is clearer. System.Text.Json ignores unknown properties, so 0.4.x reads a new file and simply drops `worktreeRoot` and `editor`.
- **Editor value.** `EditorChoice` in `Domain`: an `EditorPreset` enum (`VsCode`, `Cursor`, `Rider`, `VisualStudio`, `Explorer`, `Custom`) plus, for `Custom`, an executable and an argument list. Stored as `"editor": { "preset": "VsCode" }` or `{ "preset": "Custom", "executable": "C:\\Tools\\subl.exe", "arguments": ["-n", "{folder}"] }`. Arguments are a list in the file so nothing ever re-parses a command line; the dialog shows them on one line and `CommandArguments.Split` (double quotes group, tested) turns the line into the list. How each preset reaches its real executable is `folder-column-and-open-keys`' decision; this change only stores the choice. Alternative: a free-text command line. Rejected: it invites shell interpolation of the folder path.
- **One holder, read on use.** `Application\CurrentSettings` holds the `Settings` value (a reference swapped atomically on save) and saves through `IVantageConfig`. `RepositoryCatalogue`, `WorktreeInventory` and `DialogEffects` take `CurrentSettings` instead of copied values and take a snapshot at the start of each scan, wizard or dialog; `WizardState.Open` receives the worktree root and default base from that snapshot, so the reducer stays pure. The header context becomes a function the screen calls on each redraw. Alternative: restart the screen loop after a save. Rejected: it loses the selection and filter and still needs every consumer rebuilt.
- **Placement.** `SiblingWorktree` becomes `PlannedWorktree.For(FolderPath worktreeRoot, FolderPath repository, WorktreeSlug slug)`: path `<worktreeRoot>\<repository name>-<slug>`, branch `<slug>`. `LaunchPlanBuilder.Build` and `LaunchPreview.Describe` take the worktree root. `git worktree add` creates missing leading folders, which an Infrastructure test against a real repository confirms, so no new folder-creating port is needed; if the test shows otherwise, `IFolders` gains `CreateDirectory` in the same task.
- **Picker.** `RepositoryCatalogue` keeps a child only when `.git` is a folder.
- **Inventory.** The scan adds the worktree root as a second source of candidates (`.git` file children), skipped when it equals a root, so a broken worktree under it is found; registered worktrees anywhere are already listed by git per repository. Empty `.worktrees` leftovers stay a roots-only rule, as the spec says.
- **Dialog as reducer and binder.** `SettingsState` (roots text, worktree root text, preset, custom executable, custom arguments text, base, problem, focus, `Func<string, bool>` folder check supplied at open) with `SettingsInput` mirroring control events (`RootsChanged`, `WorktreeRootChanged`, `PresetChanged`, `ExecutableChanged`, `ArgumentsChanged`, `BaseChanged`, `FieldFocused`, `Save`, `Cancel`); `SettingsView.Reduce` returns the state and an optional effect, `SaveSettings(Settings)` or `Close`. Validation lives in `Settings.TryParse(text inputs, folderExists)` returning a `SettingsProblem` fact (`NoRoots`, `RootNotFullPath(text)`, `RootMissing(path)`, `WorktreeRootNotFullPath`, `NoExecutable`, `BatchFileExecutable`, `NoFolderPlaceholder`) that `Wording` says. `SettingsDialog` binds `SettingsControls` (a multi-line `TextView` for roots, `TextField`s, an `OptionSelector` for preset and base) under the usual `binding` guard.
- **Key and save path.** `,` in both reducers raises `OpenSettings`, an `IDialogEffect`; its flow in `DialogEffects` opens the dialog with the current snapshot and, on `SaveSettings`, dispatches it to `SaveSettingsHandler` (`IEffectHandler<SaveSettings>`), which saves through `CurrentSettings` and returns a `SettingsSaved` outcome worded in `WordingOfOutcomes`. The footer then confirms, the refresh after a dispatch rescans with the new values.
- **Header.** The left column gains `Worktree root:`; the label column widens from 11 to 14 characters and the value and key-hint columns move right by three. Checked with `tools\HeadlessTerminal grid` at 120 columns.

## Risks / Trade-offs

- [Two writers of `config.json`: the dialog and a hand edit while Vantage runs] → the dialog writes the whole file from its snapshot, so a concurrent hand edit is lost; the README says to edit by hand only while Vantage is closed, or use the dialog.
- [A consumer keeps a reference to an old snapshot across a save] → snapshots are taken per operation and `Settings` is immutable; a scan already running finishes with the old roots and the next refresh uses the new ones.
- [Worktree root on another drive than the repository] → git supports it; the `.worktreeinclude` copy already writes by full path; covered by the existing worktree tests with the root moved.
- [Header width at narrow terminals] → three more columns on the left; the key hints already need about 118 columns, so the grid check uses 120.

## Migration Plan

Nothing moves on upgrade: existing sibling worktrees keep their folders and registrations and stay removable. The first save from the dialog writes the two new properties. Rolling back to 0.4.x ignores them, and worktrees created under the new root stay listed because git lists them per repository.

## Dependencies and rebasing

- Builds on `header-and-help` (which replaces the machine and Claude path lines in the header string this change turns into a function) and `remove-session-descriptions` (which removes `DescriptionText` from `LaunchRequest` and the description field from `WizardState` that this change also touches). If either is archived after this one, rebase the header and launch-request edits; no requirement text is shared.
- `folder-column-and-open-keys` reads `Settings.Editor` and the worktree root for its relative-folder rule.
- The `session-launch` requirement "Repository is chosen from configured roots" and the renamed worktree requirement are touched by no other change in this set.
