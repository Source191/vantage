# Vantage

A Terminal.Gui console for Claude Code sessions and git worktrees on Windows, packaged as the dotnet global tool `vantage`. The README is the user guide and `CONTRIBUTING.md` the contributor's guide (setting up, the OpenSpec stages, pull requests, CI and releasing); `openspec/` holds the specifications and the changes made against them.

Facts that matter only in part of the code are path-scoped rules in `.claude\rules`, loaded when a matching file is read or edited. Read the one that applies before reasoning about its area from anywhere else:

- **`console-screen.md`:** the console's layout, tab keys, refreshing and worktree scanning, detail pane and status line.
- **`terminal-gui.md`:** the verified Terminal.Gui 2.5.0 facts (focus roles, dialogs, tooltips, `Tabs`, spinners, `OpenDialog`, `ImageView`).
- **`windows.md`:** the verified Windows Terminal facts (`wt.exe` semicolons, UI Automation tabs, tab colours and titles, the fragment, updating, ShellExecute) and Windows process facts (memory, process handles, the process tree, command lines).
- **`checks.md`:** the CI and release workflows, and the hand-off, smoke and Claude Code contract checks in detail.
- **`locale.md`:** what must stay invariant, what translating Vantage or supporting another culture will need, and the known gaps for other languages and scripts (cell widths, slugs, az's code page, git's translations).

## Build, test, release

- Test loop: `dotnet build -c Debug` (warnings are errors), `dotnet test test\Source191.Vantage.Core.Tests -c Debug --no-build` for the fast in-memory suite (about two seconds, xunit.v3 on Microsoft.Testing.Platform), `dotnet test -c Debug --no-build` at the solution for every project including the real-git and real-process adapter tests, `dotnet format --verify-no-changes`.
- Projects: `src\Source191.Vantage.Core` (Domain, Ports, Application; its packages are Logging.Abstractions and System.CommandLine), `src\Source191.Vantage.Infrastructure` (the adapters), `src\Source191.Vantage.Tui` (Terminal.Gui), `src\Source191.Vantage` (`Program.cs`, packed as the tool with the other three inside); `test\Source191.Vantage.Core.Tests`, `test\Source191.Vantage.Infrastructure.Tests`, `test\Source191.Vantage.TestDoubles` (the shared fakes, no test framework) and `tools\HeadlessTerminal.Tests`.
- Local install for testing: `tools\install-local.ps1` stops a running `vantage.exe` (a running exe locks its output and `dotnet tool update` fails), packs as `<Version>-local.<timestamp>` and installs or updates the global tool; `-FromArtifact <folder>` installs a nupkg downloaded from a CI run instead.
- Never start `vantage`, or anything that opens tabs, from inside a Claude Code session without clearing NO_COLOR, CLAUDECODE, CLAUDE_PID and CLAUDE_CODE_*: Windows Terminal hands the caller's environment to new tabs and everything in them runs monochrome. Vantage drops those from its own children (`InheritedEnvironment`), but the Vantage process itself inherits whatever launched it.
- Hand-off check after any change to attach, `vantage here` or the pseudo-console: `dotnet run --project tools\HeadlessTerminal -- check` from `tools\HeadlessTerminal`; exit 0 passes. It is the one automated test of a real `claude attach` and detach.
- Smoke check of the packed tool: `dotnet run --project tools\HeadlessTerminal -- smoke <exe> <worktree-folder>`; exit 0 passes, 1 is a blocked UI thread, 2 no exe, 4 a step whose marker never appeared. Its keys and markers come from `Wording`, so a new dialog is one step in `SmokeScript`.
- Claude Code contract tests start real sessions, so they carry the trait `Category=ClaudeContract` and skip unless `VANTAGE_CLAUDE_CONTRACT=1`: run them with `$env:VANTAGE_CLAUDE_CONTRACT = 1; dotnet test --project test\Source191.Vantage.Infrastructure.Tests -c Debug -- --filter-trait "Category=ClaudeContract"` from a trusted repository. Accepting a help snapshot is copying its `<name>.received.txt` over it, in a change that re-checks the CLI facts below. Never add `--bg --resume --help` to them: it starts a session.
- Mutation testing: Stryker from `test\Source191.Vantage.Core.Tests` with `--test-runner mtp` (xunit.v3 scores 0 % under the VSTest bridge) and `--project Source191.Vantage.Core.csproj`, scoped with `--mutate "**/Domain/*.cs"` style globs, never solution-relative paths.
- Release: every pull request that changes the packaged tool (any file under `src\`, `Directory.Build.props`, `global.json`, `nuget.config`) raises `Version` in `src\Source191.Vantage\Source191.Vantage.csproj`, and `Assert-VersionBumped.ps1` fails it otherwise; each merge of one is a GitHub Release. Versions follow semantic versioning (https://semver.org/): patch for fixes and text, minor for a new key or behaviour that keeps existing keys working, major for a change that breaks how existing keys, state files or the `vantage here` command line behave; `0.y.z` while the tool is pre-1.0, where minor may break. Publishing to nuget.org is only ever `publish.yml`, run by hand, because nuget.org versions cannot be replaced. The manual checks in `CONTRIBUTING.md` are for pull requests that touch `wt.exe`, tabs or attach.

## Working rules

- Every piece of work, including refactors and tooling, starts as an OpenSpec change (`/opsx:propose`); a change with no behaviour change declares `skip_specs: true`. Archive the change in the same pull request that completes it, so `openspec\specs` always describes the code on `main`. `openspec\changes\archive` is history: search it only when asked or when checking why something was decided, never as part of orientation, and never read an archived design as a description of the current code. `openspec validate` is the only mechanical check; the rest is convention.
- TDD: red, green, refactor, a commit per step; no untested code except `Program.cs` and wiring. Sociable tests; fakes only at boundaries (`test\...\TestDoubles`: process runner, process registry, terminal, console, transcripts, folders, state, git roots), hand-written rather than a mocking library.
- Test fixtures use made-up Northwind.* repository names and `C:\Users\me` paths; never real repositories or people. Never read or write the real `%LOCALAPPDATA%\Vantage\config.json` from tests: use `InMemoryState` and `TestSettings`, and a temporary folder for adapter tests. Never write to the real Windows Terminal Fragments folder or `~\.claude\settings.json` from a test or a session: adapter tests use a temporary folder as the root. Tests never reach nuget.org: they use `FakePackageVersions` or a stub `HttpMessageHandler`.
- A project's `.csproj` carries no comments: what is worth recording about a project or one of its settings goes in the `README.md` in that project's folder, which `CONTRIBUTING.md`'s "How the code is organised" table links to. The root `Directory.Build.props` is the exception and keeps its comments beside its settings.
- A newly verified fact about Claude Code, Terminal.Gui, Windows Terminal or Windows is recorded with its date and version: Claude Code's below, the others in their file in `.claude\rules`.
- Commit only when asked.

## Code rules

### Layers and the command line

- Layers, one namespace each and enforced by `test\...\Architecture\LayeringShould.cs` (beside it `TextValuesShould`, `DiagnosticEventsShould`, `NullFreeModelsShould` and `SealedTypesShould` keep the rules below as reflection facts): `Domain` (rules and value objects, depends on nothing), `Ports` (the boundary interfaces and their records), `Application` (use cases in `Actions` and `Launch`, read models, the `Views` reducers, `ScreenLoop`, `CommandLine`), `Adapters` (git, Claude CLI, Windows Terminal, processes, files, state, diagnostics), `Tui` (Terminal.Gui only). `Program.cs` constructs everything and calls `ScreenLoop`, `HereCommandRunner` or `TabClaimer`.
- The whole command line is one System.CommandLine `RootCommand` declared in `Application\CommandLine.Build` (the console as the root action, `here`, `setup-terminal`, hidden `claim-tab`); `Program.cs` hands it a `CommandActions` record of local functions and runs `CommandLine.InvokeAsync`, which sets `ProcessTerminationTimeout = null` because the library's handler would cancel and force an exit two seconds after a Ctrl+C, even under an attached session. Help, `--version`, parse errors, suggestions and `--`, `=`/`:` option syntax are the library's defaults, parse errors exit 1, and only the console and `here` actions locate Claude Code. A new option is a symbol with a `Description` in `Build` and a value read in its action; `CommandLineShould` invokes the root with recording actions and `StringWriter`s.

### C# idioms

- Concrete types, primary constructors, records, collection expressions, file-scoped namespaces, target-typed `new`, `is null` and `is not` patterns, `System.Threading.Lock` and `[LibraryImport]`, each held at `warning` in `.editorconfig` (IDE0008, IDE0290, IDE0300 to IDE0306, IDE0161, IDE0090, IDE0041 and IDE0083, IDE0330, SYSLIB1054). A private constructor behind `From` and `TryParse` stays explicit, because a primary constructor is always public.
- Every class or record that can be sealed is sealed, as [CA1852](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/ca1852) recommends: a concrete type is `sealed` unless another of Vantage's types derives from it; otherwise it is `abstract` or `static`. CA1852 fails the build for internal types (`.editorconfig` sets `ignore_internalsvisibleto`, so assemblies with `InternalsVisibleTo` are checked too) and `Architecture\SealedTypesShould` fails for public ones across Core, Infrastructure, Tui and TestDoubles. The Framework Design Guidelines' advice not to seal without a reason is for reusable libraries, not this application.
- TimeProvider; British English in text; braces always, except that a method whose body fits on one line is expression-bodied (IDE0022 fails the build outside the test projects, whose own `.editorconfig` keeps block bodies).
- Guard clauses use the throw helpers (`ArgumentNullException.ThrowIfNull`, `ArgumentException.ThrowIfNullOrWhiteSpace`, `ArgumentOutOfRangeException.ThrowIfNegative` and the like) wherever one fits, and CA1510 to CA1513 fail the build otherwise. The exceptions: where the exception's message is shown to the user, and in a primary constructor, which has no body, so the field initialiser that reads a parameter guards it (`store ?? throw new ArgumentNullException(nameof(store))`).
- A switch expression over a closed enum names every member and has no discard arm: CS8524 is off in `Directory.Build.props`, so a new member fails the build with CS8509 at every switch that has to learn about it. A switch over a two-case record hierarchy (`SessionNameValidation`, `LaunchPlanResult`, `NewestRelease`) names both cases and its discard arm throws `UnreachableException`, never a guess; an open hierarchy that grows a case per feature (`StatusMessage`, `Outcome`, `LaunchProblem`, `WizardProblem`, `WizardInput`) keeps a delegating or fallback arm, which the reflection facts rely on to spot a missing case, so do not "fix" it.
- Vantage is English only, and the shipped tool runs in invariant globalisation mode, where culture-aware comparisons are ordinal and every `CompareOptions` but `IgnoreCase` is ignored without an exception (so `NumericOrdering` gave way to `Domain\NumberAwareOrder`): no behaviour may rest on culture data. Parsing and formatting name `CultureInfo.InvariantCulture`, and comparisons `StringComparison.Ordinal` or `OrdinalIgnoreCase`. `InvariantGlobalization` is set in the tool project and the three test projects, so the tests run as the tool does, and never in a library, where it would only switch off CA1304, CA1305, CA1309, CA1310 and CA1311. Times are stored in UTC and shown in the local zone: a time in words is converted with `TimeZoneInfo.ConvertTime` and the caller's `TimeProvider.LocalTimeZone` (as `Wording.Detail` and `Wording.ConfigValue` take it), never `ToOffset(now.Offset)`, which gives a time from before a clock change the wrong hour, and today is the local date.
- A value one thread replaces and another reads is held in an `Application\SharedSnapshot<T>` (an immutable value, never null), never by a bare `Volatile` access or `volatile` field elsewhere.

### Reducers, effects and keys

- Reducers (`Application\Views\*View.cs`) are pure functions of state and input, composed over one `ListSelection<TRow>` (rows, selection by key, filter, loaded); everything a key does is a tested effect; the Terminal.Gui layer (`Tui`) only renders and runs effects. A view is an `IScreenDefinition` (columns, colours, cell paint, tab title, counts, key bar, reducer), so a new view adds a reducer, a definition and a tab.
- A `TableBody` routes each effect by its marker: `ISwitchesTab` (`SelectTab`, `NextTab`, `PreviousTab`, `JumpToSession`) to `ConsoleView.Apply` without leaving the application, `ILeavesScreen` (`Quit`; `AttachToSession` keeps the marker but only `vantage here` raises it) back to `ScreenLoop`, which runs the console once, never hands its terminal to a child (Enter opens a session in its own tab) and throws `UnreachableException` for any exit but quit, `IDialogEffect` to `Tui\DialogEffects`, everything else to its handler through `EffectDispatcher`; `EffectRoutingShould` fails for a marked effect nothing routes.
- The new-session wizard is a reducer too (`WizardView.Reduce` over `WizardState`, opened on a `WizardOrigin`, `Anywhere` for `n` or `Fixed` on the worktrees row's folder for `s` (`WizardOrigin.In`), whose `Chosen` answers a `RepositoryPick`, returning a `WizardEffect` to launch, close or do nothing; `WizardEffect.None` and `WizardProblem.None` stand where a null would, as `StatusMessage.Blank` does), and its dialog is a binder: `WizardControls` holds the layout, each control event becomes a `WizardInput`, and the state is pushed back to the controls under a `binding` guard so the events that pushing raises are ignored.
- A dialog with rules gets a reducer the same way, as a setting's dialog does (`SettingsView.Reduce` over `SettingsState`, scoped by a `SettingsScope` to the one value the Config tab's row edits, and holding it inside the saved settings so `Settings.Validate` checks it, bound by `SettingsDialog` and `SettingsControls`). Every repository root row opens `SettingsScope.Roots`, all the roots one per line, where Browse (F3) runs Terminal.Gui's folder picker and `SettingsInput.FoldersChosen` adds each folder as a line for F5 to check; the worktree root's dialog has the same Browse for one folder, which replaces the field, and `SettingsState.Browses` says which dialogs have it.
- A new key is four pieces and no screen change: the effect record (with a marker when it leaves the screen or needs a dialog), the reducer case and its test, a handler (`IEffectHandler<TEffect>` in `Application\Actions`, one class per effect, returning an outcome record declared in its own file, a `...HandlerShould` test asserting that record) and its line in `Composition.Handlers`. Its working text and any status message or question go in `Application\Wording` with a fact in `WordingShould`, the words for its outcome in `WordingOfOutcomes` with a fact in `WordingOfOutcomesShould` and its tone in `Wording.ToneOf` with a line in `StatusTonesShould`, and a dialog flow in `DialogEffects`. `EffectDispatcherShould` fails when a background effect has no registration, `DialogEffectsShould` when a dialog effect has no flow, `ScreenLoopShould` when an effect that leaves the screen is not handled.

### One home per fact

- The settings (roots, worktree root, editor, default base, default place) live in `Application\CurrentSettings`, read per scan, wizard, dialog and Config tab read so a save applies without a restart, with `SettingsFile` resolving config.json's missing properties to defaults.
- Git's worktree facts come from `Application\WorktreeInspector`; every tab's script, title, folder and colour from `Application\TabScripts` (the only holder of the claude and vantage executable paths outside `Program.cs`).
- The Claude CLI's words (busy, waiting, idle, working, blocked, done, failed) are read in `Adapters\Claude\ClaudeStates`, never in `Domain`, and the `gh` and `az` words (states, sign-in hints, a missing extension) only in `Adapters\PullRequests\GitHubPullRequests` and `AzureDevOpsPullRequests`; pull requests reach the rows only through `Application\PullRequestCatalogue`, which never makes a row wait.
- `IGit`'s commands throw `GitException` when git fails or answers with something unreadable, its nullable queries (`OriginUrlAsync` among them) answer null, and `IsMerged` answers false; each method says which.
- A row's folder goes to other tools through three keys, `c` (copy), `e` (editor) and `v` (solution), each an effect with a handler. The clipboard is `IClipboard` (implemented over Terminal.Gui's `app.Clipboard` by `Tui\ScreenClipboard`, attached while a table screen runs), `IDesktop` opens a file with its associated application or starts a program detached with `InheritedEnvironment` applied, and `IEditorLocator` finds a preset's real executable as a `ProgramLocation` (Visual Studio's through `vswhere -latest -property productPath`, run by its full path).

### Values, sessions and null

- Values that look like strings are types: folders are `FolderPath` (the only place two paths are compared), ids are `SessionId`, `JobId` and `BranchName`, a session's name is a `SessionName` and its worktree part a `WorktreeSlug`, and a tab's owner is a `TabOwner`; ports keep strings and callers pass `.Value`.
- Each text value implements `ITextValue<T>` and has three doors, one spelling each: the static `From` builds it or throws, for text Vantage already trusts (the constructor is private); `TryParse(string?, out T)` answers false, for text from outside Vantage; and `Validate` returns the reason as a value, for text a person typed (only `SessionName` has one). No static member answers a null instance and there is no `Parse` or `Of`; `Architecture\TextValuesShould` enforces both, and `Parsed<T>()` keeps the texts of a sequence that parse.
- A session is a `BackgroundSession` (job id and a `JobProcess`, `Running` with its id or `None` once the job is stopped) or an `InteractiveSession` (always a process), and an effect carries the kind it acts on, so nothing checks a kind flag or forgives a null job id.
- Vantage's own models and results never use null for meaning (absence is a named case or a null object); null is met only on the line that receives it from outside (JSON, Terminal.Gui, System.CommandLine, the base class library, and the nullable ports `NullFreeModelsShould` allows); `!` is never used. `Architecture\NullFreeModelsShould` fails for a nullable public property, parameter or return (`T?`, `int?`, or one inside a generic argument) in `Domain`, `Ports` or `Application`, unless it is a house shape (`TryParse(string?, out T)`, a Try method's `out` marked `[NotNullWhen(true)]` or `[MaybeNullWhen(false)]`, `Equals`, `CompareTo`, the equality operators, compiler-generated record members) or on its `Kept` list with a one-line reason; `KeepNoStaleEntry` fails for an entry whose member is no longer nullable, so removing a null removes its excuse. A new nullable is argued for there, in review.

### Wording

- User-facing text lives only in `Application\Wording` and its two test files, with two exceptions: the command line's descriptions sit beside their symbols in `Application\CommandLine` (except the root's support line, `Wording.SupportLine`, because its URL is a fact with one home), and its help layout, parse errors and suggestions are System.CommandLine's own (American English, not replaceable). Reducers return `StatusMessage` values, handlers return outcome records, and the screen asks `Wording` for the words at the last moment. Reflection facts fail when a status message or outcome case has no words.
- User text never comes from an exception message: text a person typed is checked by a `Validate` that returns the reason as a value (`SessionName.Validate` gives a `NameProblem`, `LaunchPlanBuilder` and `HereCommand` a `LaunchProblem`) and `Wording` says it, text from outside Vantage (the CLI's listing, git's output, state files) goes through a `TryParse` that answers false and asks for no reason; an exception's message is shown only to report what failed (`StatusMessage.Failed`, a load failure, a handler's failed outcome), and `catch (ArgumentException` appears only in the process registry's adapter.
- Keys and columns are data in `Wording`: a `KeyHelp` list per view (`SessionsKeys`, `WorktreesKeys`, `ConfigKeys`; `Hint` the key bar's word, empty for a key only the help lists (`KeyHelp.HelpOnly`, `OnBar` false), such as the tab keys in `TabKeyHelp`) and a `ColumnHelp` list (`SessionsColumns`, `WorktreesColumns`, `ConfigColumns`, which also name the table's columns); the help dialog and every tooltip are generated from them, so a new key or column is one line there.

### Security

- Every program Vantage starts is found once as it starts and run by its full path: `Adapters\Processes\ProgramLocator` searches the PATH folders for the `.exe` only (CreateProcess would otherwise look in the parent's current directory before the PATH for a bare name, so a `git.exe` planted in the folder Vantage was started from would run; `ProgramLocatorShould` and the fact in the security review of 2026-10-29 cover it). `ClaudeExecutable.Locate` answers a `ClaudeLocation` (`Found`, `BatchFileOnly`, `Missing`) and `Program.cs` prints `Wording.ClaudeIsABatchFile`, `ClaudeNotFound` or `GitNotFound` and exits 1; `ProgramLocator.Locate` answers a `Ports\ProgramLocation` (`Found`, `Missing`), and `GitHubPullRequests`, `AzureDevOpsPullRequests` (through `AzureCliExecutable.Locate`), `WindowsTerminal` and `Desktop` take a `ProgramLocation` and report a `Missing` one where it is needed.
- A folder reaches an editor as one element of an argument list built by `EditorCommand`, never through a command line or cmd.exe, and the locator never answers a `.cmd` shim.
- No batch file is ever given text from a person, a repository or a listing: a custom editor's executable must be a full path (`SettingsProblem.ExecutableNotFullPath`), and `Domain\BatchFileArgument.IsSafe` (letters, digits, space, dot, underscore, hyphen, slash) is the one rule for what `az.cmd` may be given, applied to the remote names in `RemoteRepository` and to the branch in `AzureDevOpsPullRequests` (`PullRequestGap.BranchNotGivenToAz`).
- User text must never be interpolated into PowerShell source: a tab's script reaches `wt.exe` Base64-encoded for [`pwsh -EncodedCommand`](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_pwsh), and every value inside it (paths, ids, folder names, whole messages) is built by `TabScripts` and goes through `PowerShellScript.Quote`, which doubles all five characters [PowerShell reads as a single quote](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_quoting_rules) (`'` and U+2018 to U+201B). `PowerShellQuotingShould` checks this against real `pwsh`. Every semicolon reaching `wt.exe` is escaped by `WindowsTerminalArguments` (`.claude\rules\windows.md`).
- An opening prompt that starts with `-` is `LaunchProblem.PromptLooksLikeAnOption`.
- A listed process id is ended only while `Domain\ProcessIdentity.StillTheSession` holds (the process started no later than the session's listed start, plus five seconds), as `TabRegistration.IsLive` already checks for tabs; close-empty lists such sessions in `Gone` and adopt answers `ProcessGone`.
- A process's command line carries secrets, so `ProgramLabel` reduces one to a package or executable name and nothing else is kept, logged or shown.
- A worktree whose `.git` file points at a live registration of a repository outside the roots is `WorktreeHealthKind.Elsewhere` (`HealthReason.RepositoryOutsideRoots`), a real worktree to the keys but refused removal with `RemovalReason.RepositoryOutsideRoots`, never deleted as a leftover.

### Diagnostics

- Diagnostics live in `Application\Diagnostics`: one `DiagnosticLog` (the latest 500 events in memory, each also written to the `VANTAGE_LOG` file when it is set), `ProcessCounts` filled by `RecordedProcessRunner` around the one process runner, and `CrashRecorder` writing `%LOCALAPPDATA%\Vantage\last-crash.log`.
- Nothing personal is ever recorded: a new fact is a new `DiagnosticEvent` case whose members are numbers, durations, versions, enums, `CodeName` (built only from a `Type` or `MethodBase`), `ExceptionSummary` (types and frames, never the message) or `ChildCommand` (subcommand words from `ChildCommandWords` only), which `Architecture\DiagnosticEventsShould` enforces, and `DiagnosticsPrivacyShould` runs the daily flows over Northwind fixtures and fails on any fixture value in the output. Never log an effect's `ToString()`, an exception's message, program output or anything typed.
- The rendered lines (`DiagnosticLine`) are the one text outside `Wording`: they are a maintainer's format, not interface text. Terminal.Gui's logger is `TerminalGuiBridge`, which keeps only the level and an exception summary, Warning and above, because its messages can quote typed or pasted input.

## Claude Code CLI facts (verified 2026-10-29, CLI 2.1.310)

Re-verify these, and move the date and version above, whenever a change accepts new help snapshots or raises `ClaudeCodeSupport.Minimum` (the header's below-minimum warning, stated as "2.1.309 or later" in the README and `openspec\config.yaml`, which `DocumentedMinimumShould` keeps in step).

- `claude --version` prints `2.1.310 (Claude Code)`; `IClaudeCli.VersionAsync` takes the leading dotted number (`NotRead` on failure) once per run for the header.
- `claude agents --json [--all]` is the scripting surface. Fields: pid, id, cwd, kind (interactive or background), startedAt, sessionId, name, status (busy, idle, waiting), state (working, blocked, done, failed, stopped), waitingFor. The job `id` is the first 8 characters of `sessionId`. A stopped session is a row without pid or status.
- An interactive listing row with a pid and no `status` is an automated run (`Domain\AutomatedRun`, sorted out in `ClaudeAgentsListing`), never a session row: the Agent SDK (`sdk-py`, `sdk-ts`; the security-guidance plugin's background review, run after a commit or push and when a turn ends, is one, about 20 s and a few thousand tokens) and `claude -p` (with a derived name such as `tmp-9d`) are listed that way for their whole lives, while a `claude` started in a terminal registers without a status and has `idle` about 130 ms later (measured 2026-10-30, CLI 2.1.314, through the headless terminal). `claude logs <id>` never registers. Their count and memory end the Sessions counts (`◇ 1 automated 216 MB`). How long a `claude -p` stays listed, and how the contract fact holds one open, are in `.claude\rules\checks.md`.
- `claude --bg -n <name> [prompt]` starts a supervised session; with no prompt it waits at its own prompt. `attach` accepts a name, `stop` and `rm` need the id. Attaching to a session with no messages lands at that session's own prompt, and Ctrl+Z detaches from it as from any conversation. The CLI has no end-of-options marker: `claude attach -- --help` answers `unknown option '--'` (checked 2026-10-29), so a prompt that starts with `-` would be read as options and Vantage refuses it instead. The npm package now installs the same native binary as the installer; Vantage never runs a `claude.cmd`.
- A session's transcript `~\.claude\projects\<cwd-encoded>\<sessionId>.jsonl` is written on the first message. Resuming a session with no transcript fails with "source session not found", so adopt (`b`), rename (`r`), open-in-tab (Enter) and resume all check `ITranscripts` first.
- `claude --bg --resume <sessionId> -n <name>` continues a *non-background* transcript under the supervisor with the same id (how `b` adopts a terminal session after ending its process). For a *listed background* job the same command with flags starts a copy, as [the docs](https://code.claude.com/docs/en/agent-view) say ("keeps its own saved options"); `claude rm <id>` first (the transcript stays on disc) and the resume then continues the same id under the new name, which is how `r` renames. Never run `claude --bg --resume --help`: it starts a session.
- Interactive sessions register in `~\.claude\sessions\<pid>.json`; they cannot be attached, stopped or removed from outside. Windows Terminal closes a tab when its root shell exits with code 0 and keeps it after a kill, so `d` and `C` end claude and then end the tab's shell cleanly (`TerminalTab`, `IProcessRegistry.EndCleanly`).
- Workspace trust is per repository (linked worktrees inherit it), granted only interactively; `claude --bg` in an untrusted folder exits with "Workspace not trusted". Never script edits to the trust records on a developer machine; the exceptions are the CI `handoff` job and the `claude-contract.yml` workflow, which seed `projects.<path>.hasTrustDialogAccepted` in the throwaway runner's own `~\.claude.json` (keys are forward-slash paths with a capital drive letter, e.g. `D:/a/vantage/vantage`).
- Background sessions do not commit or push on their own (bgIsolation none, sibling worktrees). permission_prompt and idle_prompt notifications fire unattended; agent_needs_input and agent_completed fire only while the native agent view is open, which is why Vantage rings its own bell for background rows.
- `"preferredNotifChannel": "terminal_bell"` in settings.json ([terminal configuration](https://code.claude.com/docs/en/terminal-config)) makes Claude ring the terminal bell when it finishes a task or pauses for a permission prompt while the user appears away, which flags the tab showing a session. Claude Code writes `settings.json` with bare LF; anything that rewrites it must keep that.
- On detach Claude leaves focus reporting on and the cursor hidden and sends a late terminal-version query; `ConsoleRecovery` resets these after every child.
