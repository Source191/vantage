# Vantage

A Terminal.Gui console for Claude Code sessions and git worktrees on Windows, packaged as the dotnet global tool `vantage`. The README is the user guide, `CONTRIBUTING.md` the contributor's guide (setting up, the OpenSpec stages, pull requests, CI, versions) and `MAINTAINING.md` the owner's (releases, nuget.org, secrets); `openspec/` holds the specifications and the changes made against them.

Facts that matter only in part of the code are path-scoped rules in `.claude\rules`, loaded when a matching file is read or edited. Read the one that applies before reasoning about its area from anywhere else:

- **`claude-code.md`:** the verified Claude Code CLI facts (listing fields, automated runs, `--bg`, attach, resume and rename, transcripts, trust, bells) and when to re-verify them.
- **`security.md`:** the detail behind the security and privacy invariants below (program location, batch files, PowerShell quoting, process identity, deleting folders, diagnostics).
- **`console-screen.md`:** the console's layout, tab keys, refreshing and worktree scanning, detail pane, status line, and the wizard and settings dialogs.
- **`terminal-gui.md`:** the verified Terminal.Gui 2.5.0 facts (focus roles, dialogs, tooltips, `Tabs`, spinners, `OpenDialog`, `ImageView`).
- **`windows.md`:** the verified Windows Terminal facts (`wt.exe` semicolons, UI Automation tabs, tab colours and titles, the fragment, updating, ShellExecute) and Windows process facts.
- **`checks.md`:** the CI and release workflows, and the hand-off, smoke, contract and mutation checks in detail.
- **`locale.md`:** what must stay invariant, and what translating Vantage or supporting another culture will need.

## Build, test, release

- Test loop: `dotnet build -c Debug` (warnings are errors), `dotnet test test\Source191.Vantage.Core.Tests -c Debug --no-build` for the fast in-memory suite (xunit.v3 on Microsoft.Testing.Platform), `dotnet test -c Debug --no-build` at the solution for every project including the real-git and real-process adapter tests, `dotnet format --verify-no-changes`.
- Projects: `src\Source191.Vantage.Core` (Domain, Ports, Application; its packages are Logging.Abstractions and System.CommandLine), `src\Source191.Vantage.Infrastructure` (the adapters), `src\Source191.Vantage.Tui` (Terminal.Gui), `src\Source191.Vantage` (`Program.cs` and its `Composition` folder, packed as the tool with the other three inside); `test\Source191.Vantage.Core.Tests`, `test\Source191.Vantage.Infrastructure.Tests`, `test\Source191.Vantage.TestDoubles` (the shared fakes, no test framework), `tools\HeadlessTerminal` and `tools\HeadlessTerminal.Tests`.
- Local install: `tools\install-local.ps1` stops a running `vantage.exe`, packs as `<Version>-local.<timestamp>` and installs or updates the global tool; `-FromArtifact <folder>` installs a nupkg from a CI run.
- Never start `vantage`, or anything that opens tabs, from inside a Claude Code session without clearing NO_COLOR, CLAUDECODE, CLAUDE_PID and CLAUDE_CODE_*: Windows Terminal hands the caller's environment to new tabs and everything in them runs monochrome. Vantage drops those from its own children (`InheritedEnvironment`), but the Vantage process itself inherits whatever launched it.
- Hand-off check after any change to attach, `vantage here` or the pseudo-console: `dotnet build src\Source191.Vantage -c Release`, then `dotnet run -- check` from `tools\HeadlessTerminal`; exit 0 passes. It is the one automated test of a real `claude attach` and detach. Smoke check of an installed tool: `dotnet run -- smoke <exe> <worktree-folder>` from the same folder; exit 0 passes. Its keys and markers come from `Wording`, so a new dialog is one step in `SmokeScript`.
- Claude Code contract tests (`Category=ClaudeContract`, skipped unless `VANTAGE_CLAUDE_CONTRACT=1`) and mutation testing (Stryker with `--test-runner mtp`) are run as `checks.md` says. Never add `--bg --resume --help` to the contract tests: it starts a session.
- Release: every pull request that changes the packaged tool (any file under `src\`, `Directory.Build.props`, `global.json`, `nuget.config`) raises `Version` in `src\Source191.Vantage\Source191.Vantage.csproj` (patch, minor or major as CONTRIBUTING's Versions says; `0.y.z` while pre-1.0, where minor may break), and `Assert-VersionBumped.ps1` fails it otherwise; each merge of one is a GitHub Release. Publishing to nuget.org is only ever `publish.yml`, run by hand, because nuget.org versions cannot be replaced. The manual checks in `CONTRIBUTING.md` are for pull requests that touch `wt.exe`, tabs or attach.

## Working rules

- Every piece of work, including refactors and tooling, starts as an OpenSpec change (`/opsx:propose`); a change with no behaviour change declares `skip_specs: true`. Archive the change in the same pull request that completes it, so `openspec\specs` always describes the code on `main`. `openspec\changes\archive` is history: search it only when asked or when checking why something was decided, never as part of orientation, and never read an archived design as a description of the current code. `openspec validate` is the only mechanical check; the rest is convention.
- TDD: red, green, refactor, a commit per step; no untested code except the tool project's wiring (`Program.cs` and its `Composition` folder). Sociable tests; fakes only at boundaries (`test\...\TestDoubles`, one hand-written fake per port), never a mocking library.
- Test fixtures use made-up Northwind.* repository names and `C:\Users\me` paths; never real repositories or people. Never read or write the real `%LOCALAPPDATA%\Vantage\config.json`, the Windows Terminal Fragments folder or `~\.claude\settings.json` from a test or a session: use `InMemoryState` and `TestSettings`, and a temporary folder as the root for adapter tests. Tests never reach nuget.org: they use `FakePackageVersions` or a stub `HttpMessageHandler`.
- A project's `.csproj` carries no comments: what is worth recording about a project or one of its settings goes in the `README.md` in that project's folder. The root `Directory.Build.props` is the exception and keeps its comments beside its settings.
- A newly verified fact about Claude Code, Terminal.Gui, Windows Terminal or Windows is recorded with its date and version in its file in `.claude\rules`.
- Commit only when asked.

## Code rules

### Layers and the command line

- Layers, one namespace each, enforced by `test\...\Architecture\LayeringShould.cs` (beside it `TextValuesShould`, `DiagnosticEventsShould`, `NullFreeModelsShould` and `SealedTypesShould` keep the rules below as reflection facts, and `Infrastructure.Tests\OneTypePerFileShould` the one-type-per-file rule): `Domain` (rules and value objects, depends on nothing), `Ports` (the boundary interfaces and their records), `Application` (use cases in `Actions` and `Launch`, effect routing in `Effects`, read models, the `Views` reducers, `Detail`, `Diagnostics`, `Reporting`, `TerminalSetup`, `ScreenLoop`, `CommandLine`, `Wording`), `Adapters` (git, Claude CLI, Windows Terminal, processes, files, state, pull requests, package versions, diagnostics), `Tui` (Terminal.Gui only). The tool project is the only composition root, and untested wiring: `Program.cs` keeps the process-wide start (`Composition\SharedParts`, Terminal.Gui's logger, the crash hooks, the command line), `Composition\LaunchParts` the console's and `here`'s shared preamble (`RequiredPrograms`, then `ClaudeCli`, `GitCli` and `LaunchService` once), and `ConsoleComposition`, `HereComposition` and `TerminalSetupComposition` construct each command and call `ScreenLoop`, `HereCommandRunner` or `TerminalSetupRunner`; `claim-tab` is a lambda calling `TabClaimer`. Every decision the wiring needs is a tested `Application` class (`ConsoleLoads`, `Started.From`, `UpdateCheckSwitch`, `HeaderSettingsRow`, `RequiredPrograms`). It constructs by hand, with no dependency injection container.
- The whole command line is one System.CommandLine `RootCommand` declared in `Application\CommandLine.Build` (the console as the root action, `here`, `setup-terminal`, hidden `claim-tab`); `Program.cs` hands it a `CommandActions` record of lambdas and runs `CommandLine.InvokeAsync`, which sets `ProcessTerminationTimeout = null` because the library's handler would otherwise force an exit two seconds after a Ctrl+C, even under an attached session. Help, `--version`, parse errors and option syntax are the library's defaults, parse errors exit 1, and only the console and `here` actions locate Claude Code. A new option is a symbol with a `Description` in `Build` and a value read in its action; `CommandLineShould` invokes the root with recording actions and `StringWriter`s.

### C# idioms

- Concrete types, primary constructors, records, collection expressions, file-scoped namespaces, target-typed `new`, `is null` and `is not` patterns, `System.Threading.Lock` and `[LibraryImport]`, each held at `warning` in `.editorconfig`. A private constructor behind `From` and `TryParse` stays explicit, because a primary constructor is always public.
- Every class or record that can be sealed is sealed: a concrete type is `sealed` unless another of Vantage's types derives from it; otherwise it is `abstract` or `static` (CA1852 for internal types, `SealedTypesShould` for public ones).
- One top-level type per file under `src`, `test` and `tools`, the file named after it without its generic arity (`TableBody<TState, TRow>` in `TableBody.cs`); nested types stay nested (a closed hierarchy's cases live inside their base), and a partial type's files each start with its name (`WordingOfConsole.cs`).
- TimeProvider; British English in text; braces always, except that a method whose body fits on one line is expression-bodied (outside the test projects, which keep block bodies).
- Guard clauses use the throw helpers (`ArgumentNullException.ThrowIfNull` and the like) wherever one fits. The exceptions: where the exception's message is shown to the user, and in a primary constructor, where the field initialiser that reads a parameter guards it (`store ?? throw new ArgumentNullException(nameof(store))`).
- A Try method's `out` parameter is a non-nullable reference type `T` marked `[MaybeNullWhen(false)]`, never `[NotNullWhen(true)] out T?`, as `ITextValue` and the base class library's `IParsable` declare it; callers declare `out T? x`. `NullFreeModelsShould` keeps it in Core, and review in `Infrastructure` and `Tui`.
- A switch expression over a closed enum names every member and has no discard arm (CS8524 is off, so a new member fails the build with CS8509 at every switch). A switch over a two-case record hierarchy (`SessionNameValidation`, `LaunchPlanResult`, `NewestRelease`) names both cases and its discard arm throws `UnreachableException`; an open hierarchy that grows a case per feature (`StatusMessage`, `Outcome`, `LaunchProblem`, `WizardProblem`, `WizardInput`) keeps a delegating or fallback arm, which the reflection facts rely on to spot a missing case, so do not "fix" it.
- English only, and the shipped tool runs in invariant globalisation mode (also set in the test projects, never in a library): no behaviour may rest on culture data. Parsing and formatting name `CultureInfo.InvariantCulture`, comparisons `StringComparison.Ordinal` or `OrdinalIgnoreCase`, and number-aware ordering is `Domain\NumberAwareOrder`. Times are stored in UTC and shown in the local zone through `TimeZoneInfo.ConvertTime` and the caller's `TimeProvider.LocalTimeZone`, never `ToOffset(now.Offset)`; today is the local date.
- A value one thread replaces and another reads is held in an `Application\SharedSnapshot<T>`, never by a bare `Volatile` access or `volatile` field.

### Reducers, effects and keys

- Reducers (`Application\Views\*View.cs`) are pure functions of state and input, composed over one `ListSelection<TRow>`; everything a key does is a tested effect; the `Tui` layer only renders and runs effects. A view is an `IScreenDefinition` (columns, colours, cell paint, tab title, counts, key bar, reducer), so a new view adds a reducer, a definition and a tab. The wizard and every dialog with rules are reducers too, bound to their controls (`console-screen.md`).
- A `TableBody` routes each effect by its marker: `ISwitchesTab` to `ConsoleView.Apply`; `IConsultsSessions` (Enter on a worktree) to `ConsoleView.OpenSession`, which answers from the Sessions rows with the same `RowDecision` as Sessions' own Enter; `ILeavesScreen` (`Quit`; `AttachToSession` keeps the marker but only `vantage here` raises it) back to `ScreenLoop`, which runs the console once, never hands its terminal to a child and throws `UnreachableException` for any exit but quit; `IDialogEffect` to `Tui\DialogEffects`; everything else to its handler through `Application\Effects\EffectDispatcher`. `EffectRoutingShould` fails for a marked effect nothing routes.
- A new key is four pieces and no screen change: the effect record (with a marker when it leaves the screen or needs a dialog), the reducer case and its test, a handler (an `Application\Effects\IEffectHandler<TEffect>` in `Application\Actions`, one class per effect, returning an outcome record declared in its own file, a `...HandlerShould` test asserting that record) and its line in `Application\Effects\Composition.Handlers`. Its text goes in `Wording` with a fact, the words for its outcome in `WordingOfOutcomes` with a fact, its tone in `Wording.ToneOf` with a line in `StatusTonesShould`, and a dialog flow in `DialogEffects`. `EffectDispatcherShould`, `DialogEffectsShould` and `ScreenLoopShould` fail when a piece is missing.

### One home per fact

- The settings (roots, worktree root, editor, default base, default place, update check) live in `Application\CurrentSettings`, read per scan, wizard, dialog and Config tab read so a save applies without a restart, with `SettingsFile` resolving config.json's missing properties to defaults.
- Git's worktree facts come from `Application\WorktreeInspector`; every tab's script, title, folder and colour from `Application\TabScripts` (the only holder of the claude and vantage executable paths outside the tool project's wiring).
- The Claude CLI's words (busy, waiting, idle, working, blocked, done, failed) are read in `Adapters\Claude\ClaudeStates`, never in `Domain`, and the `gh` and `az` words only in `Adapters\PullRequests\GitHubPullRequests` and `AzureDevOpsPullRequests`; pull requests reach the rows only through `Application\PullRequestCatalogue`, which never makes a row wait.
- `IGit`'s commands throw `GitException` when git fails or answers with something unreadable, its nullable queries answer null, and `IsMerged` answers false; each method says which.
- `IClaudeCli`'s `ListSessionsAsync`, `StopAsync` and `RemoveAsync` throw `ClaudeCliException` with claude's own words when claude exits with an error; the start and resume answer a result, `VersionAsync` answers `NotRead`, and each method says which.
- A row's folder goes to other tools through `c` (copy, `IClipboard` over Terminal.Gui's clipboard), `f` (editor, `IEditorLocator` finding a preset's real executable as a `ProgramLocation`) and `s` (solution, `IDesktop` opening a file with its associated application), each an effect with a handler.

### Values, sessions and null

- Values that look like strings are types: folders are `FolderPath` (the only place two paths are compared), ids are `SessionId`, `JobId` and `BranchName`, a session's name is a `SessionName` and its worktree part a `WorktreeSlug`, and a tab's owner is a `TabOwner`; ports keep strings and callers pass `.Value`.
- Each text value implements `ITextValue<T>` and has three doors, one spelling each: the static `From` builds it or throws, for text Vantage already trusts (the constructor is private); `TryParse(string?, out T)` answers false, for text from outside Vantage; and `Validate` returns the reason as a value, for text a person typed (`SessionName` and `ReportTitle`). No static member answers a null instance and there is no `Parse` or `Of`; `TextValuesShould` enforces both, and `Parsed<T>()` keeps the texts of a sequence that parse.
- A session is a `BackgroundSession` (job id and a `JobProcess`, `Running` with its id or `None` once stopped) or an `InteractiveSession` (always a process), and an effect carries the kind it acts on, so nothing checks a kind flag or forgives a null job id.
- Vantage's own models and results never use null for meaning (absence is a named case or a null object such as `WizardEffect.None` or `StatusMessage.Blank`); null is met only on the line that receives it from outside (JSON, Terminal.Gui, System.CommandLine, the base class library, and the nullable ports); `!` is never used. `NullFreeModelsShould` fails for a nullable public member in `Domain`, `Ports` or `Application` unless it is a house shape (`TryParse`, a Try method's `out` marked `[MaybeNullWhen(false)]`, `Equals`, `CompareTo`, the equality operators, compiler-generated record members) or on its `Kept` list with a one-line reason; `KeepNoStaleEntry` fails for an entry that is no longer nullable. A new nullable is argued for there, in review.

### Wording

- User-facing text lives only in `Application\Wording` and its partial files, each with its `Wording*Should` tests, with two exceptions: the command line's descriptions sit beside their symbols in `Application\CommandLine` (except the root's support line, `Wording.SupportLine`), and System.CommandLine's own help layout, parse errors and suggestions (American English, not replaceable). Reducers return `StatusMessage` values, handlers return outcome records, and the screen asks `Wording` for the words at the last moment. Reflection facts fail when a status message or outcome case has no words.
- User text never comes from an exception message: text a person typed is checked by a `Validate` that returns the reason as a value (`NameProblem`, `LaunchProblem`) and `Wording` says it; text from outside Vantage goes through a `TryParse` that answers false; an exception's message is shown only to report what failed. `catch (ArgumentException` appears only in the process registry's adapter and in `ClaudeSettings`, which rethrows a repeated JSON key as a `JsonException`.
- Keys and columns are data in `Wording`: a `KeyHelp` list per view (`SessionsKeys`, `WorktreesKeys`, `ConfigKeys`; `KeyHelp.HelpOnly` for a key only the help lists, such as the tab keys in `TabKeyHelp`) and a `ColumnHelp` list (`SessionsColumns`, `WorktreesColumns`, `ConfigColumns`, which also name the table's columns); the help dialog and every tooltip are generated from them, so a new key or column is one line there.

### Security and privacy

The detail and the reasons are in `security.md`; these hold everywhere:

- Every program Vantage starts is found once by `ProgramLocator` on the PATH's full-path folders, as an `.exe`, and run by its full path; the console and `here` exit 1 when `RequiredPrograms` finds Claude Code or git missing.
- No batch file is ever given text from a person, a repository or a listing (`BatchFileArgument.IsSafe` for `az.cmd`; a custom editor must be a full path to an executable; a folder reaches an editor as one argument from `EditorCommand`). An opening prompt that starts with `-` is refused.
- User text is never interpolated into PowerShell source: a tab's script is built by `TabScripts`, every value goes through `PowerShellScript.Quote`, and it reaches `wt.exe` Base64-encoded with every semicolon escaped.
- A listed process id is ended only while `ProcessIdentity.StillTheSession` holds; a folder is deleted only by `WorktreeRemover`, strictly inside a root or the worktree root, and never one whose `.git` file points at a live checkout.
- Nothing personal is ever recorded: a diagnostic fact is a `DiagnosticEvent` case of numbers, durations, versions, enums, `CodeName`, `ExceptionSummary` or `ChildCommand` (`DiagnosticEventsShould`, `DiagnosticsPrivacyShould`); a process's command line is reduced by `ProgramLabel` and never kept. Never log an effect's `ToString()`, an exception's message, program output or anything typed.

## Claude Code CLI

The verified facts are in `claude-code.md`. Three hold everywhere: never run `claude --bg --resume --help` (it starts a session); resuming a *listed* background job with flags starts a copy, so `claude rm <id>` it first (the transcript stays); and never script edits to Claude Code's trust records on a developer machine (only CI's throwaway runners seed them).
