# Vantage

A Terminal.Gui console for Claude Code sessions and git worktrees on Windows, packaged as the dotnet global tool `vantage`. The README is the user guide; `openspec/` holds the specifications and the changes made against them.

## Build, test, release

- Test loop: `dotnet build -c Debug` (warnings are errors), `dotnet test test\Source191.Vantage.Core.Tests -c Debug --no-build` for the fast in-memory suite (about two seconds, xunit.v3 on Microsoft.Testing.Platform), `dotnet test -c Debug --no-build` at the solution for every project including the real-git and real-process adapter tests, `dotnet format --verify-no-changes`.
- Projects: `src\Source191.Vantage.Core` (Domain, Ports, Application; its packages are Logging.Abstractions and System.CommandLine), `src\Source191.Vantage.Infrastructure` (the adapters), `src\Source191.Vantage.Tui` (Terminal.Gui), `src\Source191.Vantage` (`Program.cs`, packed as the tool with the other three inside); `test\Source191.Vantage.Core.Tests`, `test\Source191.Vantage.Infrastructure.Tests`, `test\Source191.Vantage.TestDoubles` (the shared fakes, no test framework) and `tools\HeadlessTerminal.Tests`.
- Local install for testing: `tools\install-local.ps1` stops a running `vantage.exe` (a running exe locks its output and `dotnet tool update` fails), packs as `<Version>-local.<timestamp>` and installs or updates the global tool; `-FromArtifact <folder>` installs a nupkg downloaded from a CI run instead.
- CI: `.github\workflows\check.yml` (pull requests and pushes to `main`, Windows runner, required by branch protection) builds Release, tests, checks format, packs and uploads the nupkg; `.github\workflows\release.yml` publishes a GitHub Release tagged `v<version>` when a push to `main` changes `Version` in the csproj. Release: every pull request that changes the packaged tool (`src\`, `Directory.Build.props`, `global.json`, `nuget.config`) raises `Version` (the tool cache keeps a version for ever), so each merge of one is a release; the first step of `check` (`.github\scripts\Assert-VersionBumped.ps1`) fails the pull request otherwise. Publishing to nuget.org is `.github\workflows\publish.yml`, run by hand on a tested release tag; it pushes that release's nupkg without building, through Trusted Publishing (`NUGET_USER` secret), and never happens from `release.yml`, because nuget.org versions cannot be replaced. The README's manual checks are for pull requests that touch `wt.exe`, tabs or attach. Versions follow semantic versioning (https://semver.org/): patch for fixes and text, minor for a new key or behaviour that keeps existing keys working, major for a change that breaks how existing keys, state files or the `vantage here` command line behave; `0.y.z` while the tool is pre-1.0, where minor may break.
- Hand-off check after any change to attach, dialogs or Terminal.Gui: `dotnet run --project tools\HeadlessTerminal -- check` from `tools\HeadlessTerminal` (starts and removes its own throwaway session; exit 1 means a blocked UI thread). The `handoff` job in `check.yml` runs the same check on the runner when the `CLAUDE_CODE_OAUTH_TOKEN` secret exists, and never blocks a merge. The same tool has `drive` (scripted keystrokes into a ConPTY pseudo-console, capture to drive-raw.txt), `grid` (replay a capture as a screen) and `count` (plain-text markers). Keys sent before Terminal.Gui has initialised (about 8 s on a cold start) are lost, so scripts start at 8000 ms.
- Mutation testing: Stryker from `test\Source191.Vantage.Core.Tests` with `--test-runner mtp` (xunit.v3 scores 0 % under the VSTest bridge) and `--project Source191.Vantage.Core.csproj`, scoped with `--mutate "**/Domain/*.cs"` style globs, never solution-relative paths.
- Never start `vantage`, or anything that opens tabs, from inside a Claude Code session without clearing NO_COLOR, CLAUDECODE, CLAUDE_PID and CLAUDE_CODE_*: Windows Terminal hands the caller's environment to new tabs and everything in them runs monochrome. Vantage drops those from its own children (`InheritedEnvironment`), but the Vantage process itself inherits whatever launched it.

## Code rules

- Every piece of work, including refactors and tooling, starts as an OpenSpec change (`/opsx:propose`); a change with no behaviour change declares `skip_specs: true`. Archive the change in the same pull request that completes it, so `openspec\specs` always describes the code on `main`. `openspec validate` is the only mechanical check; the rest is convention.
- TDD: red, green, refactor, a commit per step; no untested code except `Program.cs` and wiring. Sociable tests; fakes only at boundaries (`test\...\TestDoubles`: process runner, process registry, terminal, console, transcripts, folders, state, git roots), hand-written rather than a mocking library.
- Layers, one namespace each and enforced by `test\...\Architecture\LayeringShould.cs`: `Domain` (rules and value objects, depends on nothing), `Ports` (the boundary interfaces and their records), `Application` (use cases in `Actions` and `Launch`, read models, the `Views` reducers, `ScreenLoop`, `CommandLine`), `Adapters` (git, Claude CLI, Windows Terminal, processes, files, state, diagnostics), `Tui` (Terminal.Gui only). `Program.cs` constructs everything and calls `ScreenLoop`, `HereCommandRunner` or `TabClaimer`. The whole command line is one System.CommandLine `RootCommand` declared in `Application\CommandLine.Build` (the console as the root action, `here`, `setup-terminal`, hidden `claim-tab`); `Program.cs` hands it a `CommandActions` record of local functions and runs `CommandLine.InvokeAsync`, which sets `ProcessTerminationTimeout = null` because the library's handler would cancel and force an exit two seconds after a Ctrl+C, even under an attached session. Help, `--version`, parse errors, suggestions and `--`, `=`/`:` option syntax are the library's defaults, parse errors exit 1, and only the console and `here` actions locate Claude Code. A new option is a symbol with a `Description` in `Build` and a value read in its action; `CommandLineShould` invokes the root with recording actions and `StringWriter`s.
- Concrete types, primary constructors, records, collection expressions, file-scoped namespaces, TimeProvider, braces always (a method whose body fits on one line is expression-bodied instead: IDE0022 fails the build outside the test projects, whose own `.editorconfig` keeps block bodies), guard clauses use the throw helpers (`ArgumentNullException.ThrowIfNull`, `ArgumentException.ThrowIfNullOrWhiteSpace`, `ArgumentOutOfRangeException.ThrowIfNegative` and the like) wherever one fits, except where the exception's message is shown to the user, and CA1510 to CA1513 fail the build otherwise, British English in text. A switch expression over a closed enum names every member and has no discard arm: CS8524 is off in `Directory.Build.props`, so a new member fails the build with CS8509 at every switch that has to learn about it. A switch over a two-case record hierarchy (`SessionNameValidation`, `LaunchPlanResult`) names both cases and its discard arm throws `UnreachableException`, never a guess; an open hierarchy that grows a case per feature (`Footer`, `Outcome`, `LaunchProblem`, `WizardProblem`, `WizardInput`) keeps a delegating or fallback arm, which the reflection facts rely on to spot a missing case, so do not "fix" it. Reducers (`Application\Views\*View.cs`) are pure functions of state and input, composed over one `ListSelection<TRow>` (rows, selection by key, filter, loaded); everything a key does is a tested effect; the Terminal.Gui layer (`Tui`) only renders and runs effects. The new-session wizard is a reducer too (`WizardView.Reduce` over `WizardState`, returning a `WizardEffect` to launch, close or do nothing; `WizardEffect.None` and `WizardProblem.None` stand where a null would, as `Footer.Blank` does), and its dialog is a binder: `WizardControls` holds the layout, each control event becomes a `WizardInput`, and the state is pushed back to the controls under a `binding` guard so the events that pushing raises are ignored. A dialog with rules gets a reducer the same way, as the settings dialog does (`SettingsView.Reduce` over `SettingsState`, bound by `SettingsDialog` and `SettingsControls`). Each kind of fact has one home: the settings (roots, worktree root, editor, default base) live in `Application\CurrentSettings`, read per scan, wizard, dialog and header redraw so a save applies without a restart, with `SettingsFile` resolving config.json's missing properties to defaults; git's worktree facts come from `Application\WorktreeInspector`, every tab's script, title, folder and colour from `Application\TabScripts` (the only holder of the claude and vantage executable paths outside `Program.cs`), the Claude CLI's words (busy, waiting, idle, working, blocked, done, failed) are read in `Adapters\Claude\ClaudeStates`, never in `Domain`, and the `gh` and `az` words (states, sign-in hints, a missing extension) only in `Adapters\PullRequests\GitHubPullRequests` and `AzureDevOpsPullRequests`; pull requests reach the rows only through `Application\PullRequestCatalogue`, which never makes a row wait. `IGit`'s commands throw `GitException` when git fails or answers with something unreadable, its nullable queries (`OriginUrlAsync` among them) answer null, and `IsMerged` answers false; each method says which. Values that look like strings are types: folders are `FolderPath` (the only place two paths are compared), ids are `SessionId`, `JobId` and `BranchName`, a session's name is a `SessionName` and its worktree part a `WorktreeSlug`, and a tab's owner is a `TabOwner`; ports keep strings and callers pass `.Value`. Each text value implements `ITextValue<T>` and has three doors, one spelling each: the static `From` builds it or throws, for text Vantage already trusts (the constructor is private); `TryParse(string?, out T)` answers false, for text from outside Vantage; and `Validate` returns the reason as a value, for text a person typed (only `SessionName` has one). No static member answers a null instance and there is no `Parse` or `Of`; `Architecture\TextValuesShould` enforces both, and `Parsed<T>()` keeps the texts of a sequence that parse. A session is a `BackgroundSession` (job id, maybe a process) or an `InteractiveSession` (always a process), and an effect carries the kind it acts on, so nothing checks a kind flag or forgives a null job id. User-facing text lives only in `Application\Wording` and its two test files, with two exceptions: the command line's descriptions sit beside their symbols in `Application\CommandLine`, and its help layout, parse errors and suggestions are System.CommandLine's own (American English, not replaceable): reducers return `Footer` values, handlers return outcome records, and the screen asks `Wording` for the words at the last moment. User text never comes from an exception message: text a person typed is checked by a `Validate` that returns the reason as a value (`SessionName.Validate` gives a `NameProblem`, `LaunchPlanBuilder` and `HereCommand` a `LaunchProblem`) and `Wording` says it, text from outside Vantage (the CLI's listing, git's output, state files) goes through a `TryParse` that answers false and asks for no reason; an exception's message is shown only to report what failed (`Footer.Failed`, a load failure, a handler's failed outcome), and `catch (ArgumentException` appears only in the process registry's adapter. Reflection facts fail when a footer or outcome case has no words. One `TableScreen<TState, TRow>` renders every table view and routes each effect by its marker: `ILeavesScreen` back to `ScreenLoop`, `IDialogEffect` to `Tui\DialogEffects`, everything else to its handler through `EffectDispatcher`. A view is an `IScreenDefinition` (layout text, keys, columns, colours, reducer) plus a thin screen class, so a new view adds a reducer, a definition and no screen code. A table's title is a `TableTitle` fact (`ListSelection.Title(noun, labelOf)`) that `Wording.Describe` turns into words. Keys and columns are data in `Wording`: a `KeyHelp` list per view (`SessionsKeys`, `WorktreesKeys`; `Hint` null for a key only the help lists, `Column` the header column) and a `ColumnHelp` list (`SessionsColumns`, `WorktreesColumns`, which also name the table's columns); the help dialog and every tooltip are generated from them, so a new key or column is one line there. The header's first three values are `Wording.HeaderValues` (Vantage version, Claude Code version, roots) and `Program.cs` hands both screens one `ScreenContext`. A row's folder goes to other tools through three keys, `c` (copy), `e` (editor) and `v` (solution), each an effect with a handler: the FOLDER cell is `Domain\FolderLabel` through `Application\FolderLabels` (roots read per redraw from `CurrentSettings`), the clipboard is `IClipboard` (implemented over Terminal.Gui's `app.Clipboard` by `Tui\ScreenClipboard`, attached while a table screen runs), `IDesktop` opens a file with its associated application or starts a program detached with `InheritedEnvironment` applied, and `IEditorLocator` finds a preset's real executable. A folder reaches an editor as one element of an argument list built by `EditorCommand`, never through a command line or cmd.exe, and the locator never answers a `.cmd` shim.
- A new key is four pieces and no screen change: the effect record (with a marker when it leaves the screen or needs a dialog), the reducer case and its test, a handler (`IEffectHandler<TEffect>` in `Application\Actions`, one class per effect, returning an outcome record declared in its own file, a `...HandlerShould` test asserting that record) and its line in `Composition.Handlers`. Its working text and any footer or question go in `Application\Wording` with a fact in `WordingShould`, the words for its outcome in `WordingOfOutcomes` with a fact in `WordingOfOutcomesShould`, and a dialog flow in `DialogEffects`. `EffectDispatcherShould` fails when a background effect has no registration, `DialogEffectsShould` when a dialog effect has no flow, `ScreenLoopShould` when an effect that leaves the screen is not handled.
- Test fixtures use made-up Northwind.* repository names and `C:\Users\me` paths; never real repositories or people. Never read or write the real `%LOCALAPPDATA%\Vantage\config.json` from tests: use `InMemoryState` and `TestSettings`, and a temporary folder for adapter tests.
- Commit only when asked.

## Claude Code CLI facts (verified 2026-10-23, CLI 2.1.309)

- `claude --version` prints `2.1.310 (Claude Code)`; `IClaudeCli.VersionAsync` takes the leading dotted number (null on failure) once per run for the header.
- `claude agents --json [--all]` is the scripting surface. Fields: pid, id, cwd, kind (interactive or background), startedAt, sessionId, name, status (busy, idle, waiting), state (working, blocked, done, failed, stopped), waitingFor. The job `id` is the first 8 characters of `sessionId`. A stopped session is a row without pid or status.
- `claude --bg -n <name> [prompt]` starts a supervised session; with no prompt it idles on the agent list. `attach` accepts a name, `stop` and `rm` need the id. Attaching to a session with no messages lands on Claude's agent list (Esc leaves it, Space sends a prompt); Ctrl+Z only detaches from a conversation.
- A session's transcript `~\.claude\projects\<cwd-encoded>\<sessionId>.jsonl` is written on the first message. Resuming a session with no transcript fails with "source session not found", so adopt (`b`), rename (`r`), attach and resume all check `ITranscripts` first.
- `claude --bg --resume <sessionId> -n <name>` continues a *non-background* transcript under the supervisor with the same id (how `b` adopts a terminal session after ending its process). For a *listed background* job the same command with flags starts a copy, as the docs say ("keeps its own saved options"); `claude rm <id>` first (the transcript stays on disc) and the resume then continues the same id under the new name, which is how `r` renames. Never run `claude --bg --resume --help`: it starts a session.
- Interactive sessions register in `~\.claude\sessions\<pid>.json`; they cannot be attached, stopped or removed from outside. Windows Terminal closes a tab when its root shell exits with code 0 and keeps it after a kill, so `d` and `C` end claude and then end the tab's shell cleanly (`TerminalTab`, `IProcessRegistry.EndCleanly`).
- Workspace trust is per repository (linked worktrees inherit it), granted only interactively; `claude --bg` in an untrusted folder exits with "Workspace not trusted". Never script edits to the trust records on a developer machine; the one exception is the CI `handoff` job, which seeds `projects.<path>.hasTrustDialogAccepted` in the throwaway runner's own `~\.claude.json` (keys are forward-slash paths with a capital drive letter, e.g. `D:/a/vantage/vantage`).
- Background sessions do not commit or push on their own (bgIsolation none, sibling worktrees). permission_prompt and idle_prompt notifications fire unattended; agent_needs_input and agent_completed fire only while the native agent view is open, which is why Vantage rings its own bell for background rows.
- `"preferredNotifChannel": "terminal_bell"` in settings.json makes Claude ring the terminal bell when it finishes a task or pauses for a permission prompt while the user appears away, which flags the tab showing a session. Claude Code writes `settings.json` with bare LF; anything that rewrites it must keep that.
- On detach Claude leaves focus reporting on and the cursor hidden and sends a late terminal-version query; `ConsoleRecovery` resets these after every child.

## Terminal.Gui 2.5.0 facts

- Instance API: `Application.Create().Init()`, `app.Run(window)`, `app.RequestStop`, `app.Invoke`, `app.AddTimeout`; set `app.Driver.Force16Colors = false` or the palette collapses to 16 colours.
- Never block the UI thread on an awaited call (`GetResult()`): Terminal.Gui installs a synchronisation context and the continuation deadlocks. It only showed after an attach-and-return; the harness check exists because of it.
- Focus roles: a scheme with Focus equal to Normal hides focus everywhere; ListView draws the selected row with Focus when focused and Active otherwise; a TextField needs its own background or it is invisible when empty, and a read-only TextField is drawn with the ReadOnly role once it loses focus.
- Dialogs: a Button with IsDefault takes the initial focus; set focus from the dialog's `Initialized` event, not before `Run`. A Dialog of Height 12 has 8 usable rows and the button row overdraws the last. A Label that receives text later needs a fixed Height and non-empty initial Text. A TextField's Enter raises its own `Accepting`; KeyDown handlers on the field or dialog do not see it. Ctrl+C in a TextField copies its selection through `app.Clipboard`, which Windows Terminal passes through when it has no selection of its own.
- Tooltips: `app.ToolTips.SetToolTip(view, text)` shows on hover (the label's MouseEnter), anchored under the pointer's view. A table raises no position reports unless `MousePositionTracking` is true, and its tooltip is evaluated only on entry, so the column-header tooltip is shown by hand (`ApplicationToolTip.ShowFor` from `table.MouseEvent` with `ScreenToCell(position, out header)`, hidden on leaving the header); it appears below the table, not at the header. The headless terminal can hover: send SGR motion `\u001b[<35;col;rowM` (1-based) after 8000 ms.
- A Dialog is clipped to about 31 rows on a 40-row terminal and the Label inside needs Height equal to its lines, so a help text longer than about 22 lines loses its last lines: keep the help short (keys go two to a line).
- `TextView` is obsolete (pragma CS0618) but still the wrapping multi-line box. `OptionSelector` replaces RadioGroup. Table rows take colours through `TableView.Style.RowColorGetter`.
- User text must never be interpolated into PowerShell source: a tab's script reaches `wt.exe` Base64-encoded for `pwsh -EncodedCommand`, and every value inside it (paths, ids, folder names, whole messages) is built by `TabScripts` and goes through `PowerShellScript.Quote`, which doubles all five characters PowerShell reads as a single quote (`'` and U+2018 to U+201B). `PowerShellQuotingShould` checks this against real `pwsh`.

## Windows Terminal facts (verified 2026-10-24, Windows Terminal 1.25)

- `wt.exe` focuses tabs only by index and cannot list them. Windows UI Automation can: the tab items of a `WindowsTerminal.exe` window carry the tab titles as names and support SelectionItemPattern, which is how `o` switches to an open tab (`UiAutomationTabs`, through `Interop.UIAutomationClient`, a ComImport-only net35 library that builds clean under warnings-as-errors on net10.0 and works from a pool thread).
- A tab shell's parent chain is `pwsh <- WindowsTerminal <- explorer` (no OpenConsole hop); `TabRegistration.OwningTerminal` walks it, capped at five steps.
- A program sets its own tab title with OSC 2 and the tab background with OSC 4 on palette entry 264 (`ESC ] 4 ; 264 ; rgb:rr/gg/bb ESC \`); DECAC `ESC [ 2 ; 263 ; 264 , |` resets the tab's colour indices. The terminal ignores the colour for a tab launched with an explicit `--tabColor`. Claude sets the title itself while attached, and Terminal.Gui writes the top-level's `Title` as the terminal title (OSC 0) on every `Run`, so the screens' `Window.Title` and `TerminalConsole` are handed one value, `ScreenContext.Title` from `Wording.TabTitle` (plain `Vantage`; the version is only in the header), and the title and colour are written again after every hand-off (`TabEscapes`). Every `Runnable`, dialogs included, sets `BorderSettings.TerminalTitle` in its constructor and writes its own `Title` when it becomes modal, so every dialog calls `Tui\DialogTabTitle.Apply` with its `DialogName`: that clears the flag and writes `Wording.TabTitleDuring` (`Vantage (Keys)`) on `IsModalChanged`; the main window keeps the flag and writes `Vantage` back when the dialog closes.
- `vantage setup-terminal` writes a fragment, `%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\Vantage\vantage.json` (UTF-8, no BOM), that adds the "Vantage" and "Vantage session" profiles with `bellStyle` and `bellSound`; Windows Terminal reads fragments at start-up, so a restart is needed, and a fragment cannot change `profiles.defaults`. The profile names live once in `Ports\TerminalProfiles`. While the fragment file exists, `WindowsTerminal` adds `--profile "Vantage session"` to every `wt new-tab` it runs (checked on each open). Never write to the real Fragments folder or `~\.claude\settings.json` from a test or a session: adapter tests use a temporary folder as the root. What `wt` does with `--profile` for a profile it has not loaded yet is unverified (the P13 terminal checks record it).
- A running `vantage.exe` locks its own files, so `dotnet tool update` fails while any Vantage runs. `U` therefore updates from a tab of its own (`TabScripts.Update`: `Wait-Process` on this Vantage's process id, `dotnet tool update -g Source191.Vantage`, then the vantage executable only when `$LASTEXITCODE` is 0) and Vantage quits once the tab is open. The nuget.org check (`UpdateCheck` over `IPackageVersions`) runs on a pool thread, at most once a day, never for a prerelease; tests use `FakePackageVersions` or a stub `HttpMessageHandler` and never reach nuget.org.
- `SpinnerView.AutoSpin` is safe to set repeatedly and before the view has an `App` (`EndInit` adds the timeout later); the default style is Line, and `SpinnerStyle.Dots` renders in the headless capture.
- ShellExecute (`Process.Start` with `UseShellExecute = true`, which cannot be given an environment) starts the associated application with the environment its caller was created with: removing variables from the live process first changes nothing (checked 2026-10-25, Windows 11 26100), and `cmd /c start` shows a blocking dialog for a missing file. `Desktop.OpenAsync` therefore makes the call from a short-lived `pwsh` child started through `IProcessRunner` (cleaned like every child), with the target as Base64 in its script (`OpenFileScript`); a file type registered under `HKCU\Software\Classes` with a handler that writes its environment to a file is the harmless way to test it.
