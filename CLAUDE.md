# Vantage

A Terminal.Gui console for Claude Code sessions and git worktrees on Windows, packaged as the dotnet global tool `vantage`. The README is the user guide and `CONTRIBUTING.md` the contributor's guide (setting up, the OpenSpec stages, pull requests, CI and releasing); `openspec/` holds the specifications and the changes made against them.

## Build, test, release

- Test loop: `dotnet build -c Debug` (warnings are errors), `dotnet test test\Source191.Vantage.Core.Tests -c Debug --no-build` for the fast in-memory suite (about two seconds, xunit.v3 on Microsoft.Testing.Platform), `dotnet test -c Debug --no-build` at the solution for every project including the real-git and real-process adapter tests, `dotnet format --verify-no-changes`.
- Projects: `src\Source191.Vantage.Core` (Domain, Ports, Application; its packages are Logging.Abstractions and System.CommandLine), `src\Source191.Vantage.Infrastructure` (the adapters), `src\Source191.Vantage.Tui` (Terminal.Gui), `src\Source191.Vantage` (`Program.cs`, packed as the tool with the other three inside); `test\Source191.Vantage.Core.Tests`, `test\Source191.Vantage.Infrastructure.Tests`, `test\Source191.Vantage.TestDoubles` (the shared fakes, no test framework) and `tools\HeadlessTerminal.Tests`.
- Local install for testing: `tools\install-local.ps1` stops a running `vantage.exe` (a running exe locks its output and `dotnet tool update` fails), packs as `<Version>-local.<timestamp>` and installs or updates the global tool; `-FromArtifact <folder>` installs a nupkg downloaded from a CI run instead.
- CI: `.github\workflows\check.yml` (pull requests and pushes to `main`, Windows runner, required by branch protection; a pull request the owner did not open also needs the owner's approval, through `.github\CODEOWNERS` and the "Owner approves main" ruleset, which the owner bypasses for their own) builds Release with the runner image's SDK (no `setup-dotnet`; `global.json` chooses it), tests, checks whitespace only (`dotnet format whitespace`, because the build already fails on style and analyser warnings), packs and uploads the nupkg (a pull request touching only `openspec\` or `.md` files outside `.github\` skips all of that after the version check, through `.github\scripts\Test-DocumentationOnly.ps1`; pushes to `main` run everything, and a new commit cancels a pull request's older run); every action is pinned to the commit of its release with the version in a comment (Dependabot keeps the pins current; the repository setting requiring pins is turned on once every workflow on `main` has them); `.github\workflows\codeql.yml` runs CodeQL over the C# (build mode none) and the workflows on pull requests, pushes to `main` and weekly, never as a required check; `.github\workflows\release.yml` attaches a build provenance attestation to the package and publishes a GitHub Release tagged `v<version>` when a push to `main` changes `Version` in the csproj. Release: every pull request that changes the packaged tool (`src\`, `Directory.Build.props`, `global.json`, `nuget.config`) raises `Version` (the tool cache keeps a version for ever), so each merge of one is a release; the first step of `check` (`.github\scripts\Assert-VersionBumped.ps1`) fails the pull request otherwise. Publishing to nuget.org is `.github\workflows\publish.yml`, run by hand on a tested release tag; it pushes that release's nupkg without building, through Trusted Publishing (`NUGET_USER` secret) in the `nuget` environment (runs from `main` only, each approved by the owner, and the nuget.org policy names it), and never happens from `release.yml`, because nuget.org versions cannot be replaced. The manual checks in `CONTRIBUTING.md` are for pull requests that touch `wt.exe`, tabs or attach. Versions follow semantic versioning (https://semver.org/): patch for fixes and text, minor for a new key or behaviour that keeps existing keys working, major for a change that breaks how existing keys, state files or the `vantage here` command line behave; `0.y.z` while the tool is pre-1.0, where minor may break.
- Hand-off check after any change to attach, `vantage here` or the pseudo-console: `dotnet run --project tools\HeadlessTerminal -- check` from `tools\HeadlessTerminal` (runs `vantage here` with a throwaway name and no prompt, which makes no model call, waits through `StepRunner` for Claude's `Claude Code v` banner, about 12 s, sends Ctrl+Z and waits for `here` to exit, then stops and removes the job by name; exit 1 means `here` did not exit after the detach, 3 that the banner never appeared; checked 31 October 2026, CLI 2.1.316). It is the one automated test of a real `claude attach` and detach; the console itself never hands over, so the blocked-UI-thread failure it was first built for can no longer happen. A [pseudo-console](https://learn.microsoft.com/windows/console/creating-a-pseudoconsole-session) child is started with [`STARTF_USESTDHANDLES`](https://learn.microsoft.com/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow) and no handles, or its standard output (and Claude's whole screen) would go to the driver's own stdout whenever that is piped, as in CI. The `handoff` job in `check.yml` runs the same check on the runner when the `CLAUDE_CODE_OAUTH_TOKEN` secret exists, and never blocks a merge. The same tool has `drive` (scripted keystrokes into a ConPTY pseudo-console, capture to drive-raw.txt), `grid` (replay a capture as a screen) and `count` (plain-text markers). Keys sent before Terminal.Gui has initialised (about 8 s on a cold start) are lost, so scripts start at 8000 ms.
- Smoke check of the packed tool: `dotnet run --project tools\HeadlessTerminal -- smoke <exe> <worktree-folder>` opens and cancels the Keys help, the wizard, the problem report, the first repository root's dialog on the Config tab and its folder picker (F3), the worktrees view, its help and force remove (on an idle linked worktree), then quits; exit 0 passes, 1 is a blocked UI thread, 2 no exe, 4 a step whose marker never appeared (named in the output). Its steps take their keys (by hint) and markers (dialog tab titles, a column only each view has, and the worktrees title's ", selected: " as the scan-finished signal, since the WORKTREE cell reads `repository › slug` and never the folder name) from `Wording`, so a new dialog is one step in `SmokeScript`. The `check` job installs the Claude Code CLI (signed out: `claude agents --json` prints `[]`), seeds `~\source\repos\Northwind.Smoke` with the linked worktree `Northwind.Smoke-smoke`, installs the packed nupkg into a temporary `--tool-path` and runs it, so it is the one test of the bits users install.
- Claude Code contract tests: `test\...\Infrastructure.Tests\Contract` drives Vantage's own Claude adapters against the installed CLI (version, a `--bg -n` start with no prompt, the listing's fields and state, stop and rm) and compares the commands and options of `claude --help` and `claude agents --help` with `Contract\Snapshots`. They start real sessions, so they carry the trait `Category=ClaudeContract` and skip unless `VANTAGE_CLAUDE_CONTRACT=1`: run them with `$env:VANTAGE_CLAUDE_CONTRACT = 1; dotnet test --project test\Source191.Vantage.Infrastructure.Tests -c Debug -- --filter-trait "Category=ClaudeContract"` from a trusted repository. `.github\workflows\claude-contract.yml` runs them nightly against the latest CLI, with the hand-off check, and when the install or a contract test fails comments on the open `claude-cli` issue or opens one assigned to the `CLAUDE_CLI_WATCHER` repository variable. A snapshot difference leaves `<name>.received.txt` in the output folder (and the run's `contract-results` artefact); accepting it is copying that over the snapshot, in a change that re-checks the CLI facts below. Never add `--bg --resume --help` to them: it starts a session.
- Mutation testing: Stryker from `test\Source191.Vantage.Core.Tests` with `--test-runner mtp` (xunit.v3 scores 0 % under the VSTest bridge) and `--project Source191.Vantage.Core.csproj`, scoped with `--mutate "**/Domain/*.cs"` style globs, never solution-relative paths.
- Never start `vantage`, or anything that opens tabs, from inside a Claude Code session without clearing NO_COLOR, CLAUDECODE, CLAUDE_PID and CLAUDE_CODE_*: Windows Terminal hands the caller's environment to new tabs and everything in them runs monochrome. Vantage drops those from its own children (`InheritedEnvironment`), but the Vantage process itself inherits whatever launched it.

## Code rules

- Every piece of work, including refactors and tooling, starts as an OpenSpec change (`/opsx:propose`); a change with no behaviour change declares `skip_specs: true`. Archive the change in the same pull request that completes it, so `openspec\specs` always describes the code on `main`. `openspec\changes\archive` is history: search it only when asked or when checking why something was decided, never as part of orientation, and never read an archived design as a description of the current code. `openspec validate` is the only mechanical check; the rest is convention.
- TDD: red, green, refactor, a commit per step; no untested code except `Program.cs` and wiring. Sociable tests; fakes only at boundaries (`test\...\TestDoubles`: process runner, process registry, terminal, console, transcripts, folders, state, git roots), hand-written rather than a mocking library.
- Layers, one namespace each and enforced by `test\...\Architecture\LayeringShould.cs` (beside it `TextValuesShould`, `DiagnosticEventsShould` and `NullFreeModelsShould` keep the rules below as reflection facts): `Domain` (rules and value objects, depends on nothing), `Ports` (the boundary interfaces and their records), `Application` (use cases in `Actions` and `Launch`, read models, the `Views` reducers, `ScreenLoop`, `CommandLine`), `Adapters` (git, Claude CLI, Windows Terminal, processes, files, state, diagnostics), `Tui` (Terminal.Gui only). `Program.cs` constructs everything and calls `ScreenLoop`, `HereCommandRunner` or `TabClaimer`. The whole command line is one System.CommandLine `RootCommand` declared in `Application\CommandLine.Build` (the console as the root action, `here`, `setup-terminal`, hidden `claim-tab`); `Program.cs` hands it a `CommandActions` record of local functions and runs `CommandLine.InvokeAsync`, which sets `ProcessTerminationTimeout = null` because the library's handler would cancel and force an exit two seconds after a Ctrl+C, even under an attached session. Help, `--version`, parse errors, suggestions and `--`, `=`/`:` option syntax are the library's defaults, parse errors exit 1, and only the console and `here` actions locate Claude Code. A new option is a symbol with a `Description` in `Build` and a value read in its action; `CommandLineShould` invokes the root with recording actions and `StringWriter`s.
- Concrete types, primary constructors, records, collection expressions, file-scoped namespaces, target-typed `new`, `is null` and `is not` patterns, `System.Threading.Lock` and `[LibraryImport]` (each held at `warning` in `.editorconfig`: IDE0008, IDE0290, IDE0300 to IDE0306, IDE0161, IDE0090, IDE0041 and IDE0083, IDE0330, SYSLIB1054; a private constructor behind `From` and `TryParse` stays explicit, because a primary constructor is always public), TimeProvider, braces always (a method whose body fits on one line is expression-bodied instead: IDE0022 fails the build outside the test projects, whose own `.editorconfig` keeps block bodies), guard clauses use the throw helpers (`ArgumentNullException.ThrowIfNull`, `ArgumentException.ThrowIfNullOrWhiteSpace`, `ArgumentOutOfRangeException.ThrowIfNegative` and the like) wherever one fits, except where the exception's message is shown to the user and in a primary constructor, which has no body, so the field initialiser that reads a parameter guards it (`store ?? throw new ArgumentNullException(nameof(store))`), and CA1510 to CA1513 fail the build otherwise, British English in text. A switch expression over a closed enum names every member and has no discard arm: CS8524 is off in `Directory.Build.props`, so a new member fails the build with CS8509 at every switch that has to learn about it. A switch over a two-case record hierarchy (`SessionNameValidation`, `LaunchPlanResult`, `NewestRelease`) names both cases and its discard arm throws `UnreachableException`, never a guess; an open hierarchy that grows a case per feature (`StatusMessage`, `Outcome`, `LaunchProblem`, `WizardProblem`, `WizardInput`) keeps a delegating or fallback arm, which the reflection facts rely on to spot a missing case, so do not "fix" it. A value one thread replaces and another reads is held in an `Application\SharedSnapshot<T>` (an immutable value, never null), never by a bare `Volatile` access or `volatile` field elsewhere. Reducers (`Application\Views\*View.cs`) are pure functions of state and input, composed over one `ListSelection<TRow>` (rows, selection by key, filter, loaded); everything a key does is a tested effect; the Terminal.Gui layer (`Tui`) only renders and runs effects. The new-session wizard is a reducer too (`WizardView.Reduce` over `WizardState`, opened on a `WizardOrigin`, `Anywhere` for `n` or `Fixed` on the worktrees row's folder for `s` (`WizardOrigin.In`), whose `Chosen` answers a `RepositoryPick`, returning a `WizardEffect` to launch, close or do nothing; `WizardEffect.None` and `WizardProblem.None` stand where a null would, as `StatusMessage.Blank` does), and its dialog is a binder: `WizardControls` holds the layout, each control event becomes a `WizardInput`, and the state is pushed back to the controls under a `binding` guard so the events that pushing raises are ignored. A dialog with rules gets a reducer the same way, as a setting's dialog does (`SettingsView.Reduce` over `SettingsState`, scoped by a `SettingsScope` to the one value the Config tab's row edits (every repository root row opens `SettingsScope.Roots`, all the roots one per line, where Browse (F3) runs Terminal.Gui's folder picker and `SettingsInput.FoldersChosen` adds each folder as a line for F5 to check; the worktree root's dialog has the same Browse for one folder, which replaces the field, and `SettingsState.Browses` says which dialogs have it) and holding it inside the saved settings so `Settings.Validate` checks it, bound by `SettingsDialog` and `SettingsControls`). Each kind of fact has one home: the settings (roots, worktree root, editor, default base, default place) live in `Application\CurrentSettings`, read per scan, wizard, dialog and Config tab read so a save applies without a restart, with `SettingsFile` resolving config.json's missing properties to defaults; git's worktree facts come from `Application\WorktreeInspector`, every tab's script, title, folder and colour from `Application\TabScripts` (the only holder of the claude and vantage executable paths outside `Program.cs`), the Claude CLI's words (busy, waiting, idle, working, blocked, done, failed) are read in `Adapters\Claude\ClaudeStates`, never in `Domain`, and the `gh` and `az` words (states, sign-in hints, a missing extension) only in `Adapters\PullRequests\GitHubPullRequests` and `AzureDevOpsPullRequests`; pull requests reach the rows only through `Application\PullRequestCatalogue`, which never makes a row wait. `IGit`'s commands throw `GitException` when git fails or answers with something unreadable, its nullable queries (`OriginUrlAsync` among them) answer null, and `IsMerged` answers false; each method says which. Values that look like strings are types: folders are `FolderPath` (the only place two paths are compared), ids are `SessionId`, `JobId` and `BranchName`, a session's name is a `SessionName` and its worktree part a `WorktreeSlug`, and a tab's owner is a `TabOwner`; ports keep strings and callers pass `.Value`. Each text value implements `ITextValue<T>` and has three doors, one spelling each: the static `From` builds it or throws, for text Vantage already trusts (the constructor is private); `TryParse(string?, out T)` answers false, for text from outside Vantage; and `Validate` returns the reason as a value, for text a person typed (only `SessionName` has one). No static member answers a null instance and there is no `Parse` or `Of`; `Architecture\TextValuesShould` enforces both, and `Parsed<T>()` keeps the texts of a sequence that parse. A session is a `BackgroundSession` (job id and a `JobProcess`, `Running` with its id or `None` once the job is stopped) or an `InteractiveSession` (always a process), and an effect carries the kind it acts on, so nothing checks a kind flag or forgives a null job id. User-facing text lives only in `Application\Wording` and its two test files, with two exceptions: the command line's descriptions sit beside their symbols in `Application\CommandLine` (except the root's support line, `Wording.SupportLine`, because its URL is a fact with one home), and its help layout, parse errors and suggestions are System.CommandLine's own (American English, not replaceable): reducers return `StatusMessage` values, handlers return outcome records, and the screen asks `Wording` for the words at the last moment. User text never comes from an exception message: text a person typed is checked by a `Validate` that returns the reason as a value (`SessionName.Validate` gives a `NameProblem`, `LaunchPlanBuilder` and `HereCommand` a `LaunchProblem`) and `Wording` says it, text from outside Vantage (the CLI's listing, git's output, state files) goes through a `TryParse` that answers false and asks for no reason; an exception's message is shown only to report what failed (`StatusMessage.Failed`, a load failure, a handler's failed outcome), and `catch (ArgumentException` appears only in the process registry's adapter. Reflection facts fail when a status message or outcome case has no words. The console is one Terminal.Gui application, `Tui\ConsoleScreen`: one settings row (`Wording.SettingsRow`, orange labels and white values as `TextPart`s; the roots and the worktree root are on the Config tab) to the right of `Tui\VantageIcon` where the terminal draws images, a `Tabs` strip with the fixed titles Sessions, Worktrees and Config (a title that changed left the strip measured for the old one; Left and Right, `TabKeys.TryFor`, step between them as `NextTab` and `PreviousTab`, 1, 2 and 3 are `SelectTab`, and `<` and `>` scroll a table's columns in `TableBody`, because Shift+Left and Shift+Right never reached Vantage in Windows Terminal though they worked headless), the active tab's title in bold cyan and every frame grey (`Palette.TabFrame`: `Tabs` draws a title with the Focus role and the lines with Normal; frames coloured per tab broke at the joins the tabs share), the table's header a closed box in the same grey with white names, holding one `TableBody<TState, TRow>` per view, the counts (`Wording.SessionCounts`, `WorktreeCounts`, `ConfigCounts`) after the titles and the table's title right-aligned on the same row (a filter being typed before it, cut at its end), and the two-row key bar (`Wording.SessionsBar`, `WorktreesBar`, `ConfigBar`, placed `KeyBarItem`s drawn as clickable label pairs with tooltips) at the bottom. `ConsoleState` holds every tab's state and the active tab; a `TableBody` routes each effect by its marker: `ISwitchesTab` (`SelectTab`, `NextTab`, `PreviousTab`, `JumpToSession`) to `ConsoleView.Apply` without leaving the application, `ILeavesScreen` (`Quit`; `AttachToSession` keeps the marker but only `vantage here` raises it) back to `ScreenLoop`, which runs the console once, never hands its terminal to a child (Enter opens a session in its own tab) and throws `UnreachableException` for any exit but quit, `IDialogEffect` to `Tui\DialogEffects`, everything else to its handler through `EffectDispatcher`; `EffectRoutingShould` fails for a marked effect nothing routes. The worktrees are scanned once as the console opens, whichever tab is shown, and that scan waits for the Sessions tab's first listing (succeeded or failed) through `Application\LatestSessions`, which holds the Sessions tab's latest listing for every scan, so a scan runs no `claude agents` of its own; after it the Worktrees tab rescans on every show and every 15 seconds while shown, never while hidden, and `Application\RunningLoads` lets one scan run at a time (the console reserves one on the UI thread before `TriggerLoad` and starts nothing when it cannot, and the scan function is wrapped in its `Track`, so the reload after an action is counted but never skipped). Under the Sessions and Worktrees tables `Tui\DetailPane` shows what the selected row does not: a definition's `Detail` is a `Tui\TableDetail<TRow>`: `Pane` over an `Application\Detail\IDetailSource<TRow>` (`SessionDetails` and `WorktreeDetails` over `DetailLoader`, whose every fact fails on its own as `Unavailable`), or `None` on Config, which adds no pane; the source states the most lines it takes, so the pane has a fixed height per tab and the table never jumps; `DetailRequests` numbers the requests and shows only the newest answer for the selected row; `Wording.Detail` words a `DetailContent` (four fact rows of up to three columns, then a worktree's commits or changed files) and `DetailLayout` sets it out at the pane's width. `TableBody` asks only while its tab is shown (a hidden tab drawn alone lands on the shown one) and never makes a refresh wait, and the waiting spinner centres on the table, not the tab. The help's Pane section comes from `Wording.SessionsPane` and `WorktreesPane`. The status line is the console's, not a tab's: `ConsoleScreen` draws it under the settings row from the shown tab's `ITabBody.Status` and `Running`, with rows only while `State.Shown` has words or an action runs (`StatusLayout.Lines` wraps it onto at most three, and the tab strip, counts and table title move down by that many), its mark and colours from `Wording.ToneOf` (a `StatusTone` per status message and outcome case, each chosen in `StatusTonesShould`), `StatusMark` and `StatusWordsTone`; the mark shares its cell with the spinner and hides while it spins, or it blanks it. The line starts at the settings row's indent (after the icon), and a blue ✕ after the last word (`StatusLayout.Closes`) and a success's ten seconds (`StatusLayout.ClearsAfter`) both reduce `MessageDismissed` in the tab that showed the message, which clears it only while it is still that same `StatusMessage` instance. The detail pane closes the tab, and the reducers clear a message when the selection moves or the filter changes; Sessions and Worktrees have no standing message, and Config's is the selected row's description (`StatusMessage.SettingHint`, `Wording.ConfigDescription`). A view is an `IScreenDefinition` (columns, colours, cell paint, tab title, counts, key bar, reducer), so a new view adds a reducer, a definition and a tab. The Config tab is `ConfigView` over `ConfigRow`s (`ConfigRows.For(settings, SetupFacts)`, a case per setting and one `Setup` case per piece of setup, its key stable across a save); its setting rows are shown at once and the setup is read off the UI thread by `SetupFactsReader` each time the tab is shown and after each save, and it has no refresh timer. A table's title is a `TableTitle` fact (`ListSelection.Title(noun, labelOf)`) that `Wording.Describe` turns into words. Keys and columns are data in `Wording`: a `KeyHelp` list per view (`SessionsKeys`, `WorktreesKeys`, `ConfigKeys`; `Hint` the key bar's word, empty for a key only the help lists (`KeyHelp.HelpOnly`, `OnBar` false), such as the tab keys in `TabKeyHelp`) and a `ColumnHelp` list (`SessionsColumns`, `WorktreesColumns`, `ConfigColumns`, which also name the table's columns); the help dialog and every tooltip are generated from them, so a new key or column is one line there. `Program.cs` hands the console one `ScreenContext` (the tab title, the settings row, whether a release is known, the clipboard and the diagnostic log). A row's folder goes to other tools through three keys, `c` (copy), `e` (editor) and `v` (solution), each an effect with a handler: the REPOSITORY and WORKTREE cells are `Domain\WhereLabel` (repository and place `Inside` a repository, the repository's middle elided first, or the folder's label alone `Outside` one; REPOSITORY gives it no place, and neither cell shows the branch, which the detail pane does) over `Domain\FolderLabel` through `Application\FolderLabels` (roots read per redraw from `CurrentSettings`), fitted to the width the screen hands its elastic column, the clipboard is `IClipboard` (implemented over Terminal.Gui's `app.Clipboard` by `Tui\ScreenClipboard`, attached while a table screen runs), `IDesktop` opens a file with its associated application or starts a program detached with `InheritedEnvironment` applied, and `IEditorLocator` finds a preset's real executable as a `ProgramLocation` (Visual Studio's through `vswhere -latest -property productPath`, run by its full path). A folder reaches an editor as one element of an argument list built by `EditorCommand`, never through a command line or cmd.exe, and the locator never answers a `.cmd` shim. Every program Vantage starts is found once as it starts and run by its full path: `Adapters\Processes\ProgramLocator` searches the PATH folders for the `.exe` only (CreateProcess would otherwise look in the parent's current directory before the PATH for a bare name, so a `git.exe` planted in the folder Vantage was started from would run; `ProgramLocatorShould` and the fact in the security review of 2026-10-29 cover it), `ClaudeExecutable.Locate` answers a `ClaudeLocation` (`Found`, `BatchFileOnly`, `Missing`) and `Program.cs` prints `Wording.ClaudeIsABatchFile`, `ClaudeNotFound` or `GitNotFound` and exits 1; `ProgramLocator.Locate` answers a `Ports\ProgramLocation` (`Found`, `Missing`), and `GitHubPullRequests`, `AzureDevOpsPullRequests` (through `AzureCliExecutable.Locate`), `WindowsTerminal` and `Desktop` take a `ProgramLocation` and report a `Missing` one where it is needed. No batch file is ever given text from a person, a repository or a listing: a custom editor's executable must be a full path (`SettingsProblem.ExecutableNotFullPath`), and `Domain\BatchFileArgument.IsSafe` (letters, digits, space, dot, underscore, hyphen, slash) is the one rule for what `az.cmd` may be given, applied to the remote names in `RemoteRepository` and to the branch in `AzureDevOpsPullRequests` (`PullRequestGap.BranchNotGivenToAz`). An opening prompt that starts with `-` is `LaunchProblem.PromptLooksLikeAnOption`. A listed process id is ended only while `Domain\ProcessIdentity.StillTheSession` holds (the process started no later than the session's listed start, plus five seconds), as `TabRegistration.IsLive` already checks for tabs; close-empty lists such sessions in `Gone` and adopt answers `ProcessGone`. A worktree whose `.git` file points at a live registration of a repository outside the roots is `WorktreeHealthKind.Elsewhere` (`HealthReason.RepositoryOutsideRoots`), a real worktree to the keys but refused removal with `RemovalReason.RepositoryOutsideRoots`, never deleted as a leftover.
- Vantage's own models and results never use null for meaning (absence is a named case or a null object); null is met only on the line that receives it from outside (JSON, Terminal.Gui, System.CommandLine, the base class library, and the nullable ports `NullFreeModelsShould` allows); `!` is never used. `Architecture\NullFreeModelsShould` fails for a nullable public property, parameter or return (`T?`, `int?`, or one inside a generic argument) in `Domain`, `Ports` or `Application`, unless it is a house shape (`TryParse(string?, out T)`, a Try method's `out` marked `[NotNullWhen(true)]` or `[MaybeNullWhen(false)]`, `Equals`, `CompareTo`, the equality operators, compiler-generated record members) or on its `Kept` list with a one-line reason; `KeepNoStaleEntry` fails for an entry whose member is no longer nullable, so removing a null removes its excuse. A new nullable is argued for there, in review.
- Diagnostics live in `Application\Diagnostics`: one `DiagnosticLog` (the latest 500 events in memory, each also written to the `VANTAGE_LOG` file when it is set), `ProcessCounts` filled by `RecordedProcessRunner` around the one process runner, and `CrashRecorder` writing `%LOCALAPPDATA%\Vantage\last-crash.log`. Nothing personal is ever recorded: a new fact is a new `DiagnosticEvent` case whose members are numbers, durations, versions, enums, `CodeName` (built only from a `Type` or `MethodBase`), `ExceptionSummary` (types and frames, never the message) or `ChildCommand` (subcommand words from `ChildCommandWords` only), which `Architecture\DiagnosticEventsShould` enforces, and `DiagnosticsPrivacyShould` runs the daily flows over Northwind fixtures and fails on any fixture value in the output. Never log an effect's `ToString()`, an exception's message, program output or anything typed. The rendered lines (`DiagnosticLine`) are the one text outside `Wording`: they are a maintainer's format, not interface text. Terminal.Gui's logger is `TerminalGuiBridge`, which keeps only the level and an exception summary, Warning and above, because its messages can quote typed or pasted input.
- A new key is four pieces and no screen change: the effect record (with a marker when it leaves the screen or needs a dialog), the reducer case and its test, a handler (`IEffectHandler<TEffect>` in `Application\Actions`, one class per effect, returning an outcome record declared in its own file, a `...HandlerShould` test asserting that record) and its line in `Composition.Handlers`. Its working text and any status message or question go in `Application\Wording` with a fact in `WordingShould`, the words for its outcome in `WordingOfOutcomes` with a fact in `WordingOfOutcomesShould` and its tone in `Wording.ToneOf` with a line in `StatusTonesShould`, and a dialog flow in `DialogEffects`. `EffectDispatcherShould` fails when a background effect has no registration, `DialogEffectsShould` when a dialog effect has no flow, `ScreenLoopShould` when an effect that leaves the screen is not handled.
- Test fixtures use made-up Northwind.* repository names and `C:\Users\me` paths; never real repositories or people. Never read or write the real `%LOCALAPPDATA%\Vantage\config.json` from tests: use `InMemoryState` and `TestSettings`, and a temporary folder for adapter tests.
- A project's `.csproj` carries no comments: what is worth recording about a project or one of its settings goes in the `README.md` in that project's folder, which `CONTRIBUTING.md`'s "How the code is organised" table links to. The root `Directory.Build.props` is the exception and keeps its comments beside its settings.
- Commit only when asked.

## Claude Code CLI facts (verified 2026-10-29, CLI 2.1.310)

Re-verify these, and move the date and version above, whenever a change accepts new help snapshots or raises `ClaudeCodeSupport.Minimum` (the header's below-minimum warning, stated as "2.1.309 or later" in the README and `openspec\config.yaml`, which `DocumentedMinimumShould` keeps in step).

- `claude --version` prints `2.1.310 (Claude Code)`; `IClaudeCli.VersionAsync` takes the leading dotted number (`NotRead` on failure) once per run for the header.
- `claude agents --json [--all]` is the scripting surface. Fields: pid, id, cwd, kind (interactive or background), startedAt, sessionId, name, status (busy, idle, waiting), state (working, blocked, done, failed, stopped), waitingFor. The job `id` is the first 8 characters of `sessionId`. A stopped session is a row without pid or status.
- An interactive listing row with a pid and no `status` is an automated run (`Domain\AutomatedRun`, sorted out in `ClaudeAgentsListing`), never a session row: the Agent SDK (`sdk-py`, `sdk-ts`; the security-guidance plugin's background review, run after a commit or push and when a turn ends, is one, about 20 s and a few thousand tokens) and `claude -p` (with a derived name such as `tmp-9d`) are listed that way for their whole lives, while a `claude` started in a terminal registers without a status and has `idle` about 130 ms later (measured 2026-10-30, CLI 2.1.314, through the headless terminal). `claude logs <id>` never registers. Their count and memory end the Sessions counts (`◇ 1 automated 216 MB`). A prompt-less `claude -p` with its standard input redirected and never written registers the same way, waits for input and gives up with exit 1 after about 17 s without a model call, which is how the `ClaudeContract` fact checks the rule for nothing (start it after Vantage is up when checking the screen, since Vantage's first listing takes about 10 s).
- `claude --bg -n <name> [prompt]` starts a supervised session; with no prompt it waits at its own prompt. `attach` accepts a name, `stop` and `rm` need the id. Attaching to a session with no messages lands at that session's own prompt, and Ctrl+Z detaches from it as from any conversation. The CLI has no end-of-options marker: `claude attach -- --help` answers `unknown option '--'` (checked 2026-10-29), so a prompt that starts with `-` would be read as options and Vantage refuses it instead. The npm package now installs the same native binary as the installer; Vantage never runs a `claude.cmd`.
- A session's transcript `~\.claude\projects\<cwd-encoded>\<sessionId>.jsonl` is written on the first message. Resuming a session with no transcript fails with "source session not found", so adopt (`b`), rename (`r`), open-in-tab (Enter) and resume all check `ITranscripts` first.
- `claude --bg --resume <sessionId> -n <name>` continues a *non-background* transcript under the supervisor with the same id (how `b` adopts a terminal session after ending its process). For a *listed background* job the same command with flags starts a copy, as [the docs](https://code.claude.com/docs/en/agent-view) say ("keeps its own saved options"); `claude rm <id>` first (the transcript stays on disc) and the resume then continues the same id under the new name, which is how `r` renames. Never run `claude --bg --resume --help`: it starts a session.
- Interactive sessions register in `~\.claude\sessions\<pid>.json`; they cannot be attached, stopped or removed from outside. Windows Terminal closes a tab when its root shell exits with code 0 and keeps it after a kill, so `d` and `C` end claude and then end the tab's shell cleanly (`TerminalTab`, `IProcessRegistry.EndCleanly`).
- Workspace trust is per repository (linked worktrees inherit it), granted only interactively; `claude --bg` in an untrusted folder exits with "Workspace not trusted". Never script edits to the trust records on a developer machine; the exceptions are the CI `handoff` job and the `claude-contract.yml` workflow, which seed `projects.<path>.hasTrustDialogAccepted` in the throwaway runner's own `~\.claude.json` (keys are forward-slash paths with a capital drive letter, e.g. `D:/a/vantage/vantage`).
- Background sessions do not commit or push on their own (bgIsolation none, sibling worktrees). permission_prompt and idle_prompt notifications fire unattended; agent_needs_input and agent_completed fire only while the native agent view is open, which is why Vantage rings its own bell for background rows.
- `"preferredNotifChannel": "terminal_bell"` in settings.json ([terminal configuration](https://code.claude.com/docs/en/terminal-config)) makes Claude ring the terminal bell when it finishes a task or pauses for a permission prompt while the user appears away, which flags the tab showing a session. Claude Code writes `settings.json` with bare LF; anything that rewrites it must keep that.
- On detach Claude leaves focus reporting on and the cursor hidden and sends a late terminal-version query; `ConsoleRecovery` resets these after every child.

## Terminal.Gui 2.5.0 facts

- Instance API: `Application.Create().Init()`, `app.Run(window)`, `app.RequestStop`, `app.Invoke`, `app.AddTimeout`; set `app.Driver.Force16Colors = false` or the palette collapses to 16 colours.
- Never block the UI thread on an awaited call (`GetResult()`): Terminal.Gui installs a synchronisation context and the continuation deadlocks. It showed only after an attach-and-return, which the console no longer does (a session opens in its own tab); the hand-off check was built because of it.
- Focus roles: a scheme with Focus equal to Normal hides focus everywhere; ListView draws the selected row with Focus when focused and Active otherwise; a TextField needs its own background or it is invisible when empty, and a read-only TextField is drawn with the ReadOnly role once it loses focus.
- Dialogs: a Button with IsDefault takes the initial focus; set focus from the dialog's `Initialized` event, not before `Run`. A Dialog of Height 12 has 8 usable rows and the button row overdraws the last. A Label that receives text later needs a fixed Height and non-empty initial Text. A TextField's Enter raises its own `Accepting`; KeyDown handlers on the field or dialog do not see it. Ctrl+C in a TextField copies its selection through `app.Clipboard`, which Windows Terminal passes through when it has no selection of its own.
- Tooltips: `app.ToolTips.SetToolTip(view, text)` shows on hover (the label's MouseEnter), anchored under the pointer's view. A table raises no position reports unless `MousePositionTracking` is true, and its tooltip is evaluated only on entry, so the column-header tooltip is shown by hand (`ApplicationToolTip.ShowFor` from `table.MouseEvent` with `ScreenToCell(position, out header)`, hidden on leaving the header); Terminal.Gui draws a tooltip at its target's bottom-left (`ToolTipHost.SetPosition` over `FrameToScreen`), so under the whole table it covered the detail pane, and `TableBody` targets a zero-width view laid over the header (or, for a Config row's description from `IScreenDefinition.RowTip`, over the row) at the pointer's column, which puts it on the rows just under. It still shifts a wide tooltip left to fit the screen. The headless terminal can hover: send SGR motion `\u001b[<35;col;rowM` (1-based) after 8000 ms.
- The help is `Tui\HelpDialog`: a read-only `TextView` in a dialog as tall as the text needs, up to nine tenths of the screen, with focus in the text so the arrow keys and PageUp and PageDown scroll it. A Dialog reserves its own button area, so the box is `Y = 0` with `Dim.Fill()`; reserving rows for the button as well cuts the last lines. The sessions help (26 lines) fits whole at 120 x 36.
- Removing a SubView from `Tabs` selects another and raises `ValueChanged`, so `ConsoleScreen` disposes its tabs under the binding guard, or quitting shows (and logs) the other tabs.
- `OpenDialog` (`OpenMode.Directory`, `AllowsMultipleSelection`) is the roots dialog's folder picker, checked by a spike on 30 October 2026: it derives from `Dialog<IReadOnlyList<string>>`, not the plain `Dialog`, so `DialogTabTitle.Apply` takes a `Runnable`, and it writes its own title as the tab title like any Runnable. It opens at 96 x 28 in a 120 x 36 terminal and takes `Palette.Focusable` for most of its parts. Focus starts in its path box; Tab reaches the folder list, Down moves the selection (the path box follows), Shift+Down extends it, Enter in the list confirms rather than opening the folder, and Space does not toggle a row. `FilePaths` answers the folders in the order chosen (`Path` is empty for several), and `Canceled` is true after Esc. The headless terminal drives it.
- `TextView` is obsolete (pragma CS0618) but still the wrapping multi-line box. `OptionSelector` replaces RadioGroup. Table rows take colours through `TableView.Style.RowColorGetter`.
- `Tabs` (no `TabView` or `TileView` in 2.5.0) shows each SubView as a tab titled by its `Title`; the strip takes three rows (outer border, titles, separator) and the selected tab's body starts on the fourth, framed. Its span is each title's length plus a border cell either side, adjacent tabs sharing one (`GetTotalHeaderSpan` and `Border.TabOffset` are not public), so the counts label sits after it on the title row. The selected tab is the focused SubView, so a tab's view has `CanFocus = true`; setting `Value` and clicking a title both raise `ValueChanged`, so the console applies a click under a binding guard. A spinner redraws only its own tab, title box and frame included, which lands on top of the shown tab and closes its edge under the title (the Worktrees tab's waiting spinner, which turns while its first scan runs and the tab may be hidden, did this from the first frame), so `ConsoleScreen.Show` tells both tabs which is shown (`ITabBody.Shown`) and a hidden tab keeps its spinners still; a table refresh is safe because `FrameChanged` redraws the whole window. It binds the arrow and paging keys to moving between tabs, which took Up and Down from the table, so `ConsoleScreen` removes those bindings from the strip and both tab views; every other key still reaches the window's `KeyDown`. `Shortcut` draws its command text before its key (`Attach  Enter`) with Terminal.Gui's own key names, so the key bar is label pairs with `MouseEvent` handlers on `MouseFlags.LeftButtonClicked` instead (checked by a spike, 30 October 2026).
- A table that cannot take focus draws its selected row with the scheme's Active role, which Terminal.Gui derives as a lighter shade when a scheme leaves it unset (black on cyan came out as bold dark grey on bright cyan, a red block as pink): `Palette.SelectedRow` names those colours and sets every role, and a cell that keeps its own colour there (the TAB block, `CellPaint.Always`) is drawn with `Palette.SelectedRow(colour)`.
- `ImageView` (Terminal.Gui 2.5) takes a `Color[,]` and draws it through [Sixel](https://vt100.net/docs/vt3xx-gp/chapter14.html) or [Kitty](https://sw.kovidgoyal.net/kitty/graphics-protocol/) when the driver reports support (`app.Driver.SixelSupport`, detected at start-up; Windows Terminal draws Sixel), fitted to the view at `ZoomLevel` 1; without support it colours one cell per pixel, so `VantageIcon` stays hidden then. The icon's pixels are `assets\icon\vantage-48.rgba` (`*.rgba binary` in `.gitattributes`), written by `tools\New-IconPixels.ps1` (the icon from `VantageMark.ps1` with `-Outline`, an edge in the frames' grey drawn inside its dark tile, which otherwise vanished on the console's black; white was too stark and the mark without its tile, `-NoTile`, read worse; `VantageIcon.Fit` makes the view as many cells wide as its one row is tall in pixels, from the reported cell size, because a fixed width stretched the icon) and embedded in the Tui assembly; the headless terminal reports no image support, so its captures never show the icon.
- User text must never be interpolated into PowerShell source: a tab's script reaches `wt.exe` Base64-encoded for [`pwsh -EncodedCommand`](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_pwsh), and every value inside it (paths, ids, folder names, whole messages) is built by `TabScripts` and goes through `PowerShellScript.Quote`, which doubles all five characters [PowerShell reads as a single quote](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_quoting_rules) (`'` and U+2018 to U+201B). `PowerShellQuotingShould` checks this against real `pwsh`.

## Windows Terminal facts (verified 2026-10-24, Windows Terminal 1.25)

- [`wt.exe`](https://learn.microsoft.com/windows/terminal/command-line-arguments) focuses tabs only by index and cannot list them. Windows [UI Automation](https://learn.microsoft.com/windows/win32/winauto/entry-uiauto-win32) can: the tab items of a `WindowsTerminal.exe` window carry the tab titles as names and support [SelectionItemPattern](https://learn.microsoft.com/windows/win32/api/uiautomationclient/nn-uiautomationclient-iuiautomationselectionitempattern), which is how Enter switches to an open tab (`UiAutomationTabs`, through `Interop.UIAutomationClient`, a ComImport-only net35 library that builds clean under warnings-as-errors on net10.0 and works from a pool thread).
- `wt.exe` [splits its command line](https://learn.microsoft.com/windows/terminal/command-line-arguments) on every semicolon, even inside an argument passed quoted: `--title 'fix a;b'` opens a tab titled `fix a` and a second tab that fails to launch `b pwsh.exe -NoExit`. `\;` passes a literal one (`'fix a\;b'` gives the title `fix a;b`, `'a\\;b'` gives `a\;b`) and every other backslash is left as it is (`'a\b'` gives `a\b`), in `--startingDirectory` too. A double quote, which `ArgumentList` passes as `\"`, reaches the title intact (`say "hi"`); `claude --bg -n 'a;b'` keeps the name as typed (checked 2026-10-28, Windows Terminal 1.25.2733, CLI 2.1.312). So `WindowsTerminalArguments` replaces every `;` in its arguments with `\;`, and `SessionName` refuses only a blank name. With that in place the open-in-tab key (then `o`, now Enter) finds the tabs titled `fix a;b` and `say "hi"` by their exact titles, `claude attach` takes `fix a;b` by name, both titles survive the hand-off, and rename resumes under `fix c;d` (checked 2026-10-28, 0.17.0-preview.1).
- A tab shell's parent chain is `pwsh <- WindowsTerminal <- explorer` (no OpenConsole hop); `Domain\TerminalTab` walks it (any case, eight steps) for both the tab's shell and its terminal, which `TabRegistration.OwningTerminal` uses, answering a `Domain\TerminalWindow` (`Owning`, or `Any` while the tab is being claimed or its shell is outside Windows Terminal) that `FocusTabAsync` searches.
- `claude attach` exits 0 after a Ctrl+Z detach, a `claude stop` and a `claude rm` from elsewhere (measured 29 October 2026, CLI 2.1.312, in a pseudo-console), so the attach tab's script ends with `if ($LASTEXITCODE -eq 0) { exit }` and the tab closes with the attach; its registration then goes stale with the shell. Stop, rename and delete close a session's live tabs through `Application\Actions\SessionTabs` (`EndCleanly` on each claimed shell, every registration forgotten), adopt ends the old tab's shell found before claude ends, and Enter reads a registration's liveness at the key. Git's "Permission denied" on `git worktree remove` is `GitException.InUse`, read only in `GitCli`.
- An unselected tab with a colour is that colour at alpha 77 of 255 (`deselectedTabColor.with_alpha(77)` in Windows Terminal's `Tab.cpp`) over the tab row, #2E2E2E in the default dark theme, so `Domain\TabShade.Unselected` works out each channel as `(colour × 77 + 46 × 178) / 255` and the TAB block is drawn in that shade, Vantage's own tab being the selected one whenever its table is read (measured 30 October 2026, Windows Terminal 1.25.2733.0: a window of one tab per palette colour captured with `PrintWindow` and `PW_RENDERFULLCONTENT`, which works with the workstation locked, each tab's fill the commonest pixel in its UI Automation box; 28 of the 33 channels exact, five one step high). A light theme or a custom tab row is not followed.
- A program sets its own tab title with OSC 2 and the tab background with OSC 4 on palette entry 264 (`ESC ] 4 ; 264 ; rgb:rr/gg/bb ESC \`); DECAC `ESC [ 2 ; 263 ; 264 , |` resets the tab's colour indices. The terminal ignores the colour for a tab launched with an explicit `--tabColor`. Claude sets the title itself while attached, and Terminal.Gui writes the top-level's `Title` as the terminal title (OSC 0) on every `Run`, so the console's `Window.Title` and `TerminalConsole` are handed one value, `ScreenContext.Title` from `Wording.TabTitle` (plain `Vantage`; the version is only in the settings line), and the title and colour are written once as the console starts (`TabEscapes`; the console never hands its terminal over, so nothing retitles its tab but a dialog). Every `Runnable`, dialogs included, sets `BorderSettings.TerminalTitle` in its constructor and writes its own `Title` when it becomes modal, so every dialog calls `Tui\DialogTabTitle.Apply` with its `DialogName`: that clears the flag and writes `Wording.TabTitleDuring` (`Vantage (Keys)`) on `IsModalChanged`; the main window keeps the flag and writes `Vantage` back when the dialog closes.
- `vantage setup-terminal` writes a [fragment](https://learn.microsoft.com/windows/terminal/json-fragment-extensions), `%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\Vantage\vantage.json` (UTF-8, no BOM), that adds the "Vantage" and "Vantage session" profiles with [`bellStyle`, `bellSound`](https://learn.microsoft.com/windows/terminal/customize-settings/profile-advanced) and [`icon`](https://learn.microsoft.com/windows/terminal/customize-settings/profile-general) (`vantage.ico`, shipped beside the tool from `assets\icon` and copied into the fragment's own folder so a tool update cannot break the path; `--remove` deletes it with the folder; a tab not opened from these profiles keeps its own icon, and Windows Terminal has no escape sequence for one); Windows Terminal reads fragments at start-up, so a restart is needed, and a fragment cannot change `profiles.defaults`. The profile names live once in `Ports\TerminalProfiles`. While the fragment file exists, `WindowsTerminal` adds `--profile "Vantage session"` to every `wt new-tab` it runs (checked on each open). Never write to the real Fragments folder or `~\.claude\settings.json` from a test or a session: adapter tests use a temporary folder as the root. What `wt` does with `--profile` for a profile it has not loaded yet is unverified (the P13 terminal checks record it).
- A running `vantage.exe` locks its own files, so [`dotnet tool update`](https://learn.microsoft.com/dotnet/core/tools/dotnet-tool-update) fails while any Vantage runs. `U` therefore updates from a tab of its own (`TabScripts.Update`: `Wait-Process` on this Vantage's process id, `dotnet tool update -g Source191.Vantage`, then the vantage executable only when `$LASTEXITCODE` is 0) and Vantage quits once the tab is open. The nuget.org check (`UpdateCheck` over `IPackageVersions`) is started by `ScreenLoop` on a pool thread as the console opens (never awaited; a fault is only logged), asks at most once a day, never for a prerelease; tests use `FakePackageVersions` or a stub `HttpMessageHandler` and never reach nuget.org.
- `SpinnerView.AutoSpin` is safe to set repeatedly and before the view has an `App` (`EndInit` adds the timeout later); the default style is Line, and `SpinnerStyle.Dots` renders in the headless capture.
- [ShellExecute](https://learn.microsoft.com/windows/win32/api/shellapi/nf-shellapi-shellexecutew) (`Process.Start` with [`UseShellExecute = true`](https://learn.microsoft.com/dotnet/api/system.diagnostics.processstartinfo.useshellexecute), which cannot be given an environment) starts the associated application with the environment its caller was created with: removing variables from the live process first changes nothing (checked 2026-10-25, Windows 11 26100), and `cmd /c start` shows a blocking dialog for a missing file. `Desktop.OpenAsync` therefore makes the call from a short-lived `pwsh` child started through `IProcessRunner` (cleaned like every child), with the target as Base64 in its script (`OpenFileScript`); a file type registered under `HKCU\Software\Classes` with a handler that writes its environment to a file is the harmless way to test it.

## Windows process facts (verified 2026-10-29, Windows 11 26100)

- A process's memory for the detail pane's Memory line and the `m` breakdown is its private working set, read with [`GetProcessMemoryInfo`](https://learn.microsoft.com/windows/win32/api/psapi/nf-psapi-getprocessmemoryinfo) and [`PROCESS_MEMORY_COUNTERS_EX2`](https://learn.microsoft.com/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2) (`PrivateWorkingSetSize`): the figure Task Manager's Memory column and the `Working Set - Private` counter show. It counts resident pages only: an MCP server idle for hours reads a few kilobytes against 90 MB of commit (`PrivateUsage`, the same structure) because Windows has paged its heap out, and thirty node processes share the runtime's image pages, so summing working sets (`WorkingSet64`) doubled a tree's figure. A megabyte is 1,048,576 bytes throughout.
- [`Process.GetProcessById`](https://learn.microsoft.com/dotnet/api/system.diagnostics.process.getprocessbyid) walks the whole process table on every call, about 20 ms: measuring six sessions' 235 processes through it took 4 to 6 s per refresh, against 40 to 230 ms through [`OpenProcess`](https://learn.microsoft.com/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocess) with [`PROCESS_QUERY_LIMITED_INFORMATION`](https://learn.microsoft.com/windows/win32/procthread/process-security-and-access-rights) and [`GetProcessTimes`](https://learn.microsoft.com/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes) (which also reads processes a full-access handle is refused for). `UsageOf` opens the handle itself; `ProcessRegistryIntegrationShould` keeps two hundred queries under a second.
- [`CreateToolhelp32Snapshot`](https://learn.microsoft.com/windows/win32/api/tlhelp32/nf-tlhelp32-createtoolhelp32snapshot) lists every process with its parent's id in a few milliseconds without opening any; the parent id is never cleared when the parent exits, and Windows reuses ids, so a process may list a parent younger than itself (an installer-launched app sat under a session's reused id during the spike). `ProcessTree` keeps a child only when it started after its nearest measured ancestor.
- [`NtQueryInformationProcess`](https://learn.microsoft.com/windows/win32/api/winternl/nf-winternl-ntqueryinformationprocess) with class 60 (`ProcessCommandLineInformation`) answers a process's command line as a `UNICODE_STRING`; asked with no buffer it answers `STATUS_INFO_LENGTH_MISMATCH` and the length. Command lines carry secrets (an MCP server's API key was in one), so `ProgramLabel` reduces one to a package or executable name and nothing else is kept, logged or shown.
- A Terminal.Gui Label reads `_` as its hotkey mark unless `HotKeySpecifier` is set to U+FFFF before `Text` (node_repl showed as noderepl). A Dialog holding one Label per line from Y 1 and a Button with its shadow row drew nothing in its last two content rows at Height lines + 6 (the same loss as a single multi-line Label through `Confirm.Ask`), so `MemoryDialog` uses lines + 8; this is two rows fewer than the "8 usable rows at Height 12" rule above allows, and the difference is unexplained.
