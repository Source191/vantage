# Windows Terminal and Windows process facts

## Windows Terminal facts (verified 2026-10-24, Windows Terminal 1.25)

- [`wt.exe`](https://learn.microsoft.com/windows/terminal/command-line-arguments) focuses tabs only by index and cannot list them. Windows [UI Automation](https://learn.microsoft.com/windows/win32/winauto/entry-uiauto-win32) can: the tab items of a `WindowsTerminal.exe` window carry the tab titles as names and support [SelectionItemPattern](https://learn.microsoft.com/windows/win32/api/uiautomationclient/nn-uiautomationclient-iuiautomationselectionitempattern), which is how Enter switches to an open tab (`UiAutomationTabs`, through `Interop.UIAutomationClient`, a ComImport-only net35 library that builds clean under warnings-as-errors on net10.0 and works from a pool thread).
- `wt.exe` [splits its command line](https://learn.microsoft.com/windows/terminal/command-line-arguments) on every semicolon, even inside an argument passed quoted: `--title 'fix a;b'` opens a tab titled `fix a` and a second tab that fails to launch `b pwsh.exe -NoExit`. `\;` passes a literal one (`'fix a\;b'` gives the title `fix a;b`, `'a\\;b'` gives `a\;b`) and every other backslash is left as it is (`'a\b'` gives `a\b`), in `--startingDirectory` too. A double quote, which `ArgumentList` passes as `\"`, reaches the title intact (`say "hi"`); `claude --bg -n 'a;b'` keeps the name as typed (checked 2026-10-28, Windows Terminal 1.25.2733, CLI 2.1.312). So `WindowsTerminalArguments` replaces every `;` in its arguments with `\;`, and `SessionName` refuses only a blank name. With that in place the open-in-tab key (then `o`, now Enter) finds the tabs titled `fix a;b` and `say "hi"` by their exact titles, `claude attach` takes `fix a;b` by name, both titles survive the hand-off, and rename resumes under `fix c;d` (checked 2026-10-28, 0.17.0-preview.1).
- A tab shell's parent chain is `pwsh <- WindowsTerminal <- explorer` (no OpenConsole hop); `Domain\TerminalTab` walks it (any case, eight steps) for both the tab's shell and its terminal, which `TabRegistration.OwningTerminal` uses, answering a `Domain\TerminalWindow` (`Owning`, or `Any` while the tab is being claimed or its shell is outside Windows Terminal) that `FocusTabAsync` searches.
- `wt -w 0 new-tab`, which `WindowsTerminalArguments` uses, opens the tab in the most recently used window: run from a tab of a window just opened with `wt -w new`, the tab lands in that new window and not in an older one (checked 4 November 2026, Windows Terminal 1.25.2733.0, by UI Automation tab names per window). `tools\ReadmeScene` relies on it to keep the screenshot's session tabs in its own window.
- `claude attach` exits 0 after a Ctrl+Z detach, a `claude stop` and a `claude rm` from elsewhere (measured 29 October 2026, CLI 2.1.312, in a pseudo-console), so the attach tab's script ends with `if ($LASTEXITCODE -eq 0) { exit }` and the tab closes with the attach; its registration then goes stale with the shell. Stop, rename and delete close a session's live tabs through `Application\Actions\SessionTabs` (`EndCleanly` on each claimed shell, every registration forgotten), adopt ends the old tab's shell found before claude ends, and Enter reads a registration's liveness at the key. Git's "Permission denied" on `git worktree remove` is `GitException.InUse`, read only in `GitCli`.
- An unselected tab with a colour is that colour at alpha 77 of 255 (`deselectedTabColor.with_alpha(77)` in Windows Terminal's [`Tab.cpp`](https://github.com/microsoft/terminal/blob/v1.25.2733.0/src/cascadia/TerminalApp/Tab.cpp#L2387)) over the tab row, #2E2E2E in the default dark theme, so `Domain\TabShade.Unselected` works out each channel as `(colour × 77 + 46 × 178) / 255` and the TAB block is drawn in that shade, Torni's own tab being the selected one whenever its table is read (measured 30 October 2026, Windows Terminal 1.25.2733.0: a window of one tab per palette colour captured with `PrintWindow` and `PW_RENDERFULLCONTENT`, which works with the workstation locked, each tab's fill the commonest pixel in its UI Automation box; 28 of the 33 channels exact, five one step high). A light theme or a custom tab row is not followed.
- A program sets its own tab title with OSC 2 and the tab background with OSC 4 on palette entry 264 (`ESC ] 4 ; 264 ; rgb:rr/gg/bb ESC \`); DECAC `ESC [ 2 ; 263 ; 264 , |` resets the tab's colour indices. The terminal ignores the colour for a tab launched with an explicit `--tabColor`. Claude sets the title itself while attached, and Terminal.Gui writes the top-level's `Title` as the terminal title (OSC 0) on every `Run`, so the console's `Window.Title` and `TerminalConsole` are handed one value, `ScreenContext.Title` from `Wording.TabTitle` (plain `Torni`; the version is only in the settings line), and the title and colour are written once as the console starts (`TabEscapes`; the console never hands its terminal over, so nothing retitles its tab but a dialog). Every `Runnable`, dialogs included, sets `BorderSettings.TerminalTitle` in its constructor and writes its own `Title` when it becomes modal, so every dialog calls `Tui\DialogTabTitle.Apply` with its `DialogName`: that clears the flag and writes `Wording.TabTitleDuring` (`Torni (Keys)`) on `IsModalChanged`; the main window keeps the flag and writes `Torni` back when the dialog closes.
- `torni setup-terminal` writes a [fragment](https://learn.microsoft.com/windows/terminal/json-fragment-extensions), `%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\Torni\torni.json` (UTF-8, no BOM), that adds the "Torni" and "Torni session" profiles with [`bellStyle`, `bellSound`](https://learn.microsoft.com/windows/terminal/customize-settings/profile-advanced) and [`icon`](https://learn.microsoft.com/windows/terminal/customize-settings/profile-general) (`torni.ico`, shipped beside the tool from `assets\icon` and copied into the fragment's own folder so a tool update cannot break the path; `--remove` deletes it with the folder; a tab not opened from these profiles keeps its own icon, and Windows Terminal has no escape sequence for one); Windows Terminal reads fragments at start-up, so a restart is needed, and a fragment cannot change `profiles.defaults`. The profile names live once in `Ports\TerminalProfiles`. While the fragment file exists, `WindowsTerminal` adds `--profile "Torni session"` to every `wt new-tab` it runs (checked on each open). What `wt` does with `--profile` for a profile it has not loaded yet is unverified (the P13 terminal checks record it).
- A running `torni.exe` locks its own files, so an upgrade fails while any Torni runs (as [`dotnet tool update`](https://learn.microsoft.com/dotnet/core/tools/dotnet-tool-update) did). `U` therefore upgrades from a tab of its own (`TabScripts.Update`: `Wait-Process` on this Torni's process id, `winget upgrade --id Source191.Torni --exact --source winget` by winget's full path, then the torni executable only when `$LASTEXITCODE` is 0) and Torni quits once the tab is open; with no winget on the PATH no tab opens and Torni stays (`WingetMissingOutcome`). The check (`UpdateCheck` over `IPackageVersions`, `WingetPackageVersions` reading winget-pkgs' version folders and the changelog at a tag) is started by `ScreenLoop` on a pool thread as the console opens (never awaited; a fault is only logged), asks at most once a day, never for a prerelease.
- [ShellExecute](https://learn.microsoft.com/windows/win32/api/shellapi/nf-shellapi-shellexecutew) (`Process.Start` with [`UseShellExecute = true`](https://learn.microsoft.com/dotnet/api/system.diagnostics.processstartinfo.useshellexecute), which cannot be given an environment) starts the associated application with the environment its caller was created with: removing variables from the live process first changes nothing (checked 2026-10-25, Windows 11 26100), and `cmd /c start` shows a blocking dialog for a missing file. `Desktop.OpenAsync` therefore makes the call from a short-lived `pwsh` child started through `IProcessRunner` (cleaned like every child), with the target as Base64 in its script (`OpenFileScript`); a file type registered under `HKCU\Software\Classes` with a handler that writes its environment to a file is the harmless way to test it.
- A file whose type nothing is associated with does not make ShellExecute fail: `Process.Start` with `UseShellExecute = true` and the default `ErrorDialog = false` (which sets `SEE_MASK_FLAG_NO_UI`) on a `.torninoapp` file returned without an exception and Windows opened its "How do you want to open this file?" picker (`OpenWith.exe`) on the desktop, so no `Win32Exception` or native error code (1155, `ERROR_NO_ASSOCIATION`, was expected) reaches the caller (checked 1 November 2026, Windows 11 26100.9711, pwsh 7.6.9 on .NET 10). Never run that start to test it again: it opens the picker. Asking first is harmless: [`AssocQueryString`](https://learn.microsoft.com/windows/win32/api/shlwapi/nf-shlwapi-assocquerystringw) with `ASSOCF_INIT_IGNOREUNKNOWN` (0x400), `ASSOCSTR_PROGID` (20) and no verb answers `0x80070483` (the HRESULT of 1155) for an unassociated extension and S_OK with a ProgID for `.cmd` (`cmdfile`), `.bat`, `.exe`, `.txt` (Notepad's AppX ProgID), `.sln`, `.slnx`, `.ps1` and `.md`; `ASSOCSTR_COMMAND` and `ASSOCSTR_EXECUTABLE` with no verb answered 0x80070483 even for associated types (they need the verb `open`), and an empty extension answers `0x80070057`. `Desktop.OpenAsync` asks it (through `FileAssociations`) for a full file path before starting the `pwsh` child and reports only that exact HRESULT as no application; URLs are never asked about.

## Windows process facts (verified 2026-10-29, Windows 11 26100)

- A process's memory for the detail pane's Memory line and the `m` breakdown is its private working set, read with [`GetProcessMemoryInfo`](https://learn.microsoft.com/windows/win32/api/psapi/nf-psapi-getprocessmemoryinfo) and [`PROCESS_MEMORY_COUNTERS_EX2`](https://learn.microsoft.com/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2) (`PrivateWorkingSetSize`): the figure Task Manager's Memory column and the `Working Set - Private` counter show. It counts resident pages only: an MCP server idle for hours reads a few kilobytes against 90 MB of commit (`PrivateUsage`, the same structure) because Windows has paged its heap out, and thirty node processes share the runtime's image pages, so summing working sets (`WorkingSet64`) doubled a tree's figure. A megabyte is 1,048,576 bytes throughout.
- [`Process.GetProcessById`](https://learn.microsoft.com/dotnet/api/system.diagnostics.process.getprocessbyid) walks the whole process table on every call, about 20 ms: measuring six sessions' 235 processes through it took 4 to 6 s per refresh, against 40 to 230 ms through [`OpenProcess`](https://learn.microsoft.com/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocess) with [`PROCESS_QUERY_LIMITED_INFORMATION`](https://learn.microsoft.com/windows/win32/procthread/process-security-and-access-rights) and [`GetProcessTimes`](https://learn.microsoft.com/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes) (which also reads processes a full-access handle is refused for). Every read in `ProcessRegistry` (`StartTimeOf`, `ParentOf`, `UsageOf`) opens its own limited handle, and `GetProcessById` is used only to end a process. `NtQueryInformationProcess` with `ProcessBasicInformation` (the parent id) and [`QueryFullProcessImageNameW`](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew) (the executable name) answer through that same limited right (checked 2026-11-02, Windows 11 build 26100, 0.20.0-preview.27); `ProcessRegistryIntegrationShould` keeps two hundred start times, parents or usages each under a second.
- [`CreateToolhelp32Snapshot`](https://learn.microsoft.com/windows/win32/api/tlhelp32/nf-tlhelp32-createtoolhelp32snapshot) lists every process with its parent's id in a few milliseconds without opening any; the parent id is never cleared when the parent exits, and Windows reuses ids, so a process may list a parent younger than itself (an installer-launched app sat under a session's reused id during the spike). `ProcessTree` keeps a child only when it started after its nearest measured ancestor.
- [`NtQueryInformationProcess`](https://learn.microsoft.com/windows/win32/api/winternl/nf-winternl-ntqueryinformationprocess) with class 60 (`ProcessCommandLineInformation`) answers a process's command line as a `UNICODE_STRING`; asked with no buffer it answers `STATUS_INFO_LENGTH_MISMATCH` and the length. Command lines carry secrets (an MCP server's API key was in one), so `ProgramLabel` reduces one to a package or executable name and nothing else is kept, logged or shown.

## winget facts (checked 2026-11-02 and 2026-11-03, winget 1.29.380, Windows 11 26100)

- winget's `LocalManifestFiles` setting is an admin setting, off by default (`winget settings export` lists it under `adminSettings`), and enabling it needs an administrator shell, so `winget install --manifest` of an unsubmitted manifest is the owner's step, never an unattended session's. Unprivileged symbolic links need Developer Mode (on since 3 November 2026 on the owner's machine; a session sees it without restarting); without it `ProgramFolderShould`'s link fact skips, and it always runs on CI's runners.
- `wingetcreate` 1.12.13.0 (`microsoft/winget-create`, released 23 July 2026) is what `publish.yml` pins, with its SHA-256; `update <id> --version --urls '<url>|x64' --submit --token` updates an existing manifest and opens the pull request, and fills `ReleaseNotesUrl` and `ReleaseDate` from a GitHub release (its `doc/update.md` at that tag).
- **The install spike (3 November 2026, winget 1.29.380, Developer Mode on, local manifests of this repository's zip and of a single-file probe built the same way, from a throwaway prerelease):** a portable zip is extracted whole into a folder of its own, `%LOCALAPPDATA%\Microsoft\WinGet\Packages\<id>_<source>` (`Source191.Torni__DefaultSource` for a local manifest; the community source's name was not seen), so `libonigwrap.dll`, `CHANGELOG.md`, `torni.ico` and `THIRD-PARTY-NOTICES.txt` sit beside `torni.exe`, and the alias is a symbolic link `%LOCALAPPDATA%\Microsoft\WinGet\Links\torni.exe` to it, that folder already on the user PATH. Started through the link, .NET 10 answers the **link's** folder for both `Environment.ProcessPath` and `AppContext.BaseDirectory` (`...\WinGet\Links\`), where none of the other files are, so Torni reads its own files through `ProgramFolder.Of`, which follows the link with `File.ResolveLinkTarget(..., returnFinalTarget: true)` to the package folder. `torni --version` through the link printed the csproj version. `PackageDependencies` were listed and skipped as already installed.
- `winget upgrade` keeps the same package folder and link. With the program running, it fails with exit `0x8A150052` and "remove: Access is denied" on the executable, **after** deleting the package's other files, so the old executable keeps running but its folder has lost `CHANGELOG.md`, `torni.ico` and the native library until an upgrade with nothing running succeeds (it did, and restored them). `U` avoids it by waiting for Torni to exit; the README says to upgrade with no Torni open.
- A local-manifest install is listed as `ARP\User\X64\<id>__DefaultSource`, so `winget uninstall --id Source191.Torni --exact` finds nothing (`0x8A150014`) and the ARP id must be given; uninstalling removes the link and the package folder and leaves `%LOCALAPPDATA%\Torni` alone. A dotnet tool's shim in `~\.dotnet\tools` comes before the Links folder on the PATH, so it shadows the winget `torni` until it is uninstalled. Not checked: the PATH fallback winget uses without Developer Mode.
