# The checks and the workflows

What each check does and how CI runs it. The commands, and when each check is due, are in `CLAUDE.md`; `CONTRIBUTING.md` is the contributor's account of the same workflows.

## Workflows

- `.github\workflows\pipeline.yml` runs on pull requests and pushes to `main` on a Windows runner and is required by branch protection; a pull request the owner did not open also needs the owner's approval, through `.github\CODEOWNERS` and the "Owner approves main" ruleset, which the owner bypasses for their own.
- It builds Release with the runner image's SDK (no `setup-dotnet`; `global.json` chooses it), tests, checks whitespace only (`dotnet format whitespace --folder --exclude openspec`, because the build already fails on style and analyser warnings; folder mode loads no MSBuild workspace and skips the SDK's generated files, and `openspec`'s archive holds sample `.cs` files outside the solution), publishes the self-contained winget build (`Properties\PublishProfiles\win-x64.pubxml`), zips exactly its five files with `.github\scripts\Compress-WingetBuild.ps1` (which fails on a missing file or any other, a PDB above all) and uploads the zip. The NuGet global packages folder is cached with `actions/cache`, keyed on every `*.csproj`, `Directory.Build.props`, `nuget.config` and `global.json`; caches are scoped by ref, so only runs on `main` write the cache a release restores from. Measured on 2 November 2026 (PR #204, windows-latest, SDK 10.0.403): the `check` job took 169 s against about 3.5 minutes before. A cache hit is about 81 MB, restored in 10 s, and takes the build from 76 s to 52 s. Folder-mode format takes 10 s against 16 s, and `--no-build` saves about 3 s off the smoke check. The `DOTNET_` first-run variables left the pause before restore at 9 to 10 s, against 14 to 32 s in earlier runs, which is within the runners' own variation, so they are kept because they cost nothing rather than for speed. A pull request touching only `openspec\` or `.md` files outside `.github\` skips all of that after the version check, through `.github\scripts\Test-DocumentationOnly.ps1`; pushes to `main` run everything, and a new commit cancels a pull request's older run.
- Every action is pinned to the commit of its release with the version in a comment (Dependabot keeps the pins current; the repository setting requiring pins is turned on once every workflow on `main` has them).
- `.github\workflows\codeql.yml` runs CodeQL over the C# (build mode none) and the workflows on pull requests, pushes to `main` and weekly, never as a required check.
- `pipeline.yml` also publishes a GitHub Release tagged `v<version>` when a push to `main` changes `Version` in the csproj (a separate `release.yml` did until 3 November 2026, building and testing the same commit a second time; the workflow was `check.yml` until then too, and its job is still named `check` because branch protection requires that name): the `check` job's "Decide the release version" step compares the csproj with the first parent, so that run names the zip for the plain `Version` instead of `-ci.N`, smoke-tests that very zip and uploads it as the `release` artefact after the smoke check, and a `release` job (`needs: check`, no checkout) holds `contents: write`, `id-token: write` and `attestations: write` to download it, attach a build provenance attestation and run `gh release create` with it; a commit whose check failed is never released. Nothing reaches winget automatically: `.github\workflows\publish.yml` (`workflow_dispatch` with a `tag` input, one `winget` job in the `winget` environment, which waits for the owner's approval, accepts only `main` and holds the `WINGET_PKGS_TOKEN` environment secret; `contents: read`, `attestations: read`) refuses a tag with a prerelease label, downloads the release's zip, runs `gh attestation verify` with `--signer-workflow` `pipeline.yml` and `--source-ref refs/heads/main`, fails when winget-pkgs has no `manifests/s/Source191/Torni` (HTTP 404 from the contents API; the first version is submitted by hand, MAINTAINING.md), then runs a pinned, hash-checked `wingetcreate update --submit`, failing loudly without the token. For a stable version the `check` job also writes its `CHANGELOG.md` section (`Write-ReleaseNotes.ps1`) into the artefact, and the release job passes it with `--notes-file` beside `--generate-notes` and `--notes-start-tag` the previous stable tag (`gh release list --exclude-pre-releases`), which `gh release create --help` (gh 2.103.3, 1 November 2026) says prepends it to the generated notes. Immutable releases are off for the repository (`gh api repos/Source191/torni/immutable-releases` answered `enabled: false` on 1 November 2026); a fix is a new version all the same. The first step of `check` (`.github\scripts\Assert-VersionBumped.ps1`) fails a pull request that changes the packaged tool without raising `Version`, so each merge of one is a release. The next (`Assert-ChangelogUpdated.ps1`, sharing `ToolPaths.ps1` with it) fails one that leaves `CHANGELOG.md` unchanged or raises `Version` to a stable version without that version's section and an empty Unreleased; the Dependabot bump step adds its pull request's Internal line with `Add-InternalChangelogEntry.ps1`.

## Mutation testing

- Stryker from `test\Source191.Torni.Core.Tests` with `--test-runner mtp` (xunit.v3 scores 0 % under the VSTest bridge) and `--project Source191.Torni.Core.csproj`, scoped with `--mutate "**/Domain/*.cs"` style globs, never solution-relative paths.

## Hand-off check

- `dotnet run --project tools\HeadlessTerminal -- check` runs `torni here` with a throwaway name and no prompt, which makes no model call, waits through `StepRunner` for Claude's `Claude Code v` banner, about 12 s, sends Ctrl+Z and waits for `here` to exit, then stops and removes the job by name; exit 1 means `here` did not exit after the detach, 2 that the check could not start (no Release exe, for one), 3 that the banner never appeared (checked 31 October 2026, CLI 2.1.316). Its defaults are relative to the current folder, so run it from `tools\HeadlessTerminal` (CI: `dotnet run --project . -- check` there) after `dotnet build src\Source191.Torni -c Release`.
- It is the one automated test of a real `claude attach` and detach; the console itself never hands over, so the blocked-UI-thread failure it was first built for can no longer happen.
- A [pseudo-console](https://learn.microsoft.com/windows/console/creating-a-pseudoconsole-session) child is started with [`STARTF_USESTDHANDLES`](https://learn.microsoft.com/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow) and no handles, or its standard output (and Claude's whole screen) would go to the driver's own stdout whenever that is piped, as in CI.
- The `handoff` job in `pipeline.yml` runs the same check on the runner when the `CLAUDE_CODE_OAUTH_TOKEN` secret exists, and never blocks a merge.
- The same tool has `drive` (scripted keystrokes into a ConPTY pseudo-console, capture to drive-raw.txt), `grid` (replay a capture as a screen) and `count` (plain-text markers). Keys sent before Terminal.Gui has initialised (about 8 s on a cold start) are lost, so scripts start at 8000 ms. Setting `LOCALAPPDATA` does not move Torni's state folder: `Environment.GetFolderPath(LocalApplicationData)` asks Windows for the known folder and ignores the variable (checked 1 November 2026, .NET 10, Windows 11 26100), so a `drive` of a local torni.exe reads and writes the real `%LOCALAPPDATA%\Torni` and the Windows Terminal fragments folder, and is for the owner to run, never an unattended session.

## Smoke check of the packed tool

- `smoke <exe> <worktree-folder>` opens and cancels the Keys help, the wizard, the problem report, the first repository root's dialog on the Config tab and its folder picker (F3), the Open folder with dialog (found by filtering for `with`) with Custom chosen and its file picker (F3), the worktrees view, its help, force remove, the fixed-folder wizard (`n`) and the solution chooser (`s`) on an idle linked worktree holding two solutions, then quits; exit 0 passes, 1 is a blocked UI thread, 2 no exe, 4 a step whose marker never appeared (named in the output).
- `smoke-update <exe>` (U opens What's new, Esc closes it) and `smoke-whats-new <exe>` (What's new opens before the console, Esc, the sessions view) need a stable build that has recorded a newer release or an older `last-run.json`, which CI's `-ci.N` prerelease never is, so they are the owner's, with seeded state in the real `%LOCALAPPDATA%\Torni`; running `smoke-update` after `smoke-whats-new` also shows that a second start opens nothing first.
- Its steps take their keys (by hint) and markers (dialog tab titles, a column only each view has, and the worktrees title's ", selected: " as the scan-finished signal, since the WORKTREE cell reads `repository › slug` and never the folder name) from `Wording`, so a new dialog is one step in `SmokeScript`.
- The `check` job installs the Claude Code CLI (signed out: `claude agents --json` prints `[]`), seeds `~\source\repos\Northwind.Smoke` with the linked worktree `Northwind.Smoke-smoke`, extracts the winget zip into a temporary folder and runs its `torni.exe`, so it is the one test of the bits users install.

## Claude Code contract tests

- They start real sessions, so they carry the trait `Category=ClaudeContract` and skip unless `TORNI_CLAUDE_CONTRACT=1`: run them with `$env:TORNI_CLAUDE_CONTRACT = 1; dotnet test --project test\Source191.Torni.Infrastructure.Tests -c Debug -- --filter-trait "Category=ClaudeContract"` from a trusted repository. Accepting a help snapshot is copying its `<name>.received.txt` over it, in a change that re-checks the CLI facts in `claude-code.md`. Never add `--bg --resume --help` to them: it starts a session.

- `test\...\Infrastructure.Tests\Contract` drives the solution's own Claude adapters against the installed CLI (version, a `--bg -n` start with no prompt, the listing's fields and state, stop and rm) and compares the commands and options of `claude --help` and `claude agents --help` with `Contract\Snapshots`.
- `.github\workflows\claude-contract.yml` runs them nightly against the latest CLI, with the hand-off check, in a job with `contents: read`; when the install or a contract test fails, a `report` job (`needs: contract`, `issues: write`) reads the outcomes and the `contract-results` artefact and comments on the open `claude-cli` issue or opens one assigned to the `CLAUDE_CLI_WATCHER` repository variable.
- A snapshot difference leaves `<name>.received.txt` in the output folder (and the run's `contract-results` artefact).
- Automated runs, measured: a prompt-less `claude -p` with its standard input redirected and never written waits 3 s for input, fails on it without a model call and exits 1; on a clean machine (a fresh `CLAUDE_CONFIG_DIR`, as on the runner) it registers as an automated run at about 7 s and exits at about 8.5 s, before a listing can see it, and a user's own hooks lengthen that (the owner's SessionEnd hook adds about 10 s; measured 2026-10-31, CLI 2.1.316). The `ClaudeContract` fact checks the automated-run rule by holding the run open with a SessionEnd hook passed through `--settings` that sleeps for 20 s (listed at about 6 s, exit 1 at about 27 s on a clean machine; a user's SessionEnd hooks run as well and add their time). Start such a run after the console is up when checking the screen, since its first listing takes about 10 s.
