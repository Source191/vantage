# Maintaining Torni

This guide is for the owner: how a merge becomes a release, how a release reaches winget, and the jobs and secrets behind them. Contributors need only [CONTRIBUTING.md](CONTRIBUTING.md).

## Workflows at a glance

| Workflow | Runs | What it does | Secrets and settings |
| --- | --- | --- | --- |
| pipeline.yml, check job | Every pull request and push to main | Version and changelog checks, build, tests, the zip and its smoke check; required by branch protection | DEPENDABOT_BUMP_TOKEN (Dependabot secret) |
| pipeline.yml, release job | A push to main that changes Version | Attests the zip and publishes the GitHub Release (a prerelease for a labelled version) | None beyond the job's own token |
| pipeline.yml, handoff job | With check | The hand-off check against a real Claude session; never blocks a merge | CLAUDE_CODE_OAUTH_TOKEN |
| publish.yml | By hand, with a stable tag | Verifies the release's zip and submits it to winget-pkgs | The winget environment and its WINGET_PKGS_TOKEN |
| claude-contract.yml | Nightly at 03:17 UTC, or by hand | The Claude Code contract tests and the hand-off check against the latest CLI; raises the claude-cli issue | CLAUDE_CODE_OAUTH_TOKEN, CLAUDE_CLI_WATCHER variable |
| codeql.yml | Every pull request and push to main, and weekly | CodeQL over the C# and the workflows; not required | None |

## Releases

A push to `main` that changes `Version` is a release, made by `.github\workflows\pipeline.yml` in the same run that checks the commit. Its `check` job, with read rights only, names the winget zip for the plain `Version` instead of a `-ci.N` prerelease, unzips and smoke-tests that zip and hands it on as an artefact, so each merge builds and tests once and a commit whose check failed is never released; the GitHub Release follows `check` by about half a minute. A `release` job (`needs: check`), which checks nothing out and builds nothing, is the only one with the rights to write and sign: it downloads that artefact, attaches a signed build provenance attestation to it (`gh attestation verify <zip> --repo Source191/torni` checks which commit and workflow built it), and publishes a GitHub Release tagged `v<version>` with `torni_<version>_win-x64.zip` attached. A stable version goes no further until you try it and run `publish.yml` for it (winget, below). Immutable releases are off for the repository (checked 1 November 2026: `gh api repos/Source191/torni/immutable-releases` answers `enabled: false`), so a release's assets could be replaced; never do so: a fix is a new version. A version with a prerelease label (`0.16.2-preview.1`) is published as a GitHub prerelease, so it never becomes the Latest release, with GitHub's generated notes. A stable version's notes are its `CHANGELOG.md` section (written by `Write-ReleaseNotes.ps1` in the `check` job and carried in the artefact), followed by the generated list of pull requests since the previous stable release's tag, so they cover every preview in between; the pull request that raised `Version` to it has already turned Unreleased into that section (CONTRIBUTING.md, The changelog). The "Release tags" ruleset stops anyone but the owner moving or deleting a `v*` tag.

## winget

A stable release is installed with `winget install Source191.Torni`: a portable package of the release's zip, whose manifest lives only in [microsoft/winget-pkgs](https://github.com/microsoft/winget-pkgs) under `manifests/s/Source191/Torni`, never in this repository. A version becomes installable, and the update check sees it, once the pull request adding its manifest is merged there. Prereleases are never submitted.

- **The manifest's shape:** `InstallerType: zip`, `NestedInstallerType: portable`, one nested installer `torni.exe` with `PortableCommandAlias: torni`, `Architecture: x64`, and `Dependencies.PackageDependencies` of `Microsoft.WindowsTerminal`, `Microsoft.PowerShell` and `Git.Git` (install if missing; winget's schema gives them no minimum version, so Torni's own checks still say when one is too old). Claude Code is deliberately not a dependency: winget's `Anthropic.ClaudeCode` was 2.1.302 on 1 November 2026, below the 2.1.309 Torni needs, and does not update itself. `ReleaseNotesUrl` is the GitHub Release page, which `wingetcreate` fills in from the release.
- **The first submission, by hand:** once the first stable release with the zip is published, run `wingetcreate new https://github.com/Source191/torni/releases/download/v<version>/torni_<version>_win-x64.zip` ([wingetcreate](https://github.com/microsoft/winget-create), `winget install Microsoft.WingetCreate`), answer its questions with the shape above (publisher `Source191`, package `Torni`, licence Apache-2.0, the short description from the README), check the manifest with `winget validate --manifest <folder>`, try it with `winget install --manifest <folder>` (which needs `winget settings --enable LocalManifestFiles` from an administrator shell) and submit it. A person reviews the first version; later ones are validated automatically. Until that first manifest is merged into winget-pkgs, `publish.yml` finds no `manifests/s/Source191/Torni` there and fails saying so.
- **Later versions, by hand:** install a stable Release's zip and try it, then run Actions, "publish", Run workflow, from `main`, with the release's tag (`v0.21.0`). `.github\workflows\publish.yml` checks the tag is a stable one, downloads the zip, verifies its provenance attestation was signed by `pipeline.yml` from `main` (so a zip swapped on the release, or a release made any other way, is refused), checks Source191.Torni is in winget-pkgs, then runs `wingetcreate update Source191.Torni --version <v> --urls <zip>|x64 --submit`, which downloads the zip, writes its SHA-256 into the manifest and opens the pull request from a fork of winget-pkgs owned by the token's account. It downloads `wingetcreate.exe` from a pinned release and checks its SHA-256; raise both together. A failed run submits nothing: fix the cause and run it again.
- **The `winget` environment:** Settings, Environments, `winget`, with you as its required reviewer and its deployment branches limited to `main`. The run waits for your approval before any step, and a copy of the workflow on another branch never reaches the environment or its secret. Keep both rules: an environment without them hands its secrets to any run that names it.
- **`WINGET_PKGS_TOKEN`:** a secret of the `winget` environment (Settings, Environments, `winget`, Environment secrets), never a repository secret, so only an approved run from `main` can read it. It holds a classic personal access token with the `public_repo` scope, from the account whose fork of winget-pkgs the pull requests come from (wingetcreate makes the fork if there is none). Without it, or when it has expired, the run fails and names it: replace the secret and run the workflow again.
- **When a submission waits:** winget-pkgs' validation can queue for hours, and its bot may ask for changes on the pull request. Nobody is offered the version meanwhile, because the update check reads only merged manifests. A version is removed only by a pull request to winget-pkgs; a bad release is superseded by a new version.

## Reviews and merging

The "Owner approves main" ruleset requires a code owner's approval, and `.github\CODEOWNERS` names the owner for every path, so a pull request opened by anyone else (an app or Dependabot included) waits for that review. The owner merges their own pull requests through the ruleset's bypass (`gh pr merge --admin`), so auto-merge does not fire for them.

## Dependabot and the version bump token

Dependabot updates the NuGet packages and the actions' pins weekly, and security updates are on, so a dependency with a known vulnerability gets a pull request at once (the build's NuGet audit fails on it anyway). A Dependabot pull request that touches the tool is bumped for you: a step before the version check raises `Version` on the pull request's branch, commits "Raise Version to <version> for the dependency update" and pushes it with `DEPENDABOT_BUMP_TOKEN`, a fine-grained personal access token with Contents read and write on this repository, stored under Settings, Secrets and variables, Dependabot (a Dependabot run can read only those). The run for the pushed commit is the one branch protection reads; you still review and merge. When the token expires the step fails naming it: create a new one and replace the secret.

## Supply chain

Every action the workflows use is pinned to the commit of its release, with the version in a comment, so a moved tag cannot change what runs; Dependabot updates the pins, and the repository setting that requires such pins is turned on once every workflow on `main` carries them. The `CLAUDE_CODE_OAUTH_TOKEN` secret reaches the latest Claude Code CLI that the `handoff` and `claude-contract` jobs install from `claude.ai`, so it belongs to an account that has nothing else and is rotated like a password.

## The hand-off job

`handoff` installs Claude Code on the runner and runs the hand-off check from `tools\HeadlessTerminal` against a real throwaway session. It needs the `CLAUDE_CODE_OAUTH_TOKEN` repository secret (from `claude setup-token`); without one it skips with a notice, as it does for a documentation-only pull request. It builds only the tool (`src\Source191.Torni`), because `check` builds and runs the tests, and installs Claude Code in the background while it builds. It never blocks a merge, because its keystroke timings were tuned on a laptop and a slow runner can fail it for reasons that are not bugs; read its `handoff-capture` artefact when it does.

The runner has no desktop, so the job seeds workspace trust for the checkout in its own `~\.claude.json`, which, with the nightly contract check, is the only place that record is ever written by a script. Torni strips `CLAUDE_CODE_*` from the environment of the `claude` processes it starts (`InheritedEnvironment`), so the token reaches the throwaway session the harness starts but not Torni's own `claude agents` and `claude attach`; the live runs show the attach reaches Claude's screen all the same. The check exits 3 when it does not: Claude's screen must be in the capture, not only Torni's.

## The nightly Claude Code contract check

Claude Code's native installer updates the CLI in the background, so users soon run a newer CLI than Torni was verified against. `.github\workflows\claude-contract.yml` runs every night at 03:17 UTC, and by hand from Actions, "claude-contract": it installs the latest CLI, runs the `ClaudeContract` tests (Torni's own Claude adapters against that CLI: the version, a background session started with no prompt, listed with every field Torni reads in a state it knows, then stopped and removed; and the commands and options in `claude --help` and `claude agents --help` against the snapshots in `test\Source191.Torni.Infrastructure.Tests\Contract\Snapshots`), then the hand-off check. It needs the same `CLAUDE_CODE_OAUTH_TOKEN` secret and seeds trust the same way; without the secret it skips with a warning. It never runs on pull requests, so a CLI release never blocks a merge.

- **The claude-cli issue:** when the latest CLI fails to install or a contract test fails, a `report` job of its own, the only one with `issues: write`, reads the contract job's outcomes and its `contract-results` artefact and comments on the open issue labelled `claude-cli`, or opens one when none is open, with the CLI version, the run link and the failing tests' messages. It assigns a new issue to the GitHub login in the `CLAUDE_CLI_WATCHER` repository variable (Settings, Secrets and variables, Actions, Variables); an assignee is subscribed to the issue, so GitHub notifies them of every comment. Close the issue by hand once the fix is merged. The hand-off check marks the run but never raises the issue.
- **Accepting a snapshot:** a difference leaves `<name>.received.txt` in the run's `contract-results` artefact (and in the test output folder locally). Copy it over the snapshot in a change that re-checks the CLI facts in `.claude\rules\claude-code.md`, so a new flag is either used, deliberately ignored or recorded.
- **Never** add `--bg --resume --help` to the contract tests: it starts a session.
